# Работа и проверка RAG дня 22

День 22 добавляет к индексам дня 21 генерацию ответа DeepSeek. Можно задать один вопрос и сравнить знания модели с ответом, которому переданы фрагменты русской Pro Git. Поиск остаётся локальным; текст вопроса и выбранные фрагменты в режиме RAG уходят в DeepSeek API.

## Запуск на Windows

Ветка `ai-challenge-day-22` создана от коммита дня 21 `3ee1ace`. Из `F:\ai-advent-challenge\ai-chat\rag`:

```powershell
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml up -d --build
```

В этой машине существующий корневой `.env` содержит LLM_API_KEY. Compose передаёт только выбранный секрет в DEEPSEEK_API_KEY контейнера backend; остальные ключи из файла не копируются в его окружение. Новую копию секрета в репозитории не создаём. Если используете собственный `rag/.env`, задайте там DEEPSEEK_API_KEY и запускайте без `--env-file ../.env`. Реальные `.env` исключены из Git и Docker build context. Не показывайте вывод `docker compose config` или env контейнера на видео: он может содержать ключ.

Без GPU уберите `-f compose.gpu.yml`. UI остаётся на http://localhost:8383, API — 8382. Compose project по-прежнему называется `ai-chat-rag-day-21`: имя намеренно сохраняется, чтобы использовать прежние volumes модели и SQLite. Ничего не удаляйте через `down -v`.

Модель генерации задаётся серверным DEEPSEEK_MODEL, по умолчанию `deepseek-flash`. Thinking отключён, temperature=0 в обоих режимах. Ключ не вводится в браузере и не возвращается в DTO. Указанный моделью фактический model сохраняется в результате. Актуальные имена и параметры сверены с [документацией DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/) и [thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/) 4 октября 2026 года.

## Алгоритм одного ответа

1. Vue отправляет question, mode, indexId, topK, contextMaxCharacters и необязательный maxOutputTokens. Ключа в запросе нет.
2. AnswerController проверяет поля и передаёт DTO в AnswerService.
3. BASELINE не читает индекс и не обращается к Ollama. RAG вызывает SearchService: embedding вопроса, проверка пространства модели, cosine search сохранённых векторов, top-K.
4. PromptAssembler отбирает целые чанки в порядке ranking. Не помещающийся чанк пропускается; небольшой последующий может поместиться. Бюджет считает только их тексты в UTF-16, не JSON-обёртку, системный промпт или токены API. Если не поместился ни один, вернётся ошибка до вызова LLM.
5. Одинаковый системный промпт объясняет правила обоих режимов. В user JSON есть question; только RAG добавляет book_context с source, section, chunk_id и текстом.
6. DeepSeekLlmClient делает один HTTP-запрос. Отсутствующий maxOutputTokens не превращается в 1200: поле max_tokens не отправляется. У провайдера остаются собственные ограничения и значения по умолчанию.
7. Backend проверяет финальный content и usage. Пустой ответ — явная ошибка; length — частичный ответ с предупреждением. Автоматического retry и скрытого платного judge нет.
8. UI показывает ответ, фактический расход, время, контекст и messages. У двух колонок независимые ошибки. Результаты переживают переключение вкладок, но не reload страницы: это лаборатория сравнения, не чат дня 25.

Сравнение запускает два отдельных платных вызова с одним снимком вопроса и настроек. Разница входных данных — материалы книги. Temperature=0 снижает случайность, но не гарантирует побайтно одинаковые ответы при повторениях.

## Проверка через интерфейс

1. Откройте UI и раздел «Ответы с RAG / без RAG». Должны быть видны модель, два режима, настройки и 10 контрольных вопросов.
2. Выберите `stash`. Раскройте «Ожидание и источник для проверки»: -u включает untracked, но не ignored; -a включает оба вида. Источник — stashing-cleaning.asc.
3. Выберите STRUCTURAL индекс 3000/300. Оставьте top-K=5, бюджет=16000; лимит ответа пустой. Для ограниченного теста можно явно ввести 1200, но неполный ответ не считать правильным результатом.
4. Нажмите «Сравнить ответы · 2 API-вызова». Дождитесь обеих колонок. Сравните факты, полноту и объяснение рисков, а не только длину текста.
5. В колонке RAG раскройте контекст. Найдите источник, прочитайте чанк, откройте сохранённый документ. В BASELINE контекст пустой. Раскройте messages: в RAG есть book_context, в BASELINE его нет.
6. Сравните input/output/total API и время. У RAG обычно больше входных токенов, поскольку он получает книгу; больше токенов не доказывает лучший ответ.
7. Скачайте MD или JSON. MD содержит поля ручного вывода: совпадения, ошибки, полезные материалы и результат сравнения.
8. Повторите на всех 10 вопросах. Можно использовать FIXED вместо STRUCTURAL и дополнительно оценить влияние chunking, но не менять индекс между двумя частями одного эксперимента.
9. Для ошибки бюджета задайте top-K=1 и бюджет=300 с вопросом reset. Если найденный чанк длиннее бюджета, RAG должен объяснить отказ без генерации; BASELINE при этом может ответить.
10. Перейдите в «Корпус документов» и вернитесь: результаты остаются. После reload они исчезнут; сначала скачайте отчёт.

## Расход и стоимость

Input/output/total и cache hit/miss берутся из ответа API, не из локального токенизатора. Embedding input tokens относятся к локальному Ollama и не прибавляются к оплачиваемым DeepSeek-токенам. Если провайдер не вернул usage, приложение пишет «неизвестно», а не 0.

Оценка стоимости использует снимок [официальных тарифов](https://api-docs.deepseek.com/quick_start/pricing/) от 2026-10-04. Диапазон охватывает off-peak/peak; не угадывает праздничный календарь и реальное списание. Когда cache split отсутствует, расширяет диапазон неопределённости. Проверять реальный платёж нужно в кабинете провайдера. Будущая смена цены требует обновления CostEstimator; неизвестная модель не получает выдуманный тариф.

## Автоматическая проверка

```powershell
pwsh -File ./scripts/verify-day22.ps1
```

Это **20 платных LLM-вызовов**: 10 вопросов × 2 режима. В тесте явно задаётся 1200 output tokens, а не меняется дефолт приложения. Проверяются source anchors в snapshot, непустые ответы, usage, отсутствие контекста BASELINE и соответствие book_context показанным чанкам. JSON с полными результатами сохраняется после каждой пары в игнорируемый `data/day22-live-results.json`. Скрипт не выдаёт автоматическую оценку истинности.

`npm run test:e2e` запускает обычные UI-тесты без платной генерации. Live UI-тест включается отдельно через RAG_LIVE=true и добавляет 2 платных вызова. Kotlin-тесты адаптера используют локальный HTTP fixture, не API DeepSeek.

## Границы задания

Нет reranker/query rewrite, обязательных проверенных цитат, LLM judge и памяти диалога. Чанки в контексте — найденные материалы, не доказательство поддержки каждого утверждения ответа. Предупреждение и инструкции в промпте не гарантируют отсутствие галлюцинаций. Проверка источников/цитат появится в дне 24, полноценный чат — в дне 25.

Схема [Archify](diagrams/day22-architecture.html) показывает доменные вызовы, не все обратные HTTP-ответы. SearchService возвращает отобранные материалы AnswerService, а DeepSeek возвращает ответ/usage; SQL не вызывает LLM напрямую. Русские подписи схемы; встроенный Viewer и html lang используют English fallback.
