# День 23: фильтр и переформулировка запроса

Приложение использует готовые индексы дня 21. Перестраивать их для этого задания не нужно. Новая вкладка — **«Фильтр и rewrite»** на [localhost:8383](http://localhost:8383/).

## Как работает запрос

1. UI отправляет один POST `/api/v1/experiments/compare` с исходным вопросом и настройками сравнения.
2. `ExperimentService` проверяет параметры и существование индекса **до** платного rewrite.
3. Если выбран режим с rewrite, `LlmQueryRewriter` просит DeepSeek вернуть JSON с одним полем `query`. Это поисковая формулировка, не ответ. Фактический исходный вопрос сохраняется отдельно.
4. `SearchService` вычисляет embedding поискового запроса через локальный Ollama и возвращает candidate top-K из выбранного SQLite-индекса. Для исходного и rewritten query выполняется максимум по одному поиску.
5. `SimilarityCandidateSelector` применяет порог только в режимах FILTERED/REWRITE_FILTERED и оставляет максимум final top-K. Порядок cosine-ranking не меняется. Каждый кандидат получает решение: SELECTED, BELOW_THRESHOLD или TOP_K_LIMIT.
6. `PromptAssembler` укладывает отобранные целые чанки в бюджет. Исключение по порогу и исключение по бюджету — разные события и отображаются раздельно.
7. `AnswerGenerator` получает **исходный** вопрос и фактически упакованные чанки. Во всех режимах одна системная инструкция и модель. Генерации независимы и могут выполняться параллельно.
8. API возвращает сравнение, общую запись rewrite и отдельные результаты. UI позволяет прочитать материалы, фактический промпт, расход и скачать отчёт.

Пример: вопрос «Как временно спрятать новые файлы, которые Git ещё не отслеживает?» может превратиться в запрос поиска с терминами `git stash`, `untracked`, `-u`. Модель ответа всё равно отвечает на первоначальный вопрос. Rewrite может не улучшить выдачу; именно поэтому контрольная колонка сохраняется.

## Режимы

| UI | API | Поиск | Отбор |
| --- | --- | --- | --- |
| Обычный RAG | RAW | Исходный вопрос | Final top-K, без порога |
| RAG + фильтр | FILTERED | Исходный вопрос | Threshold + final top-K |
| RAG + rewrite | REWRITE | Переформулированный запрос | Final top-K, без порога |
| RAG + rewrite + фильтр | REWRITE_FILTERED | Переформулированный запрос | Threshold + final top-K |

RAW — не ответ «без RAG». Для сравнения без RAG остаётся отдельная вкладка дня 22 **«Ответы с RAG / без RAG»**.

## Настройки простыми словами

- **Кандидатов до отбора:** сколько лучших фрагментов достать из индекса. По умолчанию 10; допустимо 1–20.
- **Максимум после отбора:** сколько разрешено оставить. По умолчанию 5; допустимо 1–10 и не больше candidate K.
- **Порог cosine:** минимальный score для режимов с фильтром. По умолчанию 0,65. Равенство порогу проходит; меньше порога — исключается. Это не «65% уверенности».
- **Бюджет текста чанков:** максимум UTF-16 символов текста целых чанков, по умолчанию 16000. Это не токены и не полный размер API-запроса: JSON, metadata и инструкции добавляют объём.
- **Лимит ответа:** пустое поле не передаёт `max_tokens` провайдеру. 1200 использовано только в автоматическом эксперименте. Если видите `length`, увеличьте лимит или очистите поле.

Для технического rewrite отдельно задано 512 output tokens. Обрезанный, пустой или некорректный JSON считается ошибкой, а не хорошим поисковым запросом. [Официальная документация DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/) описывает JSON mode; он помогает с форматом, но не гарантирует правильность смысла.

## Проверка через UI для записи видео

1. Откройте новую вкладку. Выберите STRUCTURAL индекс `254 чанка · 3000/300`.
2. Оставьте три режима по умолчанию: обычный RAG, фильтр, rewrite + фильтр. Настройки: 10 кандидатов, максимум 5, порог 0,65, бюджет 16000, пустой лимит ответа.
3. Выберите контрольный вопрос **add-snapshot**. Откройте «Ожидание для проверки»: должен быть ответ про состояние файла на момент последнего `git add`, а не последнюю правку рабочего файла.
4. Нажмите **«Сравнить ответы»**. Это до четырёх платных вызовов: один общий rewrite и три генерации. Автоматического повтора нет.
5. Найдите блок «Было / Стало». Проверьте, что новая формулировка не изменила смысл. В карточках сравните числа «Найдено → отобрано → передано LLM».
6. Раскройте «Кандидаты до и после отбора». Найдите исключённые низкие score. Отдельно откройте текст выбранного чанка и источник: это документ **snapshot выбранного индекса**, не текущая копия книги.
7. Прочитайте три ответа. Версия файла на момент `add` должна остаться основным выводом. Меньшее число токенов само по себе не доказывает более точный ответ.
8. Раскройте «Реальный контекст и messages». Убедитесь, что поле `question` содержит первоначальный вопрос, а `book_context` — реально переданные чанки. Общая статистика считает rewrite один раз.
9. Скачайте MD и JSON до перезагрузки страницы. Смена вкладок сохраняет результат в текущей странице, reload — нет.
10. Для второго примера выберите **stash**: `-u` включает untracked, но не ignored; для ignored нужна `-a`. На проверенном индексе фильтр сократил контекст с пяти до четырёх чанков, но результат нового запуска может отличаться.

## Пустой результат и бесплатная проверка фильтра

1. Отключите оба режима с rewrite. Оставьте RAW и FILTERED.
2. Введите «Как приготовить борщ?» и нажмите **«Только поиск · без LLM»**.
3. RAW вернёт лучшие из доступных фрагментов, хотя они не подходят вопросу. FILTERED при 0,65 должен показать `NO_CONTEXT`, а не рецепт. Генерация не выполнялась.
4. Верните вопрос про Git. Поднимите порог до 1 и снова запустите поиск: на текущих примерах он отсечёт все фрагменты. Уменьшите порог до 0,65 и сравните.
5. Не делайте вывод «в книге нет ответа» только по пустой выдаче. Возможны слишком высокий порог, неудачный embedding или формулировка вопроса.

Кнопка **«Только поиск»** с включённым rewrite всё равно делает **один платный вызов** для переформулировки. В UI это подписано. Embeddings вычисляются локально.

## Ошибки и границы задания

Если rewrite сломан, колонки RAW/FILTERED сохраняются, а режимы rewrite показывают ошибку. Если одна генерация завершилась ошибкой, остальные ответы остаются. Если ни один целый чанк не помещается в бюджет, появляется `context_budget_too_small`; тихого обрезания чанка нет. Если score низкий, no-context gate пропускает платную генерацию.

Это не чат с памятью и не автоматическая оценка цитат. Источники в карточках — данные запроса, а не гарантия поддержки каждого предложения. Сравните факты с ожиданием и найденным текстом; длинный ответ или большой score не означают победу режима.
