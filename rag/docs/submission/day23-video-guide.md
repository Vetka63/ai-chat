# День 23 — сценарий видео: фильтрация и query rewrite

Цель — показать найденных кандидатов, отбор, реальный контекст и изменение качества/расхода. Реализован cosine-фильтр с final top-K; это не cross-encoder reranker. Rewrite меняет поисковый запрос, сохраняя исходный вопрос для генерации. Ориентир: 10–15 минут плюс полный контрольный прогон.

Фактические результаты последней проверки: [общий финальный отчёт](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Ожидаемое поведение ниже не доказывает успех нового запуска. [Ранний отчёт дня 23](../day23-test-results.md) содержит исторические измерения, которые нельзя выдавать за новый прогон.

## 2. Объяснить четыре режима

Откройте **«Фильтр и rewrite»** → панель **«Что меняется после поиска»**.

> «В дне 22 сравнивались ответы с книгой и без книги. Здесь все четыре режима — RAG: обычный retrieval, пороговый отбор, переформулировка поискового запроса и их сочетание».

| UI | API | Поиск | Отбор |
| --- | --- | --- | --- |
| «Обычный RAG» | RAW | Исходный вопрос | Final top-K без порога |
| «RAG + фильтр» | FILTERED | Исходный вопрос | Порог, затем final top-K |
| «RAG + rewrite» | REWRITE | Переписанный запрос | Final top-K без порога |
| «RAG + rewrite + фильтр» | REWRITE_FILTERED | Переписанный запрос | Порог, затем final top-K |

> «RAW — обычный RAG, а не ответ без RAG. Фильтр сохраняет порядок cosine-ranking, не пересчитывает score отдельным reranker. 0,65 — не 65 процентов уверенности».

Зафиксируйте:

| Поле | Значение |
| --- | --- |
| «Индекс эксперимента» | STRUCTURAL, 3000/300 |
| «Кандидатов до отбора» | 10 |
| «Максимум после отбора» | 5 |
| «Порог cosine» | 0.65 |
| «Бюджет текста чанков» | 16000 |
| «Лимит ответа, токены» | Пусто |

Сначала находится до 10 кандидатов, затем порог в режимах с фильтром, максимум 5 и бюджет целых чанков. Поэтому «отобрано» может отличаться от «передано LLM». Модель, системная инструкция и исходный вопрос у режимов одинаковые. Temperature 0 не гарантирует дословной повторяемости.

## 3. Изолировать фильтр без платной генерации

Оставьте галочки только **«Обычный RAG»** и **«RAG + фильтр»**; оба rewrite-режима выключите. В **«Контрольный вопрос дня 23»** выберите `add-snapshot`:

> Я выполнил git add file.txt, затем ещё раз изменил file.txt. Какая версия попадёт в коммит без повторного git add и почему?

Откройте **«Ожидание для проверки»**: commit содержит версию на момент add, новая правка остаётся вне индекса. Источник — `recording-changes.asc`.

Нажмите **«Только поиск · без LLM»**. Общая сводка должна показать **«LLM-стадий: 0»**. В обеих карточках раскройте **«Кандидаты до и после отбора»**. Сопоставьте одинаковые `chunk_id`, rank и cosine: RAW/FILTERED разделяют один исходный pool.

Найдите решения **«Отобран»**, **«Ниже порога»**, **«Лимит final top-K»**. Все три необязательно встречаются на каждом вопросе.

> «Различается только отбор: score меньше 0,65 исключается, равный порогу проходит; final K ограничивает оставшиеся фрагменты. Сейчас ответы вообще не генерируются».

В preview «передано LLM 0» нормально даже при ненулевом «отобрано»: выбрана кнопка поиска, не генерации.

Поставьте **«Максимум после отбора»** = 2 и повторите бесплатный поиск: выбранных станет не больше двух. Зафиксируйте, затем верните 5. Если threshold 0.65 не изменил пятёрку, скажите об этом; отсутствие эффекта на конкретном вопросе — тоже результат.

## 4. Основной опыт с ответами

Верните 10 → 5, threshold 0.65, budget 16000. Сохраните исходный `add-snapshot`. Выберите три режима: **«Обычный RAG»**, **«RAG + фильтр»**, **«RAG + rewrite + фильтр»**.

Нажмите **«Сравнить ответы · до 4 API-вызовов»**. Верхняя граница — один общий rewrite и три генерации; при пустом контексте генерация пропускается. Для полного сравнения 2×2 перед запуском включите также **«RAG + rewrite»**: кнопка станет **«Сравнить ответы · до 5 API-вызовов»**. Четвёртая колонка отделяет эффект rewrite от фильтра.

> «Переформулировка одна общая, а не отдельная для каждой колонки. Дальше режимы отвечают на первоначальный вопрос со своим контекстом. Расход rewrite учитывается отдельно и в общей сумме один раз».

Дождитесь результата. Автоматических повторов нет; ошибка одной колонки не стирает остальные. Не повторяйте незаметно ради удачного ответа.

## 5. Показать «Было / Стало» и реальный контекст

1. В **«Общий rewrite · только для поиска»** прочитайте **«Было»** и **«Стало»**. Смысл должен сохраниться: файл подготовили, снова изменили, повторного add не было.
2. Раскройте **«Промпт и JSON rewrite»**: это поисковое поле `query`, не ответ.
3. В строках **«Поиск»** у RAW/FILTERED должен быть исходный вопрос, у rewrite-режимов — общая новая формулировка.
4. Сравните **«Найдено … → отобрано … → передано LLM …»**.
5. В **«Кандидаты до и после отбора»** найдите `recording-changes.asc`, раскройте текст → **«Открыть источник эксперимента»**. Прочитайте объяснение версии на момент `git add`.
6. В **«Реальный контекст и messages»** покажите первоначальный `question`, фактический `book_context`, количество переданных и **«не поместилось»**.

> «Rewrite используется для поиска; модель ответа всё ещё видит исходную пользовательскую задачу. Отсечение по порогу и исключение из-за бюджета — разные этапы».

Если rewrite поменял смысл, запишите это как ошибку переформулировки. Даже правильный ответ не отменяет дефекта этого шага. Точная формулировка rewrite и число чанков не обязаны совпасть с предыдущим запуском.

## 6. Сравнить качество и затраты

Основной ожидаемый вывод всех колонок: commit включает версию на момент последнего `git add`. Проверьте и дополнительные объяснения индекса/рабочих файлов. `length`, `NO_CONTEXT`, API-ошибку и неверный факт отмечайте отдельно.

При равном качестве:

> «Основной факт во всех ответах верен. В этой попытке фильтр [сократил / не изменил] контекст. Это эффект на входной объём, но не доказательство большей точности».

При ухудшении назовите точную потерю: полезный источник отфильтрован, rewrite увёл поиск, ответ исказил факт. Оставьте случай в отчёте.

Покажите API input/output/total каждой генерации, usage/время rewrite и общую сумму. Сравнивайте всю цепочку: экономию входа генерации может съесть rewrite. Один запуск не доказывает стабильный выигрыш скорости; output зависит от длины сформированного ответа.

Нажмите **«Скачать эксперимент MD»** и **«Скачать эксперимент JSON»**. Сохраните как `day23-add-snapshot-attempt1.md/json`: стандартное имя одинаково у разных опытов. Смена вкладок сохраняет результат текущей страницы, reload — нет.

## 7. Разговорный вопрос для rewrite

Выберите **«Свой вопрос»** и введите:

> Как временно спрятать новые файлы, которые Git ещё не отслеживает?

С теми же режимами выполните отдельный опыт и сохраните его. Возможные полезные термины rewrite — `git stash`, `untracked`, `-u`, но дословный результат не задан. Ожидаемый источник — `stashing-cleaning.asc`; правильный ответ объясняет `-u`/`--include-untracked`.

> «Разговорная формулировка проверяет переход к терминологии книги. Больший score ещё не означает лучший ответ: смотрю найденный текст и факты. Rewrite может ничего не улучшить или ухудшить поиск».

Опыт требует до четырёх или пяти новых вызовов. В коротком ролике его можно опустить при наличии полного контрольного прогона; нельзя незаметно заменить им неудачный основной пример.

## 8. Пустой контекст и действие порога

Снова оставьте только **«Обычный RAG»** и **«RAG + фильтр»**. Введите:

> Как приготовить борщ?

Нажмите **«Только поиск · без LLM»**, покажите `LLM-стадий: 0`. RAW выдаёт ближайшие фрагменты про Git, что не делает их подходящими. При 0.65 на проверенном корпусе ожидается `NO_CONTEXT` у FILTERED. Если что-то прошло, покажите это как ложное прохождение фильтра.

Верните `add-snapshot`, поставьте **«Порог cosine»** = 1 и повторите бесплатный поиск. Все кандидаты со score ниже 1 должны быть отсечены FILTERED, RAW порог игнорирует. Если есть score ровно 1, он проходит по правилу `>=`: значение 1 не запрещает любой результат математически.

> «NO_CONTEXT значит, что после отбора не осталось материала. Это не доказывает, что в книге вообще нет ответа: слишком строгий порог может отсечь полезный текст».

Чтобы показать пропуск именно генерации, оставьте **только «RAG + фильтр»** в опыте, где preview уже дал ноль выбранных чанков. Нажмите **«Сравнить ответы · до 1 API-вызовов»**. Ожидается `NO_CONTEXT`, нет ответа, **«LLM-стадий: 0»**: сервер пропустил генерацию без контекста. Кнопка показывает максимум, сводка — факт. Верните 0.65 после проверки.

Если включён rewrite, кнопка поиска называется **«Только поиск · 1 платный rewrite»** — такой preview уже платный. Для проверок выше оба rewrite-режима должны быть выключены.

Автоматический повтор из `rag`, в PowerShell 7:

```powershell
pwsh -File ./scripts/verify-day23.ps1
```

До **40 новых платных вызовов**: десять случаев × общий rewrite и три ответа, плюс три бесплатных preview без rewrite. Скрипт использует RAW/FILTERED/REWRITE_FILTERED, по умолчанию явно задаёт `2400` output tokens и проверяет технический контракт, а не смысл. При раннем сбое полный набор не считается выполненным. Каждый запуск создаёт отдельный `rag/data/day23-live-results-<timestamp>-<id>.json`; точный путь печатается в консоли. Полученный эксперимент сохраняется до проверок, прежние файлы остаются. Параметр `-MaxOutputTokens` меняет тестовый cap. UI с пустым лимитом — другие условия; укажите также фактическую ветку и commit.
