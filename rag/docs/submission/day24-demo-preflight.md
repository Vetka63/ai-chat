# День 24: подготовка короткой демонстрации — 5 октября 2026

## Что реально остаётся в интерфейсе

В новой доработке раздел **«Источники и цитаты» → «Сохранённые результаты»** сохраняет каждый полученный результат, включая отказ и ошибку проверки, в IndexedDB этого браузера. Это **набор отдельных вопросов и ответов, не чат**. После обновления страницы открывается последний результат; остальные выбираются в списке. Полная диагностика не обрезается. Индекс и вопрос указаны в сохранённой записи. История не переносится в другой браузер; для резервной копии нужен экспорт JSON.

Уже оплаченный JSON можно открыть через **«Открыть ранее скачанный JSON без нового запроса к LLM»**. Импорт проверяет структуру по OpenAPI и координаты цитат, но не доказывает происхождение файла, смысл или качество текущего кода. Поэтому UI явно пишет **«Импортированный результат»** и **«Статус в файле»**. Дата в таком случае — дата импорта. Кнопка открытия цитаты отдельно сверяет точный текст с доступным snapshot. Никакие образцовые ответы не встроены в приложение.

В поле **«Импорт JSON-ответов»** можно выбрать до 20 файлов одновременно, каждый не больше 20 МБ и содержит один raw `GroundedResult`. Все проходят отдельную проверку: корректные сохраняются, ошибки показываются по именам файлов, частичные успехи не откатываются. Общий aggregate-отчёт со списком `cases` не подойдёт: экспортируйте отдельные результаты. Если выбрано больше 20 файлов, весь этот выбор отклоняется без изменения уже сохранённой истории.

День 25, в отличие от этой вкладки, сохраняет настоящие чаты и память задачи на сервере в SQLite.

Проверка доработки хранения и пакетного импорта: 16 клиентских unit-тестов и TypeScript прошли; 33 бесплатные браузерные регрессии прошли на client image `3fb9f034c189d142b69a8272e1463abad215ca9f04056a51c840dbcc97bb5d12`. В их числе восстановление после refresh, импорт с постоянной предупреждающей меткой и нулём вызовов генерации, частичный успех пакета, ограничения размера/количества файлов, мобильная ширина. Ответы LLM в этих UI-тестах подставлены тестовым сервером: это доказательство работы интерфейса, **не live-приёмка качества RAG**. Настоящий исторический stash JSON также прочитан новым валидатором без изменения текста.

## Рекомендуемая короткая запись

1. Открыть вкладку «Источники и цитаты». Выбрать STRUCTURAL 3000/300, K=20/10, порог 0.60, бюджет источников 32000, cap генерации 16384, rewrite выключить.
2. Начать с вопроса: **«Как git stash сохранить untracked-файлы? Включает ли -u файлы из .gitignore?»**
3. При `ANSWERED` показать текст, цитату, source/section/chunk_id. Открыть цитату в документе и подсветку. Прочитать оговорку: `-u` не включает игнорируемые файлы; для них нужен `-a`.
4. Показать диагностику фактических вызовов и расход; скачать MD и JSON. После refresh выбрать результат снова: новый запрос не выполняется.
5. Для отказа поставить порог **1** и спросить **«Как работает git stash?»**. Показать `UNKNOWN`, уточнение, пустой отбор и фактическое отсутствие LLM-стадий. Вернуть порог 0.60. Это намеренно строгий тестовый порог, а не доказательство автоматического распознавания всех посторонних вопросов.
6. При наличии бюджета второй положительный пример: **«Выполняет ли git fetch слияние с текущими наработками? Ответь кратко только об этом.»**
7. Переключиться между сохранёнными вопросами. Если использован старый JSON, проговорить: «Это сохранённый результат предыдущего запуска; сейчас я показываю его проверку по книге, а не новую генерацию».

Не скрывать `INVALID_EVIDENCE` и не заменять отклонённый результат вручную. Такой статус демонстрирует блокировку, но не считается полезным ответом. Короткий сценарий не заменяет полный контрольный набор из десяти вопросов.

## Почему выбраны эти вопросы

В корпусе есть прямые общие правила, не требующие переносить условия книжного примера на произвольную задачу:

| Вопрос | Прямая опора в корпусе |
| --- | --- |
| Какие файлы `git stash` сохраняет по умолчанию? | `book/07-git-tools/sections/stashing-cleaning.asc`: «По умолчанию `git stash` будет сохранять только изменённые и проиндексированные _отслеживаемые_ файлы». |
| Как включить неотслеживаемые файлы в stash? | Там же: «Если вы укажете опцию `--include-untracked` или `-u`, Git также припрячет все неотслеживаемые файлы, которые вы создали». |
| Включает ли `stash -u` игнорируемые файлы, и какая опция их включает? | Там же следующий абзац различает `-u` и `--all`/`-a`. |
| Выполняет ли fetch слияние? | `book/02-git-basics/sections/remotes.asc`: «команда `git fetch` забирает данные в ваш локальный репозиторий, но не сливает их с какими-либо вашими наработками». |
| После `git add` файл снова изменился. Какая версия попадёт в коммит без нового add? | `book/02-git-basics/sections/recording-changes.asc`: «версия файла, существовавшая на момент выполнения вами команды `git add`, будет добавлена в историю снимков состояния». |

Ожидаемые цитаты — подсказка проверяющему человеку, не готовый ответ, передаваемый генератору.

#### Причина отказа в вопросе 6

Raw trace: `data/video-day24-20261005T070255116-06ca456a-result.json`. Первичный проверяющий дважды признал пункт `SUPPORTED`, `claim_scope=general`: в E5 прямо есть правило «Git индексирует файл в точности в том состоянии, в котором он находился, когда вы выполнили команду git add». Но независимая source-only разметка классифицировала весь chunk `4a7334bc3ec64e866c79da2f` как `example` из-за соседнего примера `CONTRIBUTING.md`. Детерминированное несовпадение GENERAL/EXAMPLE превратило итог в `REJECTED`.

Разрешённое однократное исправление добавило E36 — общее описание сохранения снимка проиндексированных файлов, — но сохранило E5. Поэтому тот же запрет сработал снова. Это воспроизведение известного **ложного отказа из-за слишком грубой классификации контекста**, а не отсутствие нужного правила в книге и не доказанная галлюцинация ответа. Отклонённые черновики сохранены только в диагностике; публиковать их как успешный ответ нельзя. В этом демонстрационном проходе код защиты не менялся.
