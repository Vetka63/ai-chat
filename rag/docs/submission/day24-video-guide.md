# День 24: пошаговый сценарий видео «Ответы с источниками и цитатами»

Этот документ описывает действия для новой записи видео. Фактические результаты завершённых прогонов, пропуски тестов и оставшиеся ограничения смотрите в [итоговой проверке](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Приведённые ниже ожидания — критерии проверки, а не обещание, что модель каждый раз выдаст `ANSWERED`.

## 1. Что показать и сказать в начале

Откройте приложение и скажите:

> «Это RAG по русской книге Pro Git. Ответ разбит на утверждения. Для каждого утверждения приложение требует точные цитаты из найденных фрагментов, а затем отдельная модель проверяет, поддерживают ли цитаты весь смысл утверждения. Я покажу сам ответ, его источники, поиск и корректный отказ».

В день 24 отдельный чат создавать не нужно: раздел выполняет независимые запросы. Сохраняемый диалог и память задачи демонстрируются в [дне 25](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/submission/day25-video-guide.md).

## 2. Запустить нужную версию

Откройте PowerShell 7. Перейдите в репозиторий и проверьте рабочее дерево:

```powershell
Set-Location 'F:\ai-advent-challenge\ai-chat'
git status --short
git branch --show-current
```

Если есть незакоммиченные изменения, сначала сохраните свою работу установленным для проекта способом. Не применяйте `reset --hard` для подготовки видео. Для отдельной версии дня 24 при чистом рабочем дереве:

```powershell
git switch ai-challenge-day-24
git branch --show-current
git rev-parse HEAD
Set-Location '.\rag'
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml up -d --build
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml ps
Invoke-RestMethod 'http://localhost:8382/actuator/health'
```

Дождитесь `status: UP`. Если backend ещё запускается, повторите только проверку health. Команда `up --build` нужна, чтобы контейнер использовал код выбранной ветки: один `git switch` работающий контейнер не обновляет. Для CPU исключите `-f compose.gpu.yml` из команд Compose. В свежем клоне без локальной ветки используйте `git switch --track origin/ai-challenge-day-24`.

Ключ DeepSeek настраивается только на backend: Compose читает `DEEPSEEK_API_KEY` или `LLM_API_KEY` из корневого `.env`. Если файла нет, создайте в редакторе `F:\ai-advent-challenge\ai-chat\.env` со строкой `DEEPSEEK_API_KEY=<ваш ключ>`, подставьте настоящий ключ и выполните запуск выше. Существующий `.env` не перезаписывайте и в видео его не открывайте. Порты по умолчанию: UI `8383`, API `8382`, Ollama `11435`. Переопределения `RAG_UI_PORT`, `RAG_API_PORT`, `RAG_OLLAMA_PORT` в `.env` или окружении меняют адреса; фактические порты видны в выводе Compose `ps`. Volumes содержат сохранённые индексы: `down -v` для этой проверки не нужен.

Откройте [интерфейс](http://localhost:8383). Раздел дня 24 доступен и в версии дня 25; если записываете оба дня на общей актуальной версии, оставьте `ai-challenge-day-25` и проговорите это. Название ветки само по себе не доказывает наличие последнего исправления: версию и реальные результаты сверяйте с итоговой проверкой.

## 3. Выбрать готовый индекс

1. Откройте **«Разбиение и индексы»**.
2. В **«Сохранённый индекс»** найдите структурный индекс с размером `3000` и перекрытием `300`. Для демонстрации используйте этот готовый индекс.
3. Если его нет, выберите **«По структуре»**, укажите **«Максимум символов» = 3000**, **«Перекрытие символов» = 300**, нажмите **«Построить индекс»** и дождитесь завершения. **«Посмотреть чанки»** показывает только разбиение и не создаёт поисковые векторы.
4. Если модель embeddings ещё не установлена, вне основной записи выполните `docker compose exec ollama ollama pull qwen3-embedding:0.6b`, затем повторите построение. Это загрузка локальной модели, а не вызов DeepSeek.
5. Перейдите в **«Источники и цитаты»**.

Фраза для видео:

> «Поиск работает по сохранённому индексу конкретного снимка книги. Цитата откроется именно в этом снимке, даже если оригинал книги впоследствии изменится».

## 4. Объяснить каждое поле

| Поле интерфейса | Что поставить | Что объяснить |
| --- | --- | --- |
| **Контрольный вопрос дня 24** | Сначала `stash` | Список из десяти проверочных вопросов. Выбор переносит вопрос в поле ниже. **«Свой вопрос»** позволяет ввести другой текст. |
| **Ожидание для проверки** | Развернуть после выбора случая | Подсказка человеку для ручной оценки. Она не является ответом модели и не передаётся ей как эталон. |
| **Вопрос с источниками** | Текст выбранного вопроса | Исходный вопрос, на который нужно ответить. Максимум 2000 символов. |
| **Индекс источников** | `STRUCTURAL · … чанков · 3000/300` | Корпус, по которому выполняется поиск. Число чанков зависит от готового индекса. |
| **Кандидатов поиска** | `20` | Сколько ближайших фрагментов получить до фильтрации. Допустимо 1–20. |
| **Максимум отобранных** | `10` | Верхний предел фрагментов после отбора. Не больше числа кандидатов и не больше 10. |
| **Порог релевантности** | `0.60` | Минимальный cosine score для отбора. Это настройка поиска, а не 60% вероятности правильного ответа. |
| **Бюджет текста источников** | `32000` | Максимум символов книжного контекста. Целый чанк может не поместиться, даже если прошёл порог. |
| **Лимит structured ответа** | Оставить пустым | Приложение не передаёт пользовательский `max_tokens`. Лимиты провайдера сохраняются; у отдельной проверки смысла есть собственный технический лимит. |
| **Переформулировать запрос поиска · один дополнительный LLM-вызов** | Снять флажок | Rewrite изменяет поисковый запрос, но не исходный вопрос. Для основного видео он не нужен. |

Кнопка без rewrite называется **«Ответить с цитатами · до 18 API-вызовов»**. При включённом rewrite будет до 19. Каждый из 1–8 пунктов проверяется отдельно; все фактические вызовы видны в диагностике. Локальный поиск через embeddings и внешняя генерация — разные стадии; при пустом отборе внешняя генерация не нужна.

В обновлённой сборке grounded-генератор и отдельный checker по умолчанию используют `deepseek-v4-pro` с включённым thinking и effort `high`. Checker имеет технический cap `16384`; он не заполняет пустое поле лимита пользовательского ответа. Обоим профилям задан timeout 180 секунд. Назовите фактические модели из диагностики; переключение модели само по себе не доказывает улучшение качества. `/answer-settings` относится к прежнему сравнению дней 22–23, не к grounded-генератору.

Теперь генератор выбирает короткий `{evidence_id}` вида E1/E2 из текущего запроса, а сервер сам извлекает дословную цитату из snapshot. Нельзя выдавать это за доказательство смысла: правильность выбора фрагмента дополнительно проверяет checker. В публичном ответе по-прежнему показываются текст цитаты, source, section и chunk_id.

## 5. Первый ответ: показать доказательство по шагам

В списке выберите `stash`; текст вопроса:

> Как git stash сохранить untracked-файлы? Включает ли -u файлы, перечисленные в .gitignore?

Нажмите **«Ответить с цитатами · до 18 API-вызовов»**, дождитесь окончания **«Ищем и проверяем…»**.

Если результат `ANSWERED`:

1. Покажите заголовок **«Цитаты проверены»** и прочитайте один пункт ответа. Сверьте, различает ли он `-u`/`--include-untracked` и `-a`/`--all`: неотслеживаемые и игнорируемые файлы нельзя смешивать.
2. Под пунктом покажите точную цитату, путь источника, раздел и `chunk ID`. Цитата должна подтверждать всё утверждение, включая оговорки. Наличие знакомого слова само по себе недостаточно.
3. Нажмите **«Открыть цитату в источнике»**. Покажите сообщение **«Цитата совпала с snapshot»**, идентификатор снимка и координаты UTF-16.
4. Раскройте **«Документ целиком с подсветкой цитаты»**. Покажите выделенный текст и соседние предложения: они помогают проверить, не потеряны ли условия примера. Закройте окно крестиком или Escape.
5. Раскройте **«Все источники ответа»**. Это список источников принятых пунктов, а не весь результат поиска.
6. Раскройте **«Проверка смысловой поддержки · PASSED»**. У каждого пункта должен быть свой `SUPPORTED`. Объяснение проверяющей модели является диагностикой, а не ещё одним доказанным фактом.
7. Раскройте **«Поиск и реально переданный контекст»**. Покажите самостоятельный поисковый текст и числа **«найдено → отобрано → передано»**. Отдельно покажите **«Не поместилось по бюджету»**. Порог, лимит количества и лимит символов решают разные задачи.
8. Покажите **«LLM-стадий»**, input/output/total и оценку USD. Оценка стоимости не является фактическим списанием; неизвестный расход не равен нулю.
9. Нажмите **«Скачать ответ с цитатами MD»** и **«Скачать ответ с цитатами JSON»**. Markdown подходит для чтения ответа; JSON содержит расширенную диагностику.

Скажите:

> «Здесь две разные проверки: буквальное совпадение цитаты с переданным текстом и модельная оценка поддержки вывода. Вторая проверка может ошибиться, поэтому я также читаю цитату и контекст. Зелёный статус не означает доказанную истинность любого пересказа».

Если ответ отклонён, оставьте это в записи. Покажите статус и соответствующую диагностику, сохраните JSON. Для объяснения просмотра источника можно открыть другой принятый результат из текущей проверки, указав, какой именно вопрос дал его. Не выдавайте исходный JSON отклонённой генерации за готовый ответ.

## 6. Десять контрольных вопросов

Пройдите весь список **«Контрольный вопрос дня 24»**. Для каждого выберите случай, нажмите кнопку, прочитайте статус и сохраните MD/JSON до следующего запроса: новый результат заменяет текущий на экране. Сохраняйте файлы под различными именами, например `day24-stash.json` и `day24-reset.json`. Перезагрузка страницы не восстанавливает результат этой вкладки.

Полные исходные вопросы и ожидания находятся в [day22-cases.json](../../evaluation/day22-cases.json): этот набор используется и разделом дня 24.

| Случай | Что проверять в ответе и цитатах |
| --- | --- |
| `reset` | Различие воздействия `--soft`, `--mixed`, `--hard` на HEAD/ветку, индекс и рабочий каталог; риск потери локальных правок. Цитата про mixed не доказывает soft. |
| `rebase` | Отличие структуры истории merge/rebase и риск переписывания истории, на которой уже работают коллеги. Условия конкретного книжного примера нельзя превращать в общее правило. |
| `stash` | Отличие неотслеживаемых и игнорируемых файлов; правильное соответствие `-u` и `-a`. |
| `fetch-pull` | Получение удалённых данных отдельно от их интеграции. Формулировка про pull должна сохранять оговорки о способе интеграции. |
| `undo-file` | Отмена неиндексированных изменений одного файла и риск потери этих правок; не подмена отменой коммита. |
| `add-snapshot` | В коммит без повторного add попадёт подготовленная версия, а последующее изменение файла само в индекс не попадёт. |
| `branch-pointer` | Ветка как ссылка на коммит и роль HEAD; ветка не является отдельной копией всех файлов. |
| `git-objects` | Роли blob, tree и commit, подтверждённые соответствующими цитатами. |
| `bisect` | Выбор good/bad, проверка предлагаемых коммитов и завершение режима через bisect reset. |
| `submodule` | Вложенный отдельный репозиторий и фиксируемый основным репозиторием коммит, а не простое копирование каталога. |

Это перечень содержания для оценки. Реальный ответ может быть неполным или отклонённым; такие случаи отмечаются отдельно. Для сдачи число принятых ответов берите из фактического отчёта, а не из количества пунктов этого списка.

## Одна видимая правка черновика

Если появился блок **«Исправление черновика · 1 попытка»**, раскройте первоначальный черновик и причину его отклонения, затем покажите проверку последнего варианта.

> «Первая версия имела точные цитаты, но не прошла проверку смысла. Приложение один раз передало исходный вопрос, те же источники и замечания генератору, затем проверило новую версию. На экране публикуется только последний вариант с успешной проверкой; первый остаётся в диагностике».

Произносите это только при фактическом наличии такой попытки. Неверный JSON, ошибки транспорта, truncation и неточная цитата не запускают правку. В JSON `repair.originalGeneration` и `repair.originalSupportCheck` относятся к первому черновику; основные `generation`/`supportCheck` — к последнему. Расход включает каждую стадию один раз. Это не скрытый HTTP retry и не серия повторов до успеха.

## 7. Показать отсутствие ответа и блокировку слабого контекста

1. Выберите **«Свой вопрос»**, введите **«Какая погода завтра в Самаре?»**, оставьте порог `0.60` и отправьте.
2. Ожидаемое поведение: **«Не знаю по найденным материалам»**, уточнение и отсутствие придуманных цитат. Если после отбора нет контекста, статистика показывает, что LLM не вызывалась. Это проверяется по фактическому результату, а не предполагается для любого постороннего вопроса.
3. Затем введите **«Как работает git stash?»**, поставьте **«Порог релевантности» = 1** и отправьте. Для этого контрольного случая ожидается пустой отбор и `UNKNOWN` без генерации.
4. Покажите поиск и число LLM-стадий. Верните порог `0.60`, чтобы следующий вопрос не выполнялся с тестовой настройкой.

Фраза для видео:

> «Если достаточных материалов нет, приложение просит уточнение. Оно не добавляет вымышленные ссылки и не переключается автоматически на ответ без книги».

## 8. Как объяснять остальные статусы

| Статус | Как выглядит и что означает |
| --- | --- |
| `ANSWERED` | **«Цитаты проверены»**: публичные пункты прошли точность цитат и отдельную смысловую проверку. Смысл всё равно проверяется человеком. |
| `UNKNOWN` | **«Не знаю по найденным материалам»**: недостаточно контекста либо модель не нашла в нём ответ. |
| `INVALID_EVIDENCE` | **«Ответ не прошёл проверку»**: ответ, цитата, структура JSON или проверка смысла не прошли требования. Непроверенные утверждения не публикуются. |
| `ERROR` | **«Ошибка стадии»**: технический сбой. Это не успешная демонстрация отказа по недостатку знаний. |

Блок **«Диагностика LLM · исходный JSON не является проверенным ответом»** нужен для разбора ошибки. Он не отменяет статус и не делает скрытые утверждения допустимыми к публикации.

Дополнительный тест обрезания ответа: указать лимит `1` и задать вопрос о reset. Ожидается блокировка неполного ответа, после чего лимит нужно очистить. Этот тест создаёт новый платный запрос; для основного видео он необязателен.

## 9. Автоматическая проверка и завершение видео

Для отдельного нового прогона в PowerShell 7 из папки `rag`:

```powershell
.\scripts\verify-day24.ps1
```

Скрипт создаёт новый `data/day24-live-results-<время>-<id>.json`, проверяет десять вопросов и четыре отрицательных случая; путь печатается в терминале. Без rewrite — до 180 платных LLM-вызовов, включая не более одной правки на вопрос и отдельные проверки каждого пункта. Скрипт задаёт тестовый лимит генерации `6000`, тогда как пустое поле UI этого лимита не задаёт. Для десяти положительных вопросов скрипт строго требует `ANSWERED`: любой иной статус даёт ошибку итоговой приёмки, а trace сохраняется. Поэтому корректный отказ по rebase, например, не означает поломку механизма защиты, но означает, что требование получить все десять полезных ответов в этом прогоне не выполнено. Не путайте его с `ERROR` инфраструктуры. Повторный запуск — новый опыт и новые вызовы.

Не называйте пропущенный live-тест успешным. В конце покажите [итоговую проверку](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md), назовите фактический объём прогона и ограничения. Короткое завершение:

> «Я показал связь пункта ответа с точной цитатой и сохранённым документом, отдельную проверку поддержки смысла, поиск и отказы. Отклонённые результаты сохранены для диагностики. Фактические итоги приведены в отчёте».
