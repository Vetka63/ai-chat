# День 21 — сценарий видео: корпус, два разбиения и локальный индекс

Цель ролика — проследить путь от документов до сохранённых векторов и сравнить FIXED с STRUCTURAL на одном корпусе. Приложение здесь ищет фрагменты, но не генерирует ответ DeepSeek. Ориентир: 8–12 минут рассказа плюс ожидание построения.

Фактические результаты последней проверки, её условия и ограничения: [общий финальный отчёт](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Сценарий задаёт действия и критерии; сам по себе он не подтверждает успешный прогон. [Старый отчёт дня 21](../test-results.md) относится к своим сохранённым измерениям.

## 1. Подготовить запуск

Откройте Docker Desktop и дождитесь работающего Engine. В PowerShell:

```powershell
Set-Location 'F:\ai-advent-challenge\ai-chat'
git status --short
git branch --show-current
```

При чистом рабочем дереве переключитесь на ветку дня. Если есть изменения, сначала сохраните текущую работу; не сбрасывайте её ради демонстрации.

```powershell
git switch ai-challenge-day-21
git branch --show-current
git rev-parse HEAD
Set-Location ./rag
./scripts/prepare-corpus.ps1
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml up -d --build backend client
docker compose exec ollama ollama list
Invoke-RestMethod http://localhost:8382/actuator/health
```

В свежем клоне без локальной ветки вместо обычного переключения выполните `git switch --track origin/ai-challenge-day-21`. После переключения кода нужна пересборка backend/client: работающий контейнер сам не меняет версию. Без NVIDIA GPU уберите `-f compose.gpu.yml`. Если корневого `.env` нет, для дня 21 можно убрать и `--env-file ../.env`: ключ генерации не нужен.

Если в списке Ollama нет `qwen3-embedding:0.6b`, один раз выполните:

```powershell
docker compose exec ollama ollama pull qwen3-embedding:0.6b
```

Загрузка модели — подготовка, а не построение индекса. Откройте [интерфейс](http://localhost:8383); health должен вернуть `UP`. Если сразу после `up -d` соединение ещё не установлено, подождите запуска backend и повторите только health. Порты по умолчанию: UI `8383`, API `8382`, Ollama `11435`. Если в `.env` или окружении заданы `RAG_UI_PORT`, `RAG_API_PORT`, `RAG_OLLAMA_PORT`, используйте эти значения в адресах; фактические порты показывает `docker compose ps`. Не используйте `down -v`: volumes содержат SQLite и модель. Подробности — [Windows setup](../windows-setup.md).

Если снимаете все дни из объединённой ветки `ai-challenge-day-25`, оставьте её и прямо назовите это интегрированным запуском. Покажите фактическую ветку/commit; не выдавайте его за запуск отдельной ветки 21.

## 2. Начать запись: показать источник и объём

Покажите ветку и commit в терминале, затем **«Корпус документов»**.

Реплика:

> «День 21 — подготовка базы знаний. Backend написан на Kotlin и Spring, интерфейс — Vue. Я взял закреплённый набор русского Pro Git: главы 2, 3, 7 и 10. Эмбеддинги считаются локально в Ollama, индекс и тексты сохраняются в SQLite».

Покажите документы, слова и условные страницы. У включённого snapshot: 36 документов, 56 957 слов, примерно 142,39 условной страницы. Раскройте **«Что означает объём и откуда взяты данные»**: формула `words / 400`, авторство, snapshot; рядом видны revision и лицензия.

> «142 страницы — эквивалент объёма по 400 словам, не страницы PDF. Overlap не увеличивает объём исходного корпуса. Версия книги закреплена, поэтому сравнение повторяется на тех же текстах».

Откройте документ про reset или stash, покажите заголовки, обычный текст и команды. Закройте крестиком или Escape. Происхождение данных — [corpus-progit.md](../corpus-progit.md).

## 3. FIXED: отделить preview от построения

В **«Разбиение и индексы»** выберите **«Фиксированный размер»**, **«Максимум символов»** = 3000, **«Перекрытие символов»** = 300. Нажмите **«Посмотреть чанки»**.

Покажите плашку Preview и раскройте **«Метаданные фрагмента»** у одного чанка: текст, title/раздел, `source`, `chunk_id`, диапазон `[start, endExclusive)`, начальные строки блоков. Используйте фильтр документов или **«Дальше →»**.

> «Preview только разрезает текст, векторы ещё не созданы. Размер и overlap — символы, не токены. FIXED берёт окна заданного размера и может соединить конец одного раздела с началом другого. Метаданные позволяют вернуться к источнику».

Диапазон относится к нормализованному сохранённому документу. Начальные строки блоков не называйте точным диапазоном оригинального AsciiDoc: нормализация и раскрытие include меняют представление.

Нажмите **«Построить индекс»**, покажите прогресс **«Строим фиксированный размер»**. Дождитесь завершения; в **«История заданий»** должен появиться `READY`. Выберите новый результат в **«Сохранённый индекс»** → **«Открыть чанки»**.

> «Теперь для чанков вычислены настоящие векторы qwen3-embedding. READY появляется после завершения всех batches и сохранения результата. Это уже готовый индекс, а не preview».

Если построение записано отдельно, в коротком ролике можно открыть готовый FIXED 3000/300. Скажите, что показываете сохранённый результат; не представляйте просмотр как новое вычисление.

## 4. STRUCTURAL: те же параметры, другой принцип

Выберите **«По структуре»**, оставьте 3000/300 → **«Посмотреть чанки»**. Через фильтр откройте тот же документ и покажите начало и конец нескольких фрагментов.

> «STRUCTURAL учитывает разделы и абзацы. Предел размера и overlap те же, чтобы сравнить именно стратегию. Очень длинный раздел или блок команд всё равно делится; это не один чанк на любую главу».

Нажмите **«Построить индекс»**, дождитесь `READY`, откройте сохранённые чанки. Нужны два завершённых индекса одного snapshot и одной embedding-модели. Использование старого готового результата обозначьте явно.

## 5. Сравнить метрики

В **«Сравнение стратегий»** отметьте ровно FIXED 3000/300 и STRUCTURAL 3000/300 → **«Сравнить индексы»**. Покажите плашку **«Одинаковый корпус и embedding space — сравнение допустимо»**. При предупреждении о несовместимости выберите подходящую пару.

| Строка таблицы | Что объяснить |
| --- | --- |
| «Покрытие текста» | Ожидается 100% у обоих: нормализованный текст не потерян |
| «Чанков», «Минимум / медиана / p95» | Стратегии дают разную гранулярность |
| «Чанки через границы разделов» | Насколько сохраняются смысловые границы |
| «Разрезанные блоки команд» | Насколько сохраняются примеры кода |
| «Объём векторов» | Место для координат, не полный размер SQLite |
| «Построение» | Время конкретного сохранённого запуска |

Прочитайте фактические числа, не заучивайте количество чанков. Старые индексы могут оставаться после обновления chunker: для нового алгоритма покажите свежий результат либо явно обозначьте сохранённую пару; сверяйтесь с финальным отчётом.

> «Структурное разбиение может лучше сохранять границы, но создавать больше векторов. По времени одного запуска нельзя объявить победителя: влияют прогрев модели и порядок построения. Проверю ещё поиск нужного источника».

## 6. Проверить поиск на двух вопросах

Нажмите **«Проверить поиск →»**: оба индекса будут отмечены в **«Диагностическом поиске»**. Вставьте:

> Чем отличаются reset --soft, --mixed и --hard, какие три дерева Git они меняют?

Нажмите **«Найти в книге»**. В двух колонках покажите top-5, cosine, разделы и `source`. Ожидаемый документ — `reset.asc`. Нажмите **«Открыть сохранённый источник»**, прочитайте фрагмент, который действительно объясняет часть вопроса.

Затем повторите с вопросом:

> Чем merge отличается от rebase и почему опасно перебазировать опубликованные коммиты?

Ожидаемый документ — `rebasing.asc`. Если он не найден, отметьте промах retrieval, не меняйте вопрос незаметно.

> «Это найденный текст, не готовый ответ LLM. Cosine показывает сходство векторов, а не вероятность правильности. Поэтому я читаю источник, а не только score».

Полный набор — [пять поисковых случаев](../../evaluation/day21-search-cases.json). Дополнительный локальный прогон из `rag`, в PowerShell 7:

```powershell
pwsh -File ./scripts/verify-live.ps1
```

Платной генерации нет. Скрипт сохраняет timestamped JSON в `rag/data`, проверяет метаданные и попадание ожидаемого документа в top-5 отдельно для каждой стратегии. Порог по умолчанию — 0,8, то есть 4 из 5. Это проверка retrieval, не правильности будущего LLM-ответа.

Вернитесь в **«Сравнение стратегий»** → **«Скачать Markdown»** и **«Скачать JSON»**. Markdown содержит сравнение и последние результаты поиска; JSON этой кнопки — только сравнение индексов. Для всех пяти вопросов нужен отчёт скрипта.

## 7. Доказать сохранение после restart

Дождитесь окончания индексации. Из `rag`:

```powershell
$ragBeforeRestart = @(Invoke-RestMethod http://localhost:8382/api/v1/indexes)
$ragBeforeRestart | Select-Object id, snapshotId
docker compose --env-file ../.env -f compose.yml restart backend
```

Дождитесь восстановления backend, затем:

```powershell
Invoke-RestMethod http://localhost:8382/actuator/health
$ragAfterRestart = @(Invoke-RestMethod http://localhost:8382/api/v1/indexes)
$ragAfterRestart | Select-Object id, snapshotId
Compare-Object $ragBeforeRestart.id $ragAfterRestart.id
```

Если `.env` не используется, уберите соответствующий флаг. Пустой вывод `Compare-Object` при показанных непустых списках означает одинаковый набор ID. Обновите браузер, откройте сохранённые чанки и повторите первый поиск без построения индекса.

> «Backend перезапущен, ID индексов прежние, поиск работает по сохранённым векторам. Документы не пришлось эмбеддить заново. Это подтверждает постоянное хранение».

## 8. Завершить и приложить материалы

Приложите ветку/commit, MD/JSON сравнения, отчёт пяти поисковых случаев и [финальный отчёт](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Генерация ответов начинается в дне 22; технический успех индексации не доказывает безошибочность будущей модели.
