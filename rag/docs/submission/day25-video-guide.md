# День 25: пошаговый сценарий видео «Чат с RAG и памятью»

Здесь описан воспроизводимый сценарий новой записи. Фактические завершённые проверки, пропущенные тесты и ограничения указаны в [итоговой проверке](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Не считайте ожидания ниже результатом прогона: генерация, извлечение памяти и проверка смысла выполняются моделями и могут ошибаться.

Исходные реплики взяты из [day25-scenarios.json](../../evaluation/day25-scenarios.json). Нужно показать **два отдельных чата по 12 пользовательских сообщений**. Один обмен — одно сообщение пользователя и результат его обработки. Сохраняйте порядок реплик и не объединяйте несколько шагов в одно сообщение.

## 1. Что демонстрируем

Фраза в начале видео:

> «Это чат по Pro Git с отдельной памятью задачи. На каждом вопросе выполняется новый поиск по книге. История помогает понять короткую реплику, память сохраняет цель, ограничения, ситуацию и названия. Ни история, ни память не заменяют книжные доказательства. После шестого обмена я перезапущу backend и продолжу оба диалога».

Приложение объясняет команды Git, но не выполняет их в вашем репозитории. Реплики сценария — учебная ситуация.

## 2. Запуск и готовый индекс

Откройте PowerShell 7, запущенный Docker Desktop и рабочую копию проекта:

```powershell
Set-Location 'F:\ai-advent-challenge\ai-chat'
git status --short
git branch --show-current
```

Для переключения сначала сохраните незакоммиченную работу привычным для проекта способом. При чистом дереве:

```powershell
git switch ai-challenge-day-25
Set-Location '.\rag'
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml up -d --build
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml ps
Invoke-RestMethod 'http://localhost:8382/actuator/health'
```

Дождитесь `status: UP`; при необходимости повторите проверку health. Для CPU исключите `-f compose.gpu.yml`. Работающий контейнер не обновляется от одного переключения Git-ветки, поэтому нужна сборка. В свежем клоне без локальной ветки используйте `git switch --track origin/ai-challenge-day-25`.

Ключ настраивается на backend через `DEEPSEEK_API_KEY` или `LLM_API_KEY` в корневом `.env`. Если этого файла нет, создайте в редакторе `F:\ai-advent-challenge\ai-chat\.env`, добавьте `DEEPSEEK_API_KEY=<ваш ключ>` с настоящим значением и выполните запуск Compose выше. Существующий файл не перезаписывайте; ключ не показывайте на экране и не прикладывайте к сдаче. Порты по умолчанию: UI `8383`, API `8382`, Ollama `11435`. Если в `.env` или окружении заданы `RAG_UI_PORT`, `RAG_API_PORT`, `RAG_OLLAMA_PORT`, используйте их значения в адресах; опубликованные порты видны в Compose `ps`.

Откройте [приложение](http://localhost:8383). Во вкладке **«Разбиение и индексы»** проверьте готовый структурный индекс `3000/300`. Если его нет: **«По структуре»** → **«Максимум символов» = 3000** → **«Перекрытие символов» = 300** → **«Построить индекс»**. Дождитесь завершения. Кнопка **«Посмотреть чанки»** не строит векторы. Если embeddings-модель отсутствует, заранее загрузите её командой `docker compose exec ollama ollama pull qwen3-embedding:0.6b`.

Перейдите в **«Чат с RAG и памятью»**. Уже имеющиеся чаты не удаляйте: для записи создаются два новых.

## 3. Создать первый чат и объяснить все поля

Нажмите **«＋ Новый чат»**. Появится окно **«Новый чат с RAG»**.

| Поле или блок | Значение для записи | Что это значит |
| --- | --- | --- |
| **Название чата** | `Видео — отменить коммит и сохранить изменения` | Название в списке слева. Оно не задаёт цель в памяти: цель нужно сообщить текстом. |
| **Индекс для чата** | Готовый `STRUCTURAL` | Закрепляет источник и снимок книги для этого чата. В этом списке показываются стратегия и число чанков; параметры `3000/300` проверьте заранее во вкладке индексов. |
| **Настройки поиска и памяти** | Развернуть | Все следующие поля задаются при создании чата. Для других настроек создаётся новый чат. |
| **Кандидатов** | `10` | Сколько ближайших чанков получить перед фильтрацией, 1–20. |
| **После фильтра** | `5` | Максимум отобранных чанков, 1–10 и не больше числа кандидатов. |
| **Порог** | `0.65` | Минимальная близость для отбора. Это не вероятность истинности ответа. |
| **Бюджет источников** | `16000` | Лимит символов книжного контекста; целые чанки могут не поместиться. |
| **Обменов в хвосте** | `6` | Максимум недавних обменов, передаваемых модели. Полная история чата при этом сохраняется. |
| **Символов в хвосте** | `10000` | Второй предел истории. Поэтому в prompt может войти меньше шести обменов. |
| **Лимит ответа** | Оставить пустым | Приложение не задаёт пользовательский `max_tokens`. Это не отменяет ограничения провайдера и технический лимит проверки смысла. |

Нажмите **«Создать чат»**. В центре появится пустая переписка, справа — **«Память этого чата»**. Кнопка **«Память задачи»** в заголовке показывает или скрывает правую панель.

Справа четыре слоя:

| Слой | Что ожидаем в нём |
| --- | --- |
| **Цель** | Общая задача диалога, не отдельный очередной вопрос. |
| **Уточнения** | Ситуация и её изменения: например, коммит сначала локальный, позднее опубликованный. |
| **Ограничения** | Требования и запреты: сохранить изменения, не переписывать общую историю. |
| **Термины** | Назначенные пользователем имена: например, рабочая ветка `feature-login`. |

Новая пустая память — ожидаемый результат. Начальная надпись **«Пока не зафиксировано»** не является ошибкой.

## 4. Как отправлять и разбирать каждый ответ

1. Вставьте одну реплику в **«Сообщение по задаче»**.
2. Нажмите **«Отправить»** или Ctrl+Enter. Во время **«Обрабатываем…»** дождитесь результата; не создавайте вторую отправку того же текста.
3. Прочитайте статус. Для принятого ответа он называется **«Цитаты проверены · смысл сверяйте с источником»**. Наличие точной цитаты и модельной проверки не отменяет ручного чтения.
4. Под одним пунктом раскройте **«Источники и цитаты»**. Покажите цитату, документ, раздел и chunk ID.
5. Нажмите **«Открыть цитату в книге»**. Покажите подтверждение совпадения с snapshot чата и **«Документ с подсветкой»**. Закройте окно крестиком или Escape.
6. Раскройте **«Проверка смысловой поддержки · PASSED»**. Для опубликованных пунктов ожидаются `SUPPORTED`; причины проверки — диагностика, а не дополнительные факты.
7. Раскройте **«Как получен ответ»**. Покажите **«Самостоятельный вопрос поиска»**, число обменов в prompt и вне него, количество изменений памяти, расход подготовки и ответа, найденные и переданные чанки.
8. Справа проверьте появившиеся факты. У одного из них раскройте **«Откуда запомнили»** и нажмите **«К сообщению пользователя»**. Цитата должна находиться в исходной реплике пользователя, а не в ответе модели.

Скажите:

> «Для памяти я проверяю происхождение из пользователя, для технического ответа — происхождение из книги. Это разные источники и разные проверки. Самостоятельная формулировка помогает раскрыть слова “они” и “какой режим”, но не становится новым фактом памяти».

Для каждого сообщения не обязательно долго открывать все блоки в записи. Подробно покажите их на первом принятом ответе, коротких продолжениях и изменении ситуации; остальные ответы просмотрите и оставьте в полной истории.

## 5. Сценарий A: отменить коммит и сохранить изменения

Отправляйте реплики из колонки «Текст» дословно, по одной. Колонка «Проверка» предназначена вам; её в чат вставлять не нужно.

| № | Текст | Проверка после обработки |
| --- | --- | --- |
| 1 | Моя цель — отменить ошибочный локальный коммит и сохранить изменения. Коммит пока не опубликован. Чем отличаются reset --soft, --mixed и --hard? | В памяти появляются общая цель и локальный/неопубликованный статус коммита. Если ответ принят, цитаты различают режимы и риск hard. |
| 2 | Нельзя терять изменения в рабочем каталоге. Что станет с ними при --soft? | В **«Ограничения»** добавляется запрет потери изменений. Поисковый вопрос раскрывает ссылку на reset и рабочие изменения. |
| 3 | Я хочу оставить файлы в индексе. Какой режим подходит и почему? | Продолжается обсуждение режимов reset; локальное пожелание не заменяет общую цель. Проверяйте достаточность цитаты для объяснения выбранного режима. |
| 4 | Теперь нужно убрать их из индекса, но оставить в рабочем каталоге. Какой режим использовать? | В **«Самостоятельный вопрос поиска»** должно остаться имя `reset`. Нельзя подменять вопрос о его режиме любой похожей операцией или ответом про прекращение отслеживания через `rm --cached`. |
| 5 | А если выбрать --hard? | Поиск остаётся в теме reset. Ответ, если принят, должен объяснить риск для рабочего каталога и учитывать ограничение на сохранение изменений. |
| 6 | Перед переделкой я хочу временно убрать незакоммиченные правки. Как работает git stash? | Текущая тема меняется на stash, общая цель остаётся. После этого шага остановите сценарий до перезапуска, описанного ниже. |
| 7 | А как потом вернуть их и сразу убрать запись из списка? | Самостоятельный вопрос содержит `stash`, а не reset. В принятом ответе проверяйте возврат сохранения и удаление записи; условия конфликтов нельзя замалчивать, если они нужны для вывода. |
| 8 | У меня есть новый untracked-файл. Как включить его в это сохранение? | Ссылка **«это сохранение»** относится к stash. Неотслеживаемый файл не должен без основания превращаться в игнорируемый. |
| 9 | Теперь выяснилось, что ошибочный коммит уже опубликован. Историю общей ветки переписывать нельзя. Что использовать вместо reset? | В **«Уточнения»** актуализируется статус коммита; не должно остаться двух действующих противоречивых статусов. В **«Ограничения»** появляется запрет переписывания общей истории. |
| 10 | Как посмотреть старые положения HEAD, если ошибся с reset? | Самостоятельный текущий вопрос о reflog не вытесняется общей целью. Нужны собственные свежие книжные источники. |
| 11 | Объясни безопасный вариант отмены опубликованного коммита без переписывания общей истории. | Ответ соответствует опубликованной ситуации и ограничению. По книге проверяйте отмену новым коммитом, а не обещание переписать историю без последствий. |
| 12 | С учётом запрета переписывать общую историю, чем выбранная отмена отличается от reset? | Сохраняются цель и ограничения. Поисковый вопрос раскрывает сравнение. Начальный обмен уже вне ограниченного хвоста, но цель остаётся в памяти. |

На шаге 4 особенно полезно раскрыть **«Как получен ответ»**. Даже если предыдущий технический ответ был отклонён, успешно подготовленный предыдущий вопрос помогает сохранить тему; непроверенные утверждения при этом не должны попадать в историю как ответы.

## 6. Создать сценарий B и показать изоляцию

После шестого сообщения сценария A нажмите **«＋ Новый чат»**, назовите его **«Видео — отдельная ветка для команды»**, выберите тот же индекс и те же настройки. Нажмите **«Создать чат»**.

Перед первой отправкой покажите пустую историю и пустые слои памяти. Цель отмены коммита и ограничения из A не должны появиться в B. Выберите A в списке слева: его шесть обменов и память на месте. Вернитесь в B и начните второй сценарий.

| № | Текст | Проверка после обработки |
| --- | --- | --- |
| 1 | Моя цель — работать в отдельной ветке над исправлением, затем объединить изменения с командой. В общую ветку force push запрещён. Как создать ветку и переключиться на неё? | В памяти появляются собственная цель B и запрет force push. Факты сценария A не примешиваются. |
| 2 | Назовём эту рабочую ветку feature-login. Чем отличаются branch и checkout -b? | В **«Термины»** сразу появляется `feature-login`, без слова «запомни». Через **«Откуда запомнили»** покажите именно второе сообщение. |
| 3 | Что делает HEAD в этой ситуации? | История помогает раскрыть **«в этой ситуации»**; ответ об актуальной ветке подтверждается книгой. |
| 4 | Как посмотреть, в какой ветке я сейчас? | Ответ относится к просмотру текущей ветки. Не должен придумывать реальное состояние вашего компьютера: Git здесь не запускался. |
| 5 | Мне нужно сначала увидеть удалённые изменения, не объединяя их с локальными. Чем fetch отличается от pull? | Сохранено требование сначала получить данные без интеграции. Ответ различает fetch и pull. |
| 6 | А какой из них сразу объединяет изменения? | Самостоятельный вопрос должен включать и `fetch`, и `pull`, раскрывая сравнение. После этого шага перезапустите backend для обоих чатов. |
| 7 | Теперь нужно объединить feature-login с основной веткой. Что делает git merge? | После restart имя ветки и цель остаются. Ответ объясняет merge; не утверждает, что слияние уже выполнено. |
| 8 | А когда получится fast-forward? | Продолжается тема merge; цитата должна подтверждать условие fast-forward, а не просто упоминать его. |
| 9 | Две ветки меняли одну строку. Как выглядит конфликт слияния? | Показано состояние конфликта на основе книжного материала, без выдуманных результатов реального merge. |
| 10 | Как после исправления отметить конфликт решённым? | Короткое продолжение относится к предыдущему конфликту; подготовка, источники и ответ соответствуют этому действию. |
| 11 | Мы договорились не переписывать общую историю. Почему rebase общей ветки рискован? | Добавляется общее ограничение на переписывание истории. Оно не должно исчезнуть как «повтор» более узкого запрета force push; нужны оба независимых правила. |
| 12 | Как удалить локальную feature-login после успешного слияния? | Ответ о безопасном удалении слитой локальной ветки подтверждается цитатой именно об удалении. Текст о создании ветки не является достаточным доказательством. Цель, имя и оба запрета остаются в памяти. |

## 7. Перезапуск после шестого обмена в обоих чатах

Сначала выполните A1–A6 и B1–B6. Убедитесь, что последняя генерация завершилась в обоих чатах. Не перезапускайте backend посреди ответа для этой проверки.

1. В каждом чате раскройте **«Настройки чата»** и покажите индекс, хвост `6` обменов/`10000` символов и текущую память.
2. Скачайте **«Скачать чат MD»** и **«Скачать диагностику JSON»** для обоих чатов, сохраните под различными именами, например `A-before-restart.json` и `B-before-restart.json`.
3. Переключитесь в PowerShell, оставаясь в `rag`, и выполните:

```powershell
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml restart backend
Invoke-RestMethod 'http://localhost:8382/actuator/health'
```

4. Если health ещё недоступен, дождитесь запуска и повторите проверку до `UP`.
5. Перезагрузите страницу, снова откройте **«Чат с RAG и памятью»**. Выберите A и B по именам. В каждом должны сохраниться шесть пользовательских сообщений и соответствующая память. Обновление страницы само по себе не является доказательством перезапуска backend; покажите обе операции.
6. Продолжите A7–A12 и B7–B12 в тех же чатах. Первой репликой после перезапуска используйте именно предусмотренный короткий вопрос, не повторяйте всю цель и ограничения.

Фраза для видео:

> «История и память находятся в SQLite на сервере. Браузер хранит выбранный чат, черновики и сведения для восстановления отправки. После перезапуска сервера я продолжил сохранённую задачу без повторного ввода её цели».

Не используйте `docker compose down -v`: удаление volumes уничтожит данные и не относится к проверке сохранности. Если во время restart всё же был незавершённый вопрос, он может получить статус прерванного; это отдельный сценарий, а не успешное завершение обычного ответа.

## 8. Как доказать память за пределами хвоста

После двенадцатого вопроса в каждом чате:

1. Покажите, что в полной переписке сохранены все 12 сообщений пользователя.
2. У последнего ответа раскройте **«Как получен ответ»**: передано не больше шести предыдущих обменов; **«вне prompt»** — не меньше пяти. Из-за лимита символов хвост может быть ещё короче.
3. Справа покажите общую цель. Раскройте **«Откуда запомнили»** и **«К сообщению пользователя»**: источник цели — раннее сообщение, которое уже не входит в хвост последнего запроса.
4. В A проверьте сохранение требования не терять правки, актуального опубликованного статуса и запрета переписывания общей истории.
5. В B проверьте `feature-login` с происхождением из сообщения 2, отдельный запрет force push из сообщения 1 и новый общий запрет из сообщения 11.
6. Скачайте итоговую диагностику каждого чата под различными именами, например `A-complete.json` и `B-complete.json`. При необходимости покажите поля `memory.facts[].sourceTurnId`, `turns[last].includedHistoryTurnIds` и `omittedHistoryTurnCount`: ID исходной цели отсутствует в хвосте, но факт остаётся в памяти.

Скажите:

> «Полная история не удалена, но она не целиком отправляется модели. Начало диалога уже вне окна, а проверенные по цитатам пользователя факты задачи хранятся отдельно. Важно проверить и происхождение, и полноту: модель может пропустить факт даже при корректных цитатах других фактов».

## 9. Статусы, ошибки и расход: что говорить честно

| Ситуация | Как действовать в записи |
| --- | --- |
| `ANSWERED` | Покажите проверенные цитаты и `PASSED`. Прочитайте смысл и условия утверждений. Старый сохранённый ответ без `supportCheck` не является доказательством новой проверки. |
| `UNKNOWN` | Покажите **«Не знаю по найденным материалам»** и уточнение. Источников технического ответа может не быть. Подготовленная память при этом может сохраниться. |
| `INVALID_EVIDENCE` | Покажите **«Ответ не прошёл проверку источников»**. Неподтверждённые пункты не публикуются. Сохраните trace; не выдавайте отклонение за полезный ответ. |
| `ERROR` или ошибка подготовки | Зафиксируйте технический сбой и сохранённое сообщение. Не называйте это отказом по недостатку знаний или успешным тестом. |
| **«Доставка сообщения не подтверждена»** | Сначала **«Проверить статус»**: это чтение истории. **«Проверить и повторить»** тоже сначала сверяет историю, а при необходимости использует прежний requestId. Не набирайте вторую копию вопроса до выяснения статуса. |

Обмен использует до пяти внешних LLM-вызовов: подготовку вопроса/памяти, генерацию, проверку смысла и при содержательном отклонении одну правку с повторной проверкой. Локальные embeddings — другая стадия. При раннем отказе вызовов меньше. В **«Как получен ответ»** расход ответа уже включает проверку смысла: её нельзя прибавлять ещё раз к общей сумме. Оценка USD не является фактическим списанием.

В текущей сборке подготовка и генерация по умолчанию используют Flash с отключённым thinking. Смысл проверяет отдельный профиль `deepseek-v4-pro` с включённым thinking, effort `high` и техническим output cap `16384` (включая reasoning). Пустой **«Лимит ответа»** остаётся пустым для пользовательского ответа: это другой вызов. В итогах называйте фактическую модель из trace и не считайте выбранный профиль доказательством правильности его вердиктов. Для checker задан отдельный HTTP timeout 180 секунд (`DEEPSEEK_SUPPORT_TIMEOUT_SECONDS`); обычный timeout генерации остаётся 120 секунд.

Факты памяти могут успешно сохраниться даже при отклонении технического ответа. Если сама подготовка памяти не прошла проверку, изменение памяти не применяется и генерация не запускается. Исходный текст в **«Непроверенная диагностика модели»** не считается опубликованным ответом.

Каждый новый повтор того же текста после завершения предыдущего обмена — новый запрос. Не добивайтесь «красивого» результата скрытой серией повторов. Если проводится новый прогон после исправления, сохраняйте предыдущий trace и указывайте новый прогон отдельно.

Если есть **«Исправление черновика · 1 попытка»**, покажите первоначальное отклонение и результат последней проверки. Такая попытка запускается только после точных цитат и первого `supportCheck.status=REJECTED`; неверная форма JSON, транспортный сбой, truncation или ошибка цитаты не повторяются. Flash получает тот же исходный запрос и источники с feedback, затем проходят обе проверки. Второй правки нет. `repair.originalGeneration`/`repair.originalSupportCheck` сохраняют первый черновик; основные поля — последний вариант. Публичен только последний прошедший вариант; общий usage уже включает каждую из стадий один раз.

Четыре обмена отдельной проверки `scripts/verify-memory-lifecycle.ps1` — до 20 вызовов. Это текущий максимум, не число фактически выполненных запросов.

## 10. Автоматический вариант тех же двух сценариев

Это альтернатива ручной отправке, которая создаст свои два новых чата. Не запускайте её в дополнение к UI-прогону незаметно для учёта результатов. Из PowerShell 7 в папке `rag`:

```powershell
.\scripts\verify-day25.ps1 -Phase Start
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml restart backend
Invoke-RestMethod 'http://localhost:8382/actuator/health'
```

После `UP` продолжите тот же отчёт. Подставьте точный путь, напечатанный фазой Start:

```powershell
.\scripts\verify-day25.ps1 -Phase Continue -ReportPath '.\data\day25-live-results-<timestamp>.json'
```

`Start` выполняет первые шесть сообщений обоих сценариев; `Continue` — оставшиеся шесть. Путь с `<timestamp>` является примером и не запускается без подстановки. `-Phase All` выполняет 24 сообщения, но сам по себе не доказывает перезапуск между половинами.

На два сценария приходится до 120 платных LLM-вызовов. Скрипт использует тестовый лимит ответа `2400`, а UI по умолчанию оставляет лимит пустым. Проверяются свежий поиск, цитаты и координаты, происхождение памяти, обязательные факты, сохранение цели вне хвоста и несколько опорных тем. Для каждого `ANSWERED` требуется `PASSED`, а доля `ANSWERED` должна быть не ниже `0.65` в каждом сценарии. Этот порог — критерий приёмки, не вероятность истинности ответа.

Скрипт сохраняет trace до сообщения об ошибке. Если он остановился на раннем шаге, нельзя утверждать, что выполнены два полных диалога; проверяйте реальные позиции и число результатов. Ручная проверка смысла остаётся необходимой даже после успешных автоматических проверок.

## 11. Что оставить после записи

Сохраните два итоговых Markdown-экспорта и две диагностики JSON. Markdown показывает принятые ответы, цитаты и память; JSON дополнительно содержит промпты и непроверенные ответы. Для демонстрации использованы учебные данные — не добавляйте в публичную диагностику личные сведения из других чатов.

На финальном экране покажите [итоговую проверку](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md) и сформулируйте только подтверждённое:

> «Показаны два независимых диалога, короткие продолжения темы, происхождение памяти и книжных цитат, а также продолжение после перезапуска. Полная история сохранена, ранняя цель остаётся за пределами хвоста. Реальные числа принятых ответов, отклонений и пропущенных тестов приведены в отчёте».

Последнюю фразу используйте только если соответствующие шаги действительно завершены. Если часть проверки не выполнена, назовите её прямо.
