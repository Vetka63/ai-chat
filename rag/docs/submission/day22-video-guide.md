# День 22 — сценарий видео: один вопрос с RAG и без RAG

Цель — показать две реальные цепочки ответа на одинаковый вопрос и оценить их на десяти заранее заданных случаях. Сравниваются факты, полнота и переданный контекст; RAG не обязан выигрывать у модели, которая уже знает Git. Ориентир: 8–12 минут основного рассказа; десять случаев можно записать отдельным фрагментом.

Фактические результаты последней проверки: [общий финальный отчёт](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Сценарий задаёт проверку, но не подтверждает её новый успех. [Ранний отчёт дня 22](../day22-test-results.md) относится к отдельному историческому запуску.

## 1. Запустить нужную версию

При работающем Docker Desktop откройте PowerShell:

```powershell
Set-Location 'F:\ai-advent-challenge\ai-chat'
git status --short
git branch --show-current
```

При чистом рабочем дереве переключитесь на ветку дня. Если есть изменения, сначала сохраните текущую работу; не сбрасывайте её ради видео.

```powershell
git switch ai-challenge-day-22
git branch --show-current
git rev-parse HEAD
Set-Location ./rag
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml up -d --build backend client
Invoke-RestMethod http://localhost:8382/actuator/health
```

В свежем клоне без локальной ветки используйте `git switch --track origin/ai-challenge-day-22`. Без NVIDIA GPU уберите `-f compose.gpu.yml`. После переключения кода пересборка обязательна: работающий контейнер сам не меняет версию. Если снимаете объединённую ветку дня 25, назовите фактическую ветку/commit и обозначьте интегрированный запуск.

Для генерации нужен серверный ключ: на этой машине используется существующий корневой `.env` с `LLM_API_KEY` или `DEEPSEEK_API_KEY`. В свежем клоне, если файла ещё нет, создайте в редакторе `F:\ai-advent-challenge\ai-chat\.env` и добавьте строку `DEEPSEEK_API_KEY=<ваш ключ>`, заменив пример настоящим ключом, затем выполните запуск Compose выше. Существующий `.env` не перезаписывайте. Ключ не вводится в браузере и не включается в сдачу. Не показывайте `.env`, `docker compose config` и окружение контейнера. Не используйте `down -v`: индексы должны сохраниться.

Откройте [localhost:8383](http://localhost:8383). В **«Разбиение и индексы»** проверьте готовый STRUCTURAL 3000/300 нужного snapshot. Если его ещё нет, выполните из [подготовки дня 21](day21-video-guide.md) только проверку корпуса, загрузку embeddings-модели и построение индекса, оставаясь на ветке 22. Повторно строить готовый совместимый индекс для дня 22 не требуется. Health API на порту 8382 должен быть `UP`; если процесс ещё запускается, повторите health после ожидания. Порты по умолчанию: UI `8383`, API `8382`, Ollama `11435`. Если в `.env` или окружении заданы `RAG_UI_PORT`, `RAG_API_PORT`, `RAG_OLLAMA_PORT`, используйте эти значения в адресах. Вывод `docker compose --env-file ../.env ps` показывает фактические опубликованные порты без вывода ключа.

## 2. Начать запись и зафиксировать условия

Покажите ветку/commit, перейдите в **«Ответы с RAG / без RAG»**. Заголовок — **«Один вопрос. Два способа ответа.»**

> «В дне 22 к поиску добавлена генерация. Без RAG модель отвечает из своих знаний. С RAG локальный поиск сначала находит фрагменты Pro Git, затем они вместе с тем же вопросом передаются модели. Модель и системная инструкция одинаковые».

Покажите строку с моделью, `temperature=0`, `thinking=disabled`. Имя читайте с экрана; текущий серверный дефолт — `deepseek-flash`. Temperature 0 не гарантирует дословно одинаковых ответов при повторении.

| Поле UI | Значение |
| --- | --- |
| «Индекс для RAG» | STRUCTURAL, 3000/300, нужный snapshot |
| «Top-K» | 5 |
| «Бюджет текста чанков» | 16000 |
| «Лимит ответа, токены» | Пусто |

> «Пять — максимум фрагментов. 16000 — бюджет символов текстов целых чанков, не токены всего запроса. Пустой лимит означает, что приложение не отправляет max_tokens; ограничения провайдера остаются».

## 3. Первый вопрос: stash, untracked и ignored

В **«Контрольный вопрос»** выберите `stash`:

> Как git stash сохранить untracked-файлы? Включает ли -u файлы, перечисленные в .gitignore?

Раскройте **«Ожидание и источник для проверки»** до запроса. Ожидается: `-u`/`--include-untracked` включает untracked, но не ignored; для ignored нужна `-a`/`--all`. Источник — `stashing-cleaning.asc`.

> «Критерий записан заранее: различить неотслеживаемые и игнорируемые файлы. Я оцениваю этот факт и полноту, а не только длину текста».

Нажмите **«Сравнить ответы · 2 API-вызова»** один раз. Дождитесь колонок **«Без RAG · знания модели»** и **«С RAG · книга в контексте»**. Это два платных вызова. Не повторяйте незаметно ради более удачного ответа: сохраните первую попытку, повтор оформите отдельно.

## 4. Разобрать ответ и доказать передачу контекста

В обеих колонках прочитайте предложения про `-u` и `-a`. Проверьте завершение: при `finish_reason=length` ответ неполный, даже если его начало верно.

Если обе колонки правильные, скажите:

> «Оба ответа верны по основному критерию. Здесь RAG не показал преимущества в правильности: модель уже знает эту тему. Отличие проверю по переданному источнику».

Если есть ошибка, назовите её точно: «В этой попытке режим … ошибся в …; в источнике сказано …». Не объявляйте один неудачный ответ универсальным свойством режима.

Далее:

1. В BASELINE раскройте **«Переданный контекст · 0 чанков»**. Должно быть сообщение, что индекс и Ollama не вызывались.
2. В RAG раскройте **«Переданный контекст · … чанков»**. Найдите `stashing-cleaning.asc`, покажите раздел, `chunk_id`, cosine и текст.
3. Нажмите **«Открыть источник ответа»**, прочитайте часть про `--include-untracked` и соседний контекст про ignored/`--all`. Закройте крестиком.
4. В обеих колонках раскройте **«Что отправлено в LLM»**. `question` одинаковый; у RAG в JSON есть `book_context`, у BASELINE его нет.
5. Покажите **«Input / output / total API»**, **«Время LLM / retrieval»** и фактическое завершение.

> «Это фактически отправленные messages. RAG действительно получил книгу. Но наличие чанка не гарантирует поддержку каждого предложения ответа: смысл я проверяю отдельно».

Usage берётся из API. При его отсутствии расход неизвестен. Локальные embedding-токены не складываются с платными токенами DeepSeek. Стоимость на экране — оценка по тарифному снимку, не подтверждённое списание.

Нажмите **«Скачать сравнение MD»** и **«Скачать результаты JSON»**. Сохраните с ID и попыткой, например `day22-stash-attempt1.md/json`. Имя загрузки по умолчанию одинаковое для разных вопросов; переименуйте файлы, чтобы случаи не смешались.

## 5. Пройти все десять контрольных вопросов

Точные формулировки — [day22-cases.json](../../evaluation/day22-cases.json); выбирайте их через список UI. Для каждого: раскрыть ожидание → сравнить → сохранить обе колонки → дать ручную оценку. Индекс, Top-K и бюджет основного опыта не менять.

| ID | Предмет вопроса | Основной факт для проверки | Источник |
| --- | --- | --- | --- |
| `reset` | `--soft`, `--mixed`, `--hard`: HEAD, индекс, рабочие файлы и риски | В форме без пути: soft перемещает ветку/HEAD; mixed также сбрасывает индекс; hard также перезаписывает файлы с риском потери правок | `reset.asc` |
| `rebase` | Merge/rebase и коммиты, на которых работают коллеги | Merge сохраняет расходящуюся историю; rebase переписывает коммиты; общая история требует согласования | `rebasing.asc` |
| `stash` | Untracked и ignored при `-u` | `-u` включает untracked без ignored; `-a` также ignored | `stashing-cleaning.asc` |
| `fetch-pull` | Fetch против pull | Fetch получает без интеграции; pull получает и интегрирует, merge/rebase зависит от настроек | `remotes.asc` |
| `undo-file` | Отмена неиндексированных изменений файла по книге | `git checkout -- <file>` восстанавливает из индекса и теряет неиндексированные правки | `undoing.asc` |
| `add-snapshot` | Файл изменён после `git add`, повторного add нет | В commit идёт версия на момент последнего add | `recording-changes.asc` |
| `branch-pointer` | Лёгкая ветка и HEAD | Ветка — ссылка на commit; HEAD обычно указывает ветку, есть detached HEAD | `nutshell.asc` |
| `git-objects` | Blob, tree, commit | Содержимое; имена/режимы/ссылки; дерево/родители/метаданные соответственно | `objects.asc` |
| `bisect` | Бинарный поиск плохого commit | Good/bad, проверки промежуточных commits, завершение через `bisect reset` | `debugging.asc` |
| `submodule` | Почему это не копия папки | Отдельный repo; основной фиксирует его commit и конфигурацию | `submodules.asc` |

Таблица — краткий ориентир; запросы берите из UI/JSON, не заменяйте их сокращениями в середине эксперимента. В полном видео можно ускорить ожидание, сохранив порядок вопросов и заметные ошибки. Для компактной сдачи покажите один подробный разбор и всю таблицу десяти сохранённых пар; подпишите, где живой запрос, а где ранее выполненный прогон.

Шаблон ручного результата:

| ID | Без RAG: верно / частично / неверно / ошибка | С RAG: верно / частично / неверно / ошибка | Неполный ответ? | Нужный источник передан? | Конкретное совпадение или ошибка | Input/output, время |
| --- | --- | --- | --- | --- | --- | --- |
| … | … | … | … | … | … | … |

Наличие ожидаемого файла и правильность ответа — отдельные критерии. Проверяйте дополнительные утверждения: верное начало не отменяет ошибку далее. Равное качество допустимо; не назначайте победителя заранее.

Автоматический повтор из `rag`, в PowerShell 7:

```powershell
pwsh -File ./scripts/verify-day22.ps1
```

Полный успешный прогон выполняет **20 новых платных вызовов**; при раннем сбое их будет меньше. Это не просмотр данных. Скрипт проверяет технические свойства и сохраняет новый файл `rag/data/day22-live-results-<timestamp>-<id>.json`; точный путь печатается в консоли. Полученные ответы сохраняются до проверок, чтобы при ошибке остался trace. Смысл скрипт не оценивает. Тестовый cap по умолчанию — `2400`, для другого значения есть `-MaxOutputTokens`; это не дефолт UI. Каждый запуск получает отдельный файл и не заменяет прежние попытки. Подпишите ветку, commit и условия конкретного отчёта.

## 6. Ошибки и сохранение результатов

Ошибка ключа/сети — технический отказ, не неверный смысловой ответ. Ошибка одной колонки не стирает соседнюю. `length` отметьте как неполный ответ; новый запуск с большим или пустым лимитом оформите как повтор, сохранив первый.

Необязательный технический опыт: вопрос `reset`, Top-K=1, бюджет=300 → **«Только с RAG»**. Если чанк длиннее бюджета, ожидается `context_budget_too_small` до генерации. После проверки вернуть 5/16000. Это зависит от фактической длины чанка и не означает отсутствия знания в книге.

Смена вкладок сохраняет результаты в текущей странице, reload удаляет их. Скачайте файлы заранее. Постоянное хранение диалогов появилось в дне 25.

Все десять случаев сохранены и оценены по заранее заданным фактам. Ошибки, неполные ответы и расход отмечены отдельно. Это не означает, что RAG всегда точнее».
