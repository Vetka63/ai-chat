# Архитектура лаборатории RAG

Этот документ описывает индексацию дня 21, генерацию дня 22, сравнение retrieval дня 23 и grounded-ответы дня 24. Основной корпус — русский перевод Pro Git, не старое предложение QASPER. Алгоритмы и проверки — в [day22-guide.md](day22-guide.md), [day23-guide.md](day23-guide.md) и [day24-guide.md](day24-guide.md).

## Назначение компонентов

Vue-клиент помогает исследовать документы, параметры разбиения и результаты индексации. Kotlin backend владеет нормализацией текста, chunking, заданиями построения, SQLite и поиском. Ollama вычисляет локальные embeddings — числовое представление смысла текста. SQLite хранит публикации индексов и прогресс jobs; исходники корпуса поставляются отдельно с manifest.

Embedding-модель не отвечает на вопросы словами. Диагностический поиск возвращает чанки. Отдельный домен `answering` добавлен в дне 22: AnswerService использует SearchService только для RAG и LlmClient для обоих режимов. DeepSeekLlmClient отвечает за внешнюю генерацию; PromptAssembler — за одинаковые базовые инструкции, целые чанки и явный бюджет.

| Компонент | Стек | Данные и ответственность |
| --- | --- | --- |
| `client` | Vue 3, TypeScript, Vite, Router, Pinia | Экраны и REST-запросы, без локальной копии vector index |
| `backend` | Kotlin 2.2.21, Spring Boot 4.1.1, JDK 21, Gradle 9.6.1 | Контракты, бизнес-процесс, проверки, поиск |
| `ollama` | Отдельный локальный Docker runtime | `qwen3-embedding:0.6b`, CPU или GPU |
| SQLite | JDBC и Float32 BLOB | Snapshots, готовые индексы, чанки и jobs |
| `corpus/progit-ru` | Закреплённые AsciiDoc файлы | Первичные документы и происхождение |

Frontend собирается независимо от Gradle. Контракт `api/openapi.json` генерирует TypeScript-типы; серверные DTO остаются Kotlin-классами. Это не Kotlin/JS и не Kotlin Multiplatform. Версии зафиксированы для воспроизводимой сборки, а не заявлены как самые новые версии всех библиотек.

## Структура проекта

```text
rag/
├── backend/                  Kotlin Spring Boot, Wrapper, unit и integration tests
├── client/                   Vue, TypeScript, generated API types, UI tests
├── api/openapi.json          Публичный HTTP-контракт
├── corpus/progit-ru/         Manifest, лицензия и 36 исходных секций
├── evaluation/              Поисковые контрольные вопросы, не часть индекса
├── docs/                    Архитектура, установка, сценарии и Archify
├── scripts/prepare-corpus.ps1
├── compose.yml              CPU запуск и отдельные volumes/ports
├── compose.gpu.yml          Опциональный доступ Ollama к GPU
```

Backend пакеты: `config`, `common`, `documents`, `indexing`, `embeddings`, `retrieval`, `answering`, `rewriting`, `experiments`, `grounding`. Внутри доменов находятся models, controllers, services, ports, adapters и enums только при наличии реального кода. DTO принадлежат своему домену. Будущие `chat`, `taskmemory` не создаются пустыми каталогами заранее.

## Зависимости доменов

`documents` знает о whitelist исходников и загрузчике, но не о model API. `indexing` получает CorpusSnapshot и ChunkingStrategy, затем использует EmbeddingProvider и IndexRepository. `retrieval` читает готовые чанки/векторы и проверяет идентичность runtime. SQL и HTTP детали находятся в adapters. Контроллеры переводят HTTP-запросы в вызовы сервисов, но не реализуют chunking.

`common` содержит только общий формат ошибок и SHA256. Он не превращается в пакет всех DTO, политик, промптов или бизнес-сервисов.

## Неизменяемый снимок корпуса

Скрипт подготовки скачивает архив по полному SHA коммита, извлекает только whitelist текстовых секций выбранных глав и LICENSE. Другие файлы, Git hooks, изображения, Ruby scripts и код сборки книги не выполняются. ZIP пути проверяются; файл секции ограничен по размеру.

Manifest содержит repository/revision/archive SHA256, отдельные source SHA256, список глав, attribution и лицензию. Повторный запуск при совпадающей revision проверяет файлы; при иной версии или изменённом хеше останавливается, не перезаписывая корпус.

CorpusService проверяет manifest и каждый файл, вызывает DocumentLoader и фиксирует snapshot на срок жизни backend. Изменение корпуса требует новой manifest/version и перезапуска. Готовый индекс сохраняет собственный нормализованный snapshot в SQLite; документ старого индекса доступен через index-scoped endpoint, даже если текущий корпус иной.

## Нормализация и координаты

AsciiDocDocumentLoader поддерживает текстовые секции Pro Git, а не произвольный полный AsciiDoc проект. Он сохраняет текст, заголовки, абзацы и блоки команд; убирает атрибуты оформления, anchors и image directives. CorpusService до parser обрабатывает два закреплённых include: `subtree-merges.asc` заменяется ссылкой на отдельный индексируемый документ, без повторного копирования текста; Ruby-пример `git-credential-read-only` разворачивается из `manifest.resources` с проверенным SHA. Произвольные include/URL не загружаются. Оставшийся неразрешённый include отклоняется, а не теряет текст молча. Parser contract — `asciidoc-safe-v2`.

Канонический текст хранится отдельно от оригинала. Все диапазоны `[start,endExclusive)` относятся к UTF-16 этого текста. `sourceLineStart/End` чанка — начальные строки первого/последнего затронутого блока; они не являются точными конечными строками оригинальной цитаты. Точную принадлежность обеспечивает source + snapshot + canonical range. Номера PDF страниц не выдумываются.

Для проверки цитат дня 24 используется канонический snapshot, показанный в UI. Изображения книги не считаются извлечёнными текстовыми доказательствами.

## Две стратегии разбиения

FIXED создаёт последовательные окна заданного максимума, независимо от заголовков. STRUCTURAL ограничивает окно текущим разделом и старается выбрать конец целого абзаца или блока команд. Если подходящего конца нет, использует ограничение размера; длинный блок может быть разрезан.

В обеих стратегиях overlap влияет на повторное включение текста. Структурная стратегия сохраняет границы разделов, но при ненулевом overlap начало окна может попасть внутрь блока. Поэтому `splitCodeBlocks` измеряет фактические нарушения, а не предполагает, что они невозможны. Для отдельной проверки сохранения блоков можно сравнить стратегии с overlap=0.

Валидация: maxCharacters от 300 до 10000, overlap от 0 до 3000 и строго меньше половины maxCharacters. Это ограничения параметров чанкинга, не собственный лимит контекста LLM.

Chunk ID зависит от snapshot ID, стратегии, конфигурации, document ID и диапазона. Один и тот же эксперимент создаёт одни и те же ID, независимо от случайного index/job UUID. В metadata есть source, title, section, chunk_id, диапазоны и hash текста.

## Эмбеддинги и идентичность модели

Для документа embedding input — title, section и точный текст чанка. Шаблон закреплён как `progit-heading-v1`. Для вопроса используется поисковая инструкция и Query prefix. В index сохраняются имя, digest, размерность и версия шаблона.

Ollama вызывается с `truncate=false`. Backend проверяет количество векторов, одинаковую размерность, числовые конечные координаты и ненулевой вектор. При ошибке запрос не превращается в zero-vector или mock. Автоматические бесконечные retry не используются: job становится FAILED, пользователь повторяет построение явно.

До и после build проверяется идентичность модели. Retrieval отклоняет несовместимый index вместо поиска в другом embedding space. Тег без digest недостаточен для воспроизводимости. Usage локальных batch-вызовов сохраняется отдельно от размеров строк; dimension probes в embeddingInputTokens не входят.

## Выполнение заданий

HTTP POST jobs создаёт QUEUED и возвращает 202. В одном backend разрешён один активный build; второй получает 409. Отдельный single-thread executor получает RUNNING, вычисляет batches и сохраняет прогресс. UI опрашивает jobs каждые две секунды; переход страницы или её перезагрузка не останавливает job.

До публикации вектора находятся в оперативной памяти процесса. После успешной проверки одна SQLite transaction сохраняет snapshot, index, все chunks/vector BLOB и READY job. Поиск видит только полностью опубликованные индексы. При ошибке transaction откатывается; существующие индексы сохраняются.

При рестарте ранее RUNNING/QUEUED jobs становятся FAILED с объяснением прерывания. Это persistence, не durable queue с автоматическим возобновлением. Один локальный worker достаточен для учебного корпуса; горизонтальные реплики backend этим протоколом не поддерживаются.

## Модель хранения

| Таблица | Назначение |
| --- | --- |
| jobs | JSON payload конфигурации, статуса, прогресса и ошибки |
| snapshots | Полный нормализованный CorpusSnapshot по immutable ID |
| indexes | IndexInfo с конфигурацией, embedding identity, метриками и snapshot FK |
| chunks | Текст/metadata payload и Float32 little-endian vector BLOB; PK index_id + chunk_id |

SQLite использует foreign keys, WAL и busy_timeout. Каждая операция открывает короткое соединение. Общий корпус не индексируется отдельно для каждого чата: в дне 21 чатов ещё нет. Budgets, профиль пользователя и task state не смешиваются с index schema.

## Поиск и сравнение

SearchService вычисляет embedding вопроса, читает вектора выбранного индекса, считает точный cosine, сортирует по score и стабильному chunk ID, возвращает top-K. Это линейный поиск малого корпуса: он прозрачен, но при миллионах чанков потребуется другая реализация vector storage/search.

Cosine не является вероятностью корректного ответа. День 23 добавляет отдельный CandidateSelector: threshold → final top-K, без перестановки ranking. Затем PromptAssembler применяет бюджет целых чанков. Это фильтр, не обученный reranker. В trace сохраняются все кандидаты, причины исключения и переданный контекст. Пустая выдача не запускает генерацию и не доказывает отсутствия ответа в книге.

Compare требует два разных индекса. Контролируемое сравнение допускается при одном snapshot и embedding identity; различия maxCharacters/overlap помечаются отдельно. Один только меньший index или больший score не доказывает лучшее качество. Build latency содержит прогрев и зависит от порядка запуска.

## Расширение недели

День 22 уже добавил AnswerService как оркестратор, PromptAssembler и LlmClient с DeepSeek adapter. Используется существующий SearchService, а не второй дублирующий поиск. Ввод пользователя и найденный текст — разные поля user JSON; системная инструкция одинакова для BASELINE и RAG. Эта изоляция не является гарантией защиты от всех prompt injection. Ответы пока не сохраняются в SQLite как чат.

День 23 добавил QueryRewriter и CandidateSelector для четырёх сравнимых режимов. ExperimentService выполняет один общий rewrite и максимум два поиска; ошибки независимых генераций не уничтожают соседние результаты. AnswerGenerator выделен из AnswerService и переиспользуется обоими флоу. Исходный вопрос сохраняется в генерации, rewrite используется только в поиске. API usage общего rewrite считается один раз; отсутствие измерения не превращается в ноль.

День 24 реализует отдельный GroundingService: исходный вопрос → optional rewrite → поиск → отбор → упаковка → JSON → `ExactCitationValidator` → `ClaimSupportValidator` → публичный ответ. Первый валидатор проверяет форму и дословность цитат по фактически переданным чанкам; source metadata и UTF-16 координаты создаёт сервер. Второй проверяет поддержку полного смысла каждого claim его собственными цитатами. В публичном ответе только claims, прошедшие обе стадии; один неподтверждённый пункт итогового варианта закрывает весь ответ; после содержательного отклонения первого черновика разрешено одно ограниченное исправление. Слабый score даёт UNKNOWN без генерации; содержательный unknown модели тоже допустим и не запускает проверку смысла. AnswerService/ExperimentService сохраняют исторические режимы без строгих цитат; для дня 24 нужно выбирать отдельную вкладку.

`ClaimSupportPromptAssembler` передаёт только claims, их точные цитаты и контекст цитируемых чанков. Окружающий текст помогает обнаружить утраченные условия, область действия и границы примера, но не может восполнить недостающую цитату. Эталонные ответы и нецитируемые чанки проверяющей модели не передаются. `LlmClaimSupportValidator` вызывает `LlmClient.completeVerifiedJson`: один JSON-запрос с отдельным профилем checker. В адаптере используются `DeepSeekProperties.supportModel` (Pro), включённый thinking и отдельный `supportReasoningEffort`; точная конфигурация прогона фиксируется в отчёте. Обычные `complete`/`completeJson` остаются на Flash с выключенным thinking. Default-метод порта делегирует `completeJson` для совместимости других адаптеров и старых test fakes.

Схема checker требует один результат на каждый индекс пункта: `claim_index`, `verdict`, `reason`, `evidence_scope`, `claim_scope`. Scope допускает только `general` или `example`; это отдельная классификация области доказательства и утверждения. Дополнительный `text` разрешён только при дословном совпадении с исходным claim. Изменённый текст, любые другие лишние поля, повторные/пропущенные индексы, дубликаты JSON-ключей, неизвестные вердикты/scope, trailing JSON и незавершённый ответ не могут дать PASSED.

Сервер отдельно проверяет согласованность scope: при `evidence_scope=example` и `claim_scope=general` он превращает даже модельный `supported` в `unsupported`. Это не доверие общему verdict поверх признанного обобщения примера. Саму область действия по-прежнему классифицирует LLM, поэтому gate не гарантирует безошибочность оценки. Scope остаются внутренними полями ответа checker в raw JSON; публичные DTO/схема API не меняются. Неподтверждённый итоговый вариант либо неправильный ответ проверки дают INVALID_EVIDENCE без публичных claims/sources; ошибка провайдера даёт ERROR. HTTP retry и baseline fallback нет.

Grounded-ответ без исправления требует двух внешних LLM-стадий. Одна правка с повторной проверкой увеличивает максимум до четырёх без rewrite и до пяти с rewrite. Технический cap checker — 16384 completion tokens, включая reasoning; он не подменяет пользовательский `maxOutputTokens=null` для генерации. `supportCheck.generation` содержит messages, финальный JSON из `content`, finish reason, latency, usage и estimate проверки, даже если её вердикты отклонены. `reasoning_content` не сохраняется и не логируется. Usage использует полное API `completion_tokens`, уже включающее reasoning. Общий расход складывает известные стадии ровно один раз; при отсутствии usage любой вызванной стадии общий usage/cost остаётся неизвестным. Транспортный сбой учитывается в числе попыток, хотя trace ответа этой стадии ещё отсутствует. Nullable поле `supportCheck` сохраняет совместимость со старыми JSON-результатами; старый ANSWERED без него не означает прохождения новой проверки. Для checker задан отдельный HTTP timeout 180 секунд (`DEEPSEEK_SUPPORT_TIMEOUT_SECONDS`); обычный timeout генерации остаётся 120 секунд.

Дословность и смысловая поддержка остаются разными свойствами. Отдельная модельная проверка уменьшает риск неподтверждённых выводов, но сама может ошибаться и не доказывает истинность книги или полноту ответа. Ручная смысловая приёмка сохраняется; свежие результаты и фактические настройки checker — в [финальном отчёте](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md), история автоматических проверок — в [отчёте об исправлениях](day24-remediation.md). Наличие новых кода и тестов само по себе не означает успешную живую приёмку. История первоначального решения — в [day24-plan-review.md](day24-plan-review.md).

Изолированный opt-in `ClaimSupportLiveTest` содержит десять случаев checker на цитатах локального корпуса. Он включается через `RAG_RUN_LIVE_SUPPORT=true`, читает `DEEPSEEK_API_KEY` с fallback на `LLM_API_KEY`, допускает `RAG_SUPPORT_TEST_MODEL` и `RAG_SUPPORT_TEST_EFFORT` для явного выбора тестового профиля. Это отдельный эксперимент, не изменение настроек обычных ответов; каждый запуск сохраняет собственный trace.

Следующий день посвящён conversation repository и памяти задачи; это не часть runtime дня 24.

Контрольные вопросы, expected answers и gold evidence живут в evaluation, не в CorpusSnapshot и не в embedding input. Нельзя добиться хорошей проверки, проиндексировав эталонные ответы рядом с книгой.

## Ограниченная правка grounded-черновика

Исправление ограничено одной видимой попыткой: только если первый черновик прошёл `ExactCitationValidator`, а первый `supportCheck.status` равен `REJECTED`, Flash получает исходный запрос, те же переданные источники и feedback проверки. Новый вариант снова проходит дословную и смысловую проверку. Неверная форма JSON, транспортный сбой, truncation, UNKNOWN или ошибка точных цитат эту попытку не запускают; после неуспеха исправления следующей попытки нет. Это отдельная стадия работы с содержанием, не HTTP retry и не неограниченный LLM-цикл.

Nullable поле `GroundedResult.repair` сохраняет первоначально отклонённый черновик: `originalGeneration` и `originalSupportCheck`. Основные поля `generation` и `supportCheck` относятся к последнему варианту. Публичные claims/sources появляются только у последнего варианта, прошедшего обе проверки; первоначальный черновик остаётся в свёрнутой диагностике **«Исправление черновика · 1 попытка»**. Старые результаты без `repair` читаются как прежде. Каждая фактически выполненная генерация и проверка входит в API usage/cost ровно один раз, в том числе сохранённые внутри `repair`; при неизвестном расходе стадии общий расход неизвестен.

Повторное исправление не запускает новый retrieval и не меняет доказательства задним числом.

## Безопасность и наблюдаемость

Нет произвольного upload URL, команд shell или исполнения команд из книги. API публикуется только на localhost, но не имеет пользовательской авторизации; это локальное учебное приложение, не публичный production service.

Логи включают job/index ID, стратегию, прогресс, dimension и ошибки. Домен answering пишет статус провайдера, фактическую модель, latency, finish reason и usage, но не ключ, тексты вопросов или сырой ответ API. Для дня 21 ключ не нужен; день 22 получает его только через окружение backend. Runtime SQLite, модели и node_modules не отправляются в Git. Model pull и исходники скачиваются только при подготовке; индексирование после этого выполняется локально.

## Архитектурная схема

[Схема дня 24](diagrams/day24-grounding.html) и её [receipt](diagrams/day24-acceptance.md) относятся к первоначальному grounded-флоу до отдельного ClaimSupportValidator. Они сохраняются как исторические артефакты; текущая дополнительная стадия и её стоимость описаны выше и в [day24-remediation.md](day24-remediation.md). Проверка старой схемы не подтверждает наличие новой стадии на рисунке.

[Схема дня 23](diagrams/day23-architecture.html) показывает доменные обращения эксперимента; [receipt](diagrams/day23-acceptance.md) фиксирует проверку артефакта, браузера и визуальный просмотр отдельно.

[Схема дня 21](diagrams/day21-architecture.html) показывает индексацию. [Схема дня 22](diagrams/day22-architecture.html) — вызовы двух режимов ответа; [receipt](diagrams/day22-acceptance.md) отделяет проверки артефакта, браузера и визуальный просмотр. Русский текст схем сохранён; стандартные элементы viewer и HTML lang у Archify остаются английскими. Исторические rag-week-architecture файлы с QASPER не отражают текущий corpus profile и не используются как инструкция реализации.
