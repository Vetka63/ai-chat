# Как работает и проверяется день 25

День 25 — сохраняемый чат по русскому Pro Git. На каждый вопрос он ищет новые источники, отвечает только цитируемыми пунктами и отдельно запоминает данные задачи. Ни память пользователя, ни прошлый ответ модели не заменяют текст книги.

## Самая короткая проверка через UI

1. Откройте http://localhost:8383 и раздел «Чат с RAG и памятью».
2. Нажмите «Новый чат». Назовите его «Отмена коммита». Выберите готовый STRUCTURAL индекс, остальные настройки оставьте как есть. Нажмите «Создать чат».
3. Напишите: «Моя цель — отменить ошибочный локальный коммит и сохранить изменения. Коммит пока не опубликован. Что делает git reset --soft?»
4. Дождитесь ответа. Справа должны появиться цель и уточнение ситуации. В ответе раскройте «Источники и цитаты», затем «Открыть цитату в книге». Цитата должна совпасть с сохранённым snapshot.
5. Напишите: «Нельзя терять изменения в рабочем каталоге. А что станет с индексом?» Ответ должен относиться к reset --soft, а не к произвольной операции. Справа сохранится общая цель и добавится ограничение.
6. Раскройте «Как получен ответ»: увидите самостоятельный поисковый вопрос, число обменов в хвосте, изменения памяти, отдельный usage подготовки и ответа.
7. Перезагрузите страницу. Вернитесь в раздел чата: выбранный чат, сообщения и память восстановятся с backend, не из browser cache.
8. Создайте второй чат. Его история и память должны быть пустыми. Вернитесь в первый — данные на месте.

Общая цель не заменяется каждым шагом. Для её явного изменения начните сообщение с «Новая цель: …». Если это совсем другая задача, создайте новый чат: смена GOAL сама не удаляет старые ограничения и уточнения.

## Длинные сценарии для сдачи

Сценарии находятся в [day25-scenarios.json](../evaluation/day25-scenarios.json). Каждый — 12 пользовательских сообщений плюс ответы, то есть 12 обменов. Следуйте вопросам последовательно в отдельных чатах.

Первый сценарий — отмена коммита с сохранением изменений, reset, временное сохранение stash, новый файл, затем смена ситуации на опубликованный коммит и запрет переписывать общую историю. Проверьте, что вопрос «А как потом вернуть их?» относится к stash, а поздняя смена ситуации не оставляет конфликтующие сведения «локальный/опубликованный».

Второй — рабочая ветка feature-login, HEAD, fetch/pull, merge, конфликт и удаление слитой ветки. Проверьте, что запрет force push и общая цель остаются после выхода первого вопроса из короткого хвоста.

После шестого обмена перезапустите только backend из папки `rag`:

```powershell
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml restart backend
```

Дождитесь health UP, перезагрузите UI и продолжайте без повторения всей цели. По умолчанию в prompt входят до шести последних целых обменов и до 10000 символов. На 12-м вопросе начало уже не входит в хвост, но память задачи ещё передаётся. Вся история по-прежнему видна в UI.

Незавершённый во время restart вопрос помечается как прерванный. Он не удаляется и не запускается снова автоматически. Для проверки restoration обычного завершённого чата не перезапускайте backend посреди генерации.

## Алгоритм под капотом

1. Клиент отправляет question, новый requestId и expectedRevision. Secret API key клиент не получает.
2. Backend атомарно сохраняет user turn в статусе PENDING. Дубликат того же requestId не оплачивает второй вызов.
3. Из истории выбирается ограниченный хвост целых обменов. Непроверенные ответы в хвост не попадают; user questions сохраняются.
4. Первый DeepSeek-вызов выдаёт standalone query и patch памяти. Последний обмен выделен как latest_exchange, более ранние — recent_dialogue: это помогает не подменять текущую тему общей целью. Сервер проверяет точные цитаты пользовательского сообщения и ограничивает изменение общей цели.
5. Новый query кодируется через локальный Ollama; exact cosine на закреплённом индексе, threshold и final K отбирают чанки. Выбор упаковки остаётся видимым.
6. Если контекст слабый — UNKNOWN без второго LLM-вызова. Если контекст есть — второй DeepSeek-вызов получает original question, resolved query, memory, recent dialogue и новые chunks, разделённые как данные.
7. CitationValidator проверяет ответ по included chunks. Неправильная цитата блокирует все технические пункты; источники не подбираются задним числом.
8. Результат и memoryAfter сохраняются одной SQLite-транзакцией. Следующее сообщение читает обновлённую память.

Поэтому «всегда источники» означает источники каждого опубликованного технического ответа. У «не знаю», ошибки провайдера или invalid evidence источников может не быть; UI явно это показывает, а не придумывает ссылки.

## Расход и границы

Обычно один вопрос — два DeepSeek-вызова. Usage подготовки, ответа и сумма показаны раздельно. При неизвестном измерении общая сумма неизвестна, а не ноль. Embeddings Ollama локальные. Estimate USD не является фактическим списанием.

Пустой лимит ответа не отправляет max_tokens. Это не отменяет лимиты самого провайдера. Для автоматических проверок применяется явное тестовое значение 2400, не production default. Выбор хвоста — ограничение размера prompt, а не удаление сообщений или summary всей истории.

Exact quote не доказывает смысловую правильность вывода. Память тоже извлекает LLM: exact user quote подтверждает происхождение, но пересказ нужно проверить глазами. Приложение не запускает git-команды и не меняет ваш реальный репозиторий при ответах.

## Воспроизводимый live тест

Из PowerShell в папке `rag`, с настроенным серверным ключом:

```powershell
.\scripts\verify-day25.ps1 -Phase Start
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml restart backend
# Дождитесь /actuator/health со status UP.
.\scripts\verify-day25.ps1 -Phase Continue
```

Это до 48 платных LLM-вызовов на два новых сценария, без retry. Скрипт сохраняет каждый trace в ignored `data/day25-live-results.json`. Он проверяет новые retrieval inputs, exact citations/snapshot offsets, user provenance, цель и ограничения вне хвоста, расход и несколько опорных названий операций в коротких продолжениях. Последняя проверка не является полноценной semantic-оценкой ответа. `-Phase All` выполняет оба сценария без промежуточного restart.

Полный экспорт через «Скачать чат MD» включает проверенные ответы, цитаты и память. JSON — расширенная диагностика, в ней есть исходные непроверенные ответы/промпты. Не публикуйте диагностический файл, если в вашем диалоге была личная информация.

Карта классов: [conversations](../backend/src/main/kotlin/dev/aichallenge/rag/conversations/README.md) и [taskmemory](../backend/src/main/kotlin/dev/aichallenge/rag/taskmemory/README.md). [Схема Archify](diagrams/day25-chat.html) показывает зависимости компонентов, не временной порядок вызовов.
