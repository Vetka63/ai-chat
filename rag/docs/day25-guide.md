# Как работает и проверяется день 25

День 25 — сохраняемый чат по русскому Pro Git. На каждый успешно подготовленный вопрос он ищет новые источники, проверяет дословность цитат и отдельно оценивает смысловую поддержку пунктов ответа. Данные задачи хранятся отдельно. Ни память пользователя, ни прошлый ответ модели не заменяют текст книги.

## Самая короткая проверка через UI

1. Откройте http://localhost:8383 и раздел «Чат с RAG и памятью».
2. Нажмите «Новый чат». Назовите его «Отмена коммита». Выберите готовый STRUCTURAL индекс, остальные настройки оставьте как есть. Нажмите «Создать чат».
3. Напишите: «Моя цель — отменить ошибочный локальный коммит и сохранить изменения. Коммит пока не опубликован. Что делает git reset --soft?»
4. Дождитесь ответа. Справа должны появиться цель и уточнение ситуации. В ответе раскройте «Источники и цитаты», затем «Открыть цитату в книге». Цитата должна совпасть с сохранённым snapshot.
5. Напишите: «Нельзя терять изменения в рабочем каталоге. А что станет с индексом?» Ответ должен относиться к reset --soft, а не к произвольной операции. Справа сохранится общая цель и добавится ограничение.
6. Раскройте «Как получен ответ»: увидите самостоятельный поисковый вопрос, число обменов в хвосте, изменения памяти и usage. В отдельном свёрнутом блоке «Проверка смысловой поддержки» находятся статус проверки, вердикты по пунктам и причины. Объяснения проверяющей модели — диагностика, не новые факты.
7. Перезагрузите страницу. Вернитесь в раздел чата: история и память восстановятся с backend. Браузер отдельно хранит выбранный ID, черновики и сведения для восстановления отправки.
8. Создайте второй чат. Его история и память должны быть пустыми. Вернитесь в первый — данные на месте.

Общая цель не заменяется каждым шагом. Для её явного изменения начните сообщение с «Новая цель: …». Если это совсем другая задача, создайте новый чат: смена GOAL сама не удаляет старые ограничения и уточнения.

## Черновики и восстановление отправки

У каждого чата собственный черновик: переключение A → B не переносит текст, новый чат открывает пустое поле, а возврат в A восстанавливает его черновик. Перед POST клиент сохраняет по ID чата текст вопроса, requestId и ожидаемую revision. На время текущего сетевого действия переключение заблокировано.

При потере ответа POST клиент проверяет историю через GET. Если сообщение с тем же requestId уже сохранено, он показывает его без второго POST. При ошибке и этой проверки появляется панель «Доставка сообщения не подтверждена»: обычная отправка в этом чате временно недоступна. «Проверить статус» выполняет только GET. «Проверить и повторить» тоже сначала делает GET; если вопрос не найден и другой обмен не выполняется, отправляет прежний вопрос с прежним requestId и актуальной revision. Автоматического повторного платного POST нет.

Перезагрузка страницы или повторный выбор чата также сверяют сохранённый receipt с историей. После подтверждения результата можно намеренно набрать тот же вопрос снова: это новый обмен с новым requestId и возможными новыми затратами. Ошибка 404 при проверке удалённого чата не блокирует создание или выбор другого чата; незавершённый вопрос туда автоматически не переносится.

Полная история и память задачи находятся в SQLite на backend. В localStorage браузера ключ `rag-conversation-client-state-v1` хранит только черновики и незавершённые отправки по ID чата, а `rag-active-conversation` — выбранный ID. Эти данные принадлежат origin и профилю браузера, содержат текст вопросов в обычном виде и не переносятся на другое устройство. Очистка данных сайта удаляет черновики и receipts, но не серверную историю. После такой очистки проверьте сохранённые сообщения перед ручным повтором.

Если localStorage недоступен или заполнен, черновики остаются в памяти открытой вкладки, раздельно по чатам. POST выполняется лишь после успешного сохранения requestId: восстановите доступ к хранилищу и повторите действие. Закрытие или перезагрузка вкладки до сохранения может потерять такой черновик. Повреждённое состояние восстановления не перезаписывается автоматически и блокирует новую отправку. Другие вкладки того же origin получают изменения через storage; сервер независимо проверяет requestId и revision.

## Длинные сценарии для сдачи

Сценарии находятся в [day25-scenarios.json](../evaluation/day25-scenarios.json). Каждый — 12 пользовательских сообщений плюс ответы, то есть 12 обменов. Следуйте вопросам последовательно в отдельных чатах.

Первый сценарий — отмена коммита с сохранением изменений, reset, временное сохранение stash, новый файл, затем смена ситуации на опубликованный коммит и запрет переписывать общую историю. Проверьте, что вопрос «А как потом вернуть их?» относится к stash, а поздняя смена ситуации не оставляет конфликтующие сведения «локальный/опубликованный».

Второй — рабочая ветка feature-login, HEAD, fetch/pull, merge, конфликт и удаление слитой ветки. Проверьте, что имя ветки попало в TERMS уже после «Назовём …», а запрет force push и общая цель остаются после выхода первого вопроса из короткого хвоста. Поздний запрет любого переписывания общей истории должен сохраниться отдельным ограничением, а не считаться повтором запрета force push.

После шестого обмена перезапустите только backend из папки `rag`:

```powershell
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml restart backend
```

Дождитесь health UP, перезагрузите UI и продолжайте без повторения всей цели. По умолчанию в prompt входят до шести последних целых обменов и до 10000 символов. На 12-м вопросе начало уже не входит в хвост, но память задачи ещё передаётся. Вся история по-прежнему видна в UI.

Незавершённый во время restart вопрос помечается как прерванный. Он не удаляется и не запускается снова автоматически. Для проверки restoration обычного завершённого чата не перезапускайте backend посреди генерации.

## Алгоритм под капотом

1. Клиент сохраняет question, новый requestId и expectedRevision в локальном receipt по ID чата, затем выполняет POST. Восстановление неопределённой отправки использует прежний requestId. Secret API key клиент не получает.
2. Backend атомарно сохраняет user turn в статусе PENDING. Дубликат того же requestId не оплачивает второй вызов.
3. Из истории выбирается ограниченный хвост целых обменов. Непроверенные ответы в хвост не попадают; user questions сохраняются.
4. Первый DeepSeek-вызов выдаёт standalone query, inventory явно сообщённых фактов и patch памяти. Последний обмен выделен как latest_exchange, более ранние — recent_dialogue: это помогает не подменять текущую тему общей целью. Сервер проверяет связь inventory/patch, точные цитаты пользователя и ограничения изменения общей цели. Согласованный пропуск факта моделью всё ещё возможен: полноту памяти нужно проверять.
5. Новый query кодируется через локальный Ollama; exact cosine на закреплённом индексе, threshold и final K отбирают чанки. Выбор упаковки остаётся видимым.
6. Если контекст слабый — UNKNOWN без второго LLM-вызова. Если контекст есть — второй DeepSeek-вызов получает original question, resolved query, memory, recent dialogue и новые chunks, разделённые как данные.
7. CitationValidator проверяет дословность по новым included chunks. При успешной проверке технических пунктов третий LLM-вызов оценивает поддержку каждого пункта его собственными цитатами и учитывает условия цитируемого текста. Только содержательное отклонение первого checker (`REJECTED`) разрешает одну правку через Flash с исходным запросом, теми же источниками и feedback, затем повтор обеих проверок. Неверная форма JSON, транспортный сбой, truncation и ошибка цитаты правку не запускают. Неподтверждённый итоговый вариант блокирует весь публичный ответ; второй правки нет. Источники не подбираются задним числом.
8. Результат и memoryAfter сохраняются одной SQLite-транзакцией. Следующее сообщение читает обновлённую память.

Поэтому «всегда источники» означает источники каждого опубликованного технического ответа. У «не знаю», ошибки провайдера или invalid evidence источников может не быть; UI явно это показывает, а не придумывает ссылки.

## Диагностика ограниченного исправления

Nullable поле `GroundedResult.repair` сохраняет первоначально отклонённый черновик: `originalGeneration` и `originalSupportCheck`. Основные поля `generation` и `supportCheck` относятся к последнему варианту. Публичные claims/sources появляются только у последнего варианта, прошедшего обе проверки; первоначальный черновик остаётся в свёрнутой диагностике **«Исправление черновика · 1 попытка»**. Старые результаты без `repair` читаются как прежде. Каждая фактически выполненная генерация и проверка входит в API usage/cost ровно один раз, в том числе сохранённые внутри `repair`; при неизвестном расходе стадии общий расход неизвестен.

Исправление содержательного черновика не создаёт второй пользовательский turn и не повторяет POST. Механизм восстановления доставки с тем же requestId остаётся отдельным. Модель checker — Pro/thinking high с cap 16384, включая reasoning, и отдельным HTTP timeout 180 секунд; grounded-генератор также использует отдельный Pro/thinking high, сохраняя пользовательский nullable лимит. Flash остаётся только в сравнении дней 22–23.

## Расход и границы

Один вопрос использует до 51 DeepSeek-вызова: одну подготовку диалога, генерацию, по три изолированные стадии проверки каждого из 1–8 пунктов; при смысловом отклонении разрешена одна правка с полным повтором проверок. Это верхняя граница, не обязательное число вызовов. При раннем UNKNOWN или ошибке стадий меньше. Usage подготовки, grounded-флоу и общая сумма показаны раздельно; блок проверки смысла показывает её собственный usage. Grounded usage уже включает проверку, повторно прибавлять его нельзя. При неизвестном измерении общая сумма неизвестна, а не ноль. Embeddings Ollama локальные. Estimate USD не является фактическим списанием.

Пустой лимит ответа не отправляет max_tokens. Это не отменяет лимиты самого провайдера. Для автоматических проверок применяется явное тестовое значение 16384, не production default. Выбор хвоста — ограничение размера prompt, а не удаление сообщений или summary всей истории.

Exact quote сама по себе не доказывает смысловую правильность вывода. Дополнительная модельная проверка снижает риск, но может ошибаться: оценивайте вывод вместе с цитатами. Старые сохранённые ANSWERED без supportCheck не проходили новую проверку; UI отмечает отсутствие записи. Память тоже извлекает LLM: exact user quote подтверждает происхождение, но пересказ и полноту нужно проверить глазами. Приложение не запускает git-команды и не меняет ваш реальный репозиторий при ответах.

## Воспроизводимый live тест

Из PowerShell в папке `rag`, с настроенным серверным ключом:

```powershell
.\scripts\verify-day25.ps1 -Phase Start
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml restart backend
# Дождитесь /actuator/health со status UP.
# Подставьте точный путь, который напечатала фаза Start.
.\scripts\verify-day25.ps1 -Phase Continue -ReportPath '.\data\day25-live-results-<timestamp>.json'
```

Это до 504 платных LLM-вызовов на два новых сценария, с одной допустимой правкой на обмен, без HTTP retry и неограниченных циклов. Двухсообщенческий live UI smoke использует до 42 вызовов; отдельная lifecycle-проверка из четырёх обменов — до 84. Каждый новый запуск скрипта создаёт отдельный ignored `data/day25-live-results-<timestamp>.json`; `Continue -ReportPath` продолжает выбранный отчёт, не заменяя исторические доказательства. Проверяются новые retrieval inputs, точные цитаты/offsets snapshot, user provenance, ожидаемые факты памяти на последующих шагах, цель вне хвоста, расход и несколько опорных названий операций. Эти проверки не заменяют ручную оценку смысла. `-Phase All` выполняет оба сценария без промежуточного restart. Старые traces с меньшим числом LLM-стадий относятся к прежней реализации.

Полный экспорт через «Скачать чат MD» включает проверенные ответы, цитаты и память. JSON — расширенная диагностика, в ней есть исходные непроверенные ответы/промпты. Не публикуйте диагностический файл, если в вашем диалоге была личная информация.

Дополнительно скрипт проверяет `PASSED` смысловой проверки для каждого опубликованного ответа и долю `ANSWERED` не ниже 10/12 (0.8333333333) в каждом сценарии (параметр `-MinimumAnsweredRate`). Это технический порог приёмки, не оценка вероятности истины. Ошибки не считаются полезными ответами; сохраняется весь trace, а не только удачные примеры.

[Актуальная схема Archify](diagrams/verified-chat.html) показывает исправленный поток; [предыдущая схема](diagrams/day25-chat.html) оставлена для истории.
