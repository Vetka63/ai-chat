# День 24: ответы, источники и цитаты

## Как проверить через UI

1. Откройте http://localhost:8383 и вкладку **«Источники и цитаты»**.
2. Выберите готовый STRUCTURAL индекс 3000/300. При отсутствии индексов сначала постройте их во вкладке разбиения. Ключ DeepSeek нужен только backend.
3. Оставьте кандидатов 10, максимум отобранных 5, порог 0.65, бюджет 16000. Rewrite выключен. Лимит пользовательского ответа можно оставить пустым: для его генерации приложение не отправляет `max_tokens`. У отдельной проверяющей модели свой технический лимит 2048 output tokens.
4. Выберите вопрос `stash` в списке. Нажмите «Ответить с цитатами». После локального поиска возможны два внешних LLM-вызова: генерация и проверка смысла. При unknown или неточной цитате второй вызов пропускается.
5. Убедитесь: принятый ответ объясняет `-u`/`--include-untracked`, отличие ignored-файлов и `-a`/`--all`. Под каждым пунктом есть точная цитата, source, section и chunk ID. Для нового ANSWERED в JSON обязательно `supportCheck.status=PASSED` и по одному SUPPORTED на пункт. Это результат двух проверок, а не гарантия истинности книги или ответа.
6. Нажмите «Открыть цитату в источнике». Документ принадлежит snapshot выбранного индекса. Разверните «Документ целиком»: цитата выделена. Escape закрывает окно.
7. Разверните поиск: найденные кандидаты, отбор и действительно переданные чанки показаны отдельно. «Не поместилось» означает бюджет, а не низкую релевантность.
8. Скачайте MD или JSON. MD содержит публичные пункты и цитаты; JSON дополнительно включает полный диагностический trace. Переключение вкладки сохраняет результат, reload — нет.
9. Пройдите все десять вопросов из списка. Для каждого отдельно проверьте: есть ли источники, совпадает ли цитата буквально, подтверждает ли она весь смысл пункта. Сверьте ответ с «Ожиданием для проверки».
10. Спросите «Какая погода завтра в Самаре?». Ожидается «Не знаю по найденным материалам» и уточнение. Нет выдуманных цитат. При пустом отборе LLM не вызывается: это видно в статистике.
11. Для вопроса о Git поставьте порог 1: ожидается такой же отказ. Верните 0.65. Cosine — не процент достоверности; настройка 0.65 подобрана для текущей модели/книги, не универсальна.
12. Для проверки ошибки ограничения ответа поставьте лимит 1 и задайте вопрос о `git reset`. Обрезанный JSON не станет публичным ответом. Верните пустой лимит. Это дополнительный платный тест, не обязательный для основной записи.

## Что происходит внутри

`GroundingController` принимает `GroundingRequest` → `GroundingService` проверяет параметры и выбирает immutable index snapshot → необязательный `QueryRewriter` уточняет только поисковый запрос → `SearchService` вычисляет embedding и cosine → `CandidateSelector` применяет порог и final K → `PromptAssembler.select` упаковывает целые чанки в бюджет.

Пустой отбор сразу даёт UNKNOWN и просьбу уточнить. Если отобранные чанки есть, но ни один не помещается, возвращается ERROR с `context_budget_too_small`.

`GroundingPromptAssembler` передаёт исходный вопрос и точные ID/тексты включённых чанков. В системной инструкции требуется JSON с `status`, `claims` и `clarification`. `DeepSeekLlmClient.completeJson` отправляет `response_format: {type: "json_object"}`. Провайдер получает только вопрос и контекст, не эталонные ответы evaluation.

Инструкция также требует отвечать именно на исходное действие/сравнение, а не перечислять правдивые сведения по похожей теме. Контекст о создании ветки не является ответом об удалении ветки; здесь нужно unknown. Это проверяется моделью и в ручной оценке, а не гарантируется substring-валидатором.

Модель возвращает, например:

```json
{"status":"known","claims":[{"text":"Факт из книги.","citations":[{"chunk_id":"ID из book_context","quote":"Дословный фрагмент переданного текста."}]}],"clarification":null}
```

Это **пример формы**, не реальный ID или проверенная цитата. Модель не создаёт source/title/section и не присылает отдельный свободный ответ.

В known поле `clarification:null` разрешено опустить: сервер восстановит null. Для unknown просьба уточнить обязательна. Остальная структура и точность цитат не исправляются «по догадке».

`ExactCitationValidator` проверяет finish reason, JSON-форму, каждый пункт и каждую цитату. ID должен быть включён в промпт; текст — точным substring без исправления пробелов. Source/title/section и координаты вычисляются сервером из чанка. Если хотя бы одна проверка не прошла, все публичные пункты удаляются.

Следом `ClaimSupportValidator` выполняет независимый JSON-вызов через тот же настроенный `LlmClient`. Он получает claims, их собственные цитаты и тексты только цитируемых чанков, без вопроса, истории, памяти и эталонных ответов. Контекст нужен, чтобы обнаружить потерянные условия примера; нецитированные предложения не могут восполнить доказательство. Проверяется весь смысл каждого пункта, включая отрицания, условия и различие между частным случаем и общим правилом. Вердикты: supported, unsupported, contradicted. Нужен ровно один вердикт на каждый индекс, без пропусков, повторов и неизвестных значений. Только полный PASSED позволяет `GroundingService` собрать поле `answer` из `claims.text`.

Например, цитата о том, где останавливается `--mixed`, не подтверждает действие `--soft`, даже если вывод о soft известен модели. Одинаковый итог «в двух показанных примерах» не доказывает одинаковый итог всех merge/rebase. Генератор должен сохранить предпосылки, подобрать достаточные цитаты либо отказаться; проверяющая стадия должна отклонить неподтверждённое расширение.

Vue отображает текст без исполнения HTML. При открытии источника клиент дополнительно сравнивает цитату с `document.text[canonicalStart:canonicalEndExclusive]`. Это сохранённый документ индекса, не произвольный файл с диска.

## Статусы и границы

| Статус | Что означает |
|---|---|
| ANSWERED | Все пункты имеют точные цитаты и прошли отдельную проверку смысловой поддержки |
| UNKNOWN | Нечего передать после фильтра либо модель не нашла ответ в чанках; нужно уточнение |
| INVALID_EVIDENCE | Некорректная структура/цитата, неподтверждённый смысл или противоречие; также неполный, неверный или обрезанный результат проверки смысла |
| ERROR | Ошибка стадии, включая недоступность проверяющей модели, или параметров упаковки; это не успешный отказ по знанию |

Исходный JSON при INVALID_EVIDENCE доступен только в закрытой диагностике с предупреждением. Нельзя использовать его как проверенный ответ. JSON-export содержит эту диагностику; MD её не публикует.

Пункт «`-u` сохраняет ignored-файлы» может ссылаться на настоящую цитату о **неотслеживаемых** файлах. Проверка substring подтвердит цитату; новая смысловая стадия должна отклонить такой вывод. Но сама проверяющая модель может ошибиться, а дословно подтверждённое утверждение книги может быть неточным вне её примера. Поэтому смысл, полноту и важные технические оговорки по-прежнему оценивают вручную. Статус не обещает автоматическую истинность. Исторический результат без `supportCheck` не проходил новый этап.

API usage берётся из ответов провайдера, embedding usage показывается отдельно. Генерация и смысловая проверка входят в сумму отдельно, rewrite добавляет ещё один вызов и учитывается один раз. `supportCheck.generation` сохраняет расход и raw JSON проверки даже при отклонении результата. Если расход любой вызванной стадии неизвестен, общий usage/cost остаётся неизвестным; успешные отдельные измерения доступны. Стоимость — оценка диапазона по тарифу, не фактическое списание. Никаких автоматических повторов или подмены ответа режимом без RAG нет.

## Воспроизводимые проверки

В каталоге `rag`:

```powershell
.\scripts\verify-day24.ps1
```

На десять контрольных вопросов приходится **до 20 платных LLM-вызовов** без rewrite: по генерации и смысловой проверке. Четыре отрицательных вопроса должны завершиться без генерации. Скрипт проверяет точность, snapshot-координаты, PASSED для каждого ANSWERED, соответствие вердиктов пунктам и учёт двух стадий. Он не заменяет человеческую оценку правильности вердиктов.

Лимит 2400 output tokens по умолчанию в скрипте относится только к тестовой генерации ответа; UI по умолчанию оставляет его пустым. Лимит 2048 относится только к техническому ответу проверяющей модели и действует независимо от пользовательского лимита. Промежуточные результаты сохраняются даже при неуспехе в новый игнорируемый `data/day24-live-results-<UTC timestamp>-<run id>.json`. Полный путь выводится при запуске; предыдущие прогоны и старый `day24-live-results.json` не перезаписываются.

```powershell
$env:RAG_LIVE='true'
cd client
npm run test:e2e -- --grep 'live grounded'
```

Один дополнительный платный UI-тест: до двух LLM-вызовов без rewrite. Обычные `npm run test:e2e -- --grep-invert '@live'` подменяют generation API, но проверяют настоящий интерфейс и работающий корпус. Backend unit/HTTP fixture tests не вызывают DeepSeek. Подставленные вердикты в unit tests проверяют протокол и карантин ответа, а качество самой модели требует отдельного живого прогона и ручного чтения.

Для отдельной проверки модели есть `ClaimSupportLiveTest`, выключенный по умолчанию. При явно установленном `RAG_RUN_LIVE_SUPPORT=true` и серверном `DEEPSEEK_API_KEY` он делает **четыре платных вызова**: отклонение ложного действия git add, soft с цитатой про mixed, обобщения примера merge/rebase и принятие корректного пересказа stash. Цитаты читаются из локального корпуса, ответы проверяющей модели настоящие. Результаты всех четырёх случаев сохраняются до итоговой проверки в отдельный `data/day24-support-live-<timestamp>-<run id>.json`; ошибка качества не запускает retry. Сбой провайдера может остановить тест после сохранения доступной диагностики.

Из `rag/backend`, с уже настроенным локально ключом:

```powershell
$env:RAG_RUN_LIVE_SUPPORT='true'
.\gradlew.bat test --tests '*ClaimSupportLiveTest' --rerun-tasks
Remove-Item Env:RAG_RUN_LIVE_SUPPORT
```

Каждый явный повтор этой команды снова вызывает провайдера. Обычный набор тестов пропускает live-класс, пока переменная не включена.
