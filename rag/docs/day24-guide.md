# День 24: ответы, источники и проверка доказательств

Задача: содержательный ответ имеет источники и цитаты; при слабом контексте — «не знаю» с уточнением. Точность цитат, смысл и полнота проверяются отдельно. Положительный вердикт LLM не гарантирует истины.

[Видео-гайд](submission/day24-video-guide.md) · [Критерии повторной приёмки](day24-25-confidence-plan.md) · [Классы](../backend/src/main/kotlin/dev/aichallenge/rag/grounding/README.md).
Старые отчёты относятся к прежним версиям, не к текущему запуску.

## Алгоритм

1. UI отправляет исходный вопрос, индекс и явные настройки.
2. Поиск получает embedding-кандидатов. Необязательный rewrite меняет только поисковую формулировку.
3. По умолчанию: 20 кандидатов → до 10 чанков, порог 0.60, бюджет 32000 символов целых чанков. Это калибровка на данном корпусе, не универсальная константа или вероятность правильности.
4. Пустой отбор даёт UNKNOWN без генерации и выдуманных источников.
5. EvidencePassages делит переданные чанки на точные фрагменты до 1200 UTF-16 символов. EvidenceCatalog даёт им короткие уникальные адреса E1, E2… внутри этого запроса. Текст не нормализуется.
6. Отдельный grounded-генератор Pro сначала выбирает ссылки `{evidence_id}`, затем формулирует факт; цитаты вручную не перепечатывает.
7. Сервер проверяет строгий JSON, номера и принадлежность включённому контексту. Из snapshot сам извлекает цитату, source, section и координаты. Публичные claims/sources/VerifiedCitation не меняются.
8. Отдельный Pro-checker проверяет каждый пункт отдельным вызовом по собственным цитатам; до трёх вызовов одновременно на backend. Он проверяет поддержку пересказа книгой, а не истинность книги через внешние знания. Исходный вопрос задаёт предмет и условия сравнения, но не служит доказательством. Rewrite не заменяет его. В чате дополнительно передаётся явно помеченное поисковое уточнение, без всей истории/памяти. Окружающий текст источника раскрывает условия и исключения.
9. После смыслового отказа допустима одна видимая правка полного ответа на том же контексте с новой проверкой. Неверная форма, ссылка, незавершённый JSON или транспортный сбой повтор не запускают.
10. Публикуется только полностью прошедший ответ. Иначе — статус и причина, а сырой черновик остаётся свёрнутой непроверенной диагностикой.

## Ссылки вместо перепечатывания

Генератор получает book_context с passages и возвращает, например:

```json
{"status":"known","claims":[{"text":"Подтверждённый факт с условиями.","citations":[{"evidence_id":"E3"}]}],"clarification":null}
```

E3 — третий фрагмент текущего запроса. Адрес уникален среди всех переданных чанков, не является номером шага внутри книги и не переносится в другой запрос. Текст цитаты сервер берёт из индекса. Неизвестный номер отклоняет код; существующий, но неподходящий по смыслу фрагмент должен отклонить checker. Выбор по ID решает дословность, не семантику.

Legacy `{chunk_id, span_index}` и `{chunk_id, quote}` поддерживаются для прежних fixtures: для quote — только точный substring 20–600 символов. Нечёткого сопоставления или автоматической замены пробелов нет. Смешивать формы нельзя. Повторные JSON-ключи, второй JSON после первого, дробные/строковые номера отклоняются.

## Проверка смысла

Для каждого пункта checker возвращает claim_index, conditions, evidence_scope, claim_scope, verdict, reason. conditions — до восьми ссылок на предпосылки своих цитируемых чанков с признаком preserved. Неполный ответ или неизвестные значения закрывают публикацию. Если модель одновременно выставила supported и потерянное условие (preserved=false) либо расширила example до general, код понижает вердикт до unsupported.

Только после допуска всех пунктов выполняются ещё два независимых шага. SourceScopeInspector видит только источники и цитаты, без ответа: выделяет предпосылки и рамки примера. Сервер нумерует обязательные проверки `R0`…; второй проверяющий возвращает `checks` по каждому ID и буквальный `anchor` из ответа/вопроса. Дубликат, пропуск или выдуманный anchor закрывает публикацию. Первичный смысловой отказ сразу идёт к единственной правке, не оплачивая пока ненужные source/scope-проверки.

Цитата о mixed не доказывает soft; результат двух учебных примеров не доказывает правило для любых merge/rebase; игнорируемые и неотслеживаемые файлы нельзя смешивать. Но корректное условное правило не должно отклоняться только из-за соседнего примера.

Проверка вероятностная. Код детерминированно проверяет контракт и согласованность, а не доказывает смысл любой книги. Для важных ответов читайте утверждения и цитаты самостоятельно.

## Модели и расход

- DEEPSEEK_GROUNDING_MODEL: Pro по умолчанию, thinking enabled, timeout 180 секунд. DEEPSEEK_GROUNDING_THINKING_ENABLED=false отключает независимый reasoning-профиль (DEEPSEEK_GROUNDING_REASONING_EFFORT=high). Пользовательский max_tokens по умолчанию не задан; при включённом thinking он ограничивает вместе reasoning и финальный JSON.
- DEEPSEEK_SUPPORT_MODEL: Pro, технический cap 16384, timeout 180 секунд. Thinking по умолчанию enabled с отдельным reasoning effort high; DEEPSEEK_SUPPORT_THINKING_ENABLED=false отключает его.
- DEEPSEEK_SCOPE_THINKING_ENABLED: независимый guard условий использует ту же Pro-модель, но свой режим thinking (по умолчанию enabled, effort low). Кап и timeout общие с checker. Это отдельный видимый вызов, не повтор первой проверки.
- Сравнение дней 22–23 не переключается на эти профили. /answer-settings описывает прежний профиль сравнения; фактическая модель grounded-вызова есть в его trace.
- Без rewrite: один вызов генерации + до трёх отдельных проверок каждого из 1–8 пунктов (первичная, source-only, сравнение условий). Общие batch-запросы по нескольким пунктам не используются. Отказ по одному пункту не отменяет проверку остальных: перед единственной правкой собирается полный feedback. Scope использует Pro low (`DEEPSEEK_SCOPE_THINKING_ENABLED=true`), первичная проверка и анализ источников — Pro high. Максимум 50 вызовов с единственной правкой полного ответа и новыми проверками; с rewrite максимум 51. Нет HTTP retry или скрытого перебора до успеха.
- В supportCheck.generation хранится первая проверка, в additionalGenerations — остальные. Порядок совпадает с пунктами, даже при параллельном выполнении. Все отправленные проверки дожидаются завершения и учитываются при отказе одной из них.
- API usage всех выполненных стадий суммируется ровно один раз. Пустой структурированный ответ сохраняет известные usage и finish reason, но не публикуется. При неизвестном расходе стадии неизвестен и общий расход.
- reasoning_content и ключ не сохраняются. Стоимость — тарифная оценка, не счёт провайдера.

## Статусы

| Статус | Значение |
|---|---|
| ANSWERED | Точные цитаты и успешный смысловой вердикт для всех пунктов |
| UNKNOWN | Недостаточный контекст либо он не отвечает на вопрос; нужно уточнение |
| INVALID_EVIDENCE | Неверная форма/ссылка, неподтверждённый смысл или незавершённая проверка |
| ERROR | Ошибка стадии/транспорта, не успешный ответ «не знаю» |

«Открыть цитату в источнике» загружает неизменяемый документ индекса. Клиент сравнивает текст с координатами перед подсветкой. MD содержит публичный ответ; JSON — также непроверенную диагностику. Результат вкладки не восстанавливается после перезагрузки, поэтому сохраняйте экспорт.

## Воспроизводимые проверки

Из rag:

```powershell
.\scripts\calibrate-grounding-retrieval.ps1
.\scripts\verify-day24.ps1
```

Первый скрипт вызывает только локальные embeddings. Второй — до 220 платных вызовов для 10 вопросов, плюс четыре ожидаемых отказа без генерации. Тестовый cap 6000 не меняет пустой default UI. Все результаты, включая неудачи, сохраняются в отдельный data/day24-live-results-*.json.

ClaimSupportLiveTest выключен по умолчанию. RAG_RUN_LIVE_SUPPORT=true включает 22 заданных случая: 10 прежних книжных и 12 синтетических контрастных. RAG_SUPPORT_TEST_REPEATS=3 — 66 проверяемых случаев, до 198 API-вызовов. RAG_SUPPORT_TEST_THINKING=true/false и RAG_SCOPE_TEST_THINKING=true/false задают разные стадии; baseline приложения не меняется. Проверяется качество judge, не генератора; все ответы записываются до итогового assertion. Условия исходного плана: все отрицательные должны получить REJECTED, не менее 95% положительных — PASSED, все запланированные круги завершены. Скрипт прекращает новые круги, только когда критерий уже невыполним; неверный вердикт не запускает выборочный retry.

ClaimSupportReplayLiveTest отдельно воспроизводит найденный в живом ответе многопунктный ложный допуск. RAG_RUN_LIVE_REPLAY=true включает до восьми вызовов (шесть пунктов, независимая разметка источника и guard условий), RAG_SUPPORT_TEST_REPEATS=3 — до 24 вызовов. Исходные пункты и чанки зафиксированы в fixture; модель не генерирует более удобный пример заново.

Обычные backend/client-тесты не обращаются к DeepSeek. Браузерные --grep-invert '@live' подставляют generation API и проверяют реальный UI. RAG_LIVE=true и тест live grounded выполняют настоящий запрос через UI (до 50 платных стадий без rewrite).

Для оценки качества нужны полный набор на неизменной версии и ручная проверка полноты, а не повтор одного вопроса до удобного ответа.
