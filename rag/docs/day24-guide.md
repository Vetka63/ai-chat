# День 24: ответы, источники и цитаты

Фактические результаты последнего живого прогона, выбранные модель/effort и оставшиеся ограничения — в [финальном отчёте](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Инструкция ниже описывает текущий протокол и ожидаемые проверки, а не объявляет все случаи успешно пройденными.

## Как проверить через UI

1. Откройте http://localhost:8383 и вкладку **«Источники и цитаты»**.
2. Выберите готовый STRUCTURAL индекс 3000/300. При отсутствии индексов сначала постройте их во вкладке разбиения. Ключ DeepSeek нужен только backend.
3. Оставьте кандидатов 10, максимум отобранных 5, порог 0.65, бюджет 16000. Rewrite выключен. Лимит пользовательского ответа можно оставить пустым: для его генерации приложение не отправляет `max_tokens`. У отдельной проверяющей модели свой технический лимит 16384 completion tokens, включая reasoning. Для checker задан отдельный HTTP timeout 180 секунд (`DEEPSEEK_SUPPORT_TIMEOUT_SECONDS`); обычный timeout генерации остаётся 120 секунд.
4. Выберите вопрос `stash` в списке. Нажмите «Ответить с цитатами». После локального поиска возможны до четырёх внешних LLM-вызовов: генерация, проверка смысла и при допустимом содержательном отклонении одна правка с повторной проверкой. При unknown или неточной цитате второй вызов пропускается.
5. Убедитесь: принятый ответ объясняет `-u`/`--include-untracked`, отличие ignored-файлов и `-a`/`--all`. Под каждым пунктом есть точная цитата, source, section и chunk ID. Для нового ANSWERED в JSON обязательно `supportCheck.status=PASSED` и по одному SUPPORTED на пункт. Это результат двух проверок, а не гарантия истинности книги или ответа.
6. Нажмите «Открыть цитату в источнике». Документ принадлежит snapshot выбранного индекса. Разверните «Документ целиком»: цитата выделена. Escape закрывает окно.
7. Разверните поиск: найденные кандидаты, отбор и действительно переданные чанки показаны отдельно. «Не поместилось» означает бюджет, а не низкую релевантность.
8. Скачайте MD или JSON. MD содержит публичные пункты и цитаты; JSON дополнительно включает полный диагностический trace. Переключение вкладки сохраняет результат, reload — нет.
9. Пройдите все десять вопросов из списка. Для каждого отдельно проверьте: есть ли источники, совпадает ли цитата буквально, подтверждает ли она весь смысл пункта. Сверьте ответ с «Ожиданием для проверки».
10. Спросите «Какая погода завтра в Самаре?». Ожидается «Не знаю по найденным материалам» и уточнение. Нет выдуманных цитат. При пустом отборе LLM не вызывается: это видно в статистике.
11. Для вопроса о Git поставьте порог 1: ожидается такой же отказ. Верните 0.65. Cosine — не процент достоверности; настройка 0.65 подобрана для текущей модели/книги, не универсальна.
12. Для проверки ошибки ограничения ответа поставьте лимит 1 и задайте вопрос о `git reset`. Обрезанный JSON не станет публичным ответом. Верните пустой лимит. Это дополнительный платный тест, не обязательный для основной записи.

## Что происходит внутри

`GroundingController` принимает `GroundingRequest` → `GroundingService` проверяет параметры и выбирает immutable index snapshot → необязательный `QueryRewriter` уточняет только поисковый запрос → `SearchService` вычисляет embedding и cosine → `CandidateSelector` применяет порог и final K → `PromptAssembler.select` упаковывает целые чанки в бюджет.

Пустой отбор сразу даёт UNKNOWN и просьбу уточнить. Если отобранные чанки есть, но ни один не помещается, возвращается ERROR с `context_budget_too_small`.

`GroundingPromptAssembler` передаёт исходный вопрос и точные ID/тексты включённых чанков. В системной инструкции требуется JSON с `status`, `claims` и `clarification`. `DeepSeekLlmClient.completeJson` отправляет `response_format: {type: "json_object"}`. Провайдер получает только вопрос и контекст, не эталонные ответы evaluation.

Инструкция также требует отвечать именно на исходное действие/сравнение, а не перечислять правдивые сведения по похожей теме. Контекст о создании ветки не является ответом об удалении ветки; здесь нужно unknown. Это проверяется моделью и в ручной оценке, а не гарантируется substring-валидатором.

Модель возвращает, например:

```json
{"status":"known","claims":[{"text":"Факт из книги.","citations":[{"chunk_id":"ID из book_context","quote":"Дословный фрагмент переданного текста."}]}],"clarification":null}
```

Это **пример формы**, не реальный ID или проверенная цитата. Модель не создаёт source/title/section и не присылает отдельный свободный ответ.

В known поле `clarification:null` разрешено опустить: сервер восстановит null. Для unknown просьба уточнить обязательна. Остальная структура и точность цитат не исправляются «по догадке».

`ExactCitationValidator` проверяет finish reason, JSON-форму, каждый пункт и каждую цитату. ID должен быть включён в промпт; текст — точным substring без исправления пробелов. Source/title/section и координаты вычисляются сервером из чанка. Если хотя бы одна проверка не прошла, все публичные пункты удаляются.

Следом `ClaimSupportValidator` выполняет независимый JSON-вызов через `LlmClient.completeVerifiedJson`. Он получает claims, их собственные цитаты и тексты только цитируемых чанков, без вопроса, истории, памяти и эталонных ответов. Контекст нужен, чтобы обнаружить потерянные условия примера; нецитированные предложения не могут восполнить доказательство. Проверяется весь смысл каждого пункта, включая отрицания, условия и различие между частным случаем и общим правилом. Вердикты: supported, unsupported, contradicted. Нужен ровно один вердикт на каждый индекс, без пропусков, повторов и неизвестных значений. Только полный PASSED позволяет `GroundingService` собрать поле `answer` из `claims.text`.

Обязательные поля одного результата checker — `claim_index`, `verdict`, `reason`, `evidence_scope`, `claim_scope`; оба scope допускают только `general` или `example`. Если доказательство объявлено частным примером, а утверждение общим правилом, сервер заменяет `supported` на `unsupported` независимо от положительного verdict модели. Классификация scope остаётся модельной и проверяется вручную вместе с итогом. Эти поля находятся во внутреннем JSON проверки, не добавляются в публичные DTO. Необязательный `text` допускается лишь как дословное эхо исходного claim: изменённое утверждение отклоняется, а не подменяет ответ генератора. Любые другие дополнительные поля, дубликаты JSON-ключей, trailing JSON и незавершённый ответ проверки также отклоняются.

Checker использует отдельные `DeepSeekProperties.supportModel` и `supportReasoningEffort` с `thinking.type=enabled`. Обычные `complete`/`completeJson`, включая генерацию grounded-ответа, сохраняют Flash, thinking disabled и пользовательский nullable лимит. Для других адаптеров default-реализация `completeVerifiedJson` делегирует `completeJson`, сохраняя совместимость существующих test fakes.

Срез конфигурации при обновлении этого гайда: `supportModel=deepseek-v4-pro`, `supportReasoningEffort=high`. Это значения текущей конфигурации, не доказательство безошибочности checker. Фактические значения и результаты сравнения профилей берите из [финального отчёта](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md), а актуальные значения по умолчанию — из `DeepSeekProperties`.

Например, цитата о том, где останавливается `--mixed`, не подтверждает действие `--soft`, даже если вывод о soft известен модели. Одинаковый итог «в двух показанных примерах» не доказывает одинаковый итог всех merge/rebase. Генератор должен сохранить предпосылки, подобрать достаточные цитаты либо отказаться; проверяющая стадия должна отклонить неподтверждённое расширение.

Vue отображает текст без исполнения HTML. При открытии источника клиент дополнительно сравнивает цитату с `document.text[canonicalStart:canonicalEndExclusive]`. Это сохранённый документ индекса, не произвольный файл с диска.

## Одна видимая попытка исправления

Исправление ограничено одной видимой попыткой: только если первый черновик прошёл `ExactCitationValidator`, а первый `supportCheck.status` равен `REJECTED`, Flash получает исходный запрос, те же переданные источники и feedback проверки. Новый вариант снова проходит дословную и смысловую проверку. Неверная форма JSON, транспортный сбой, truncation, UNKNOWN или ошибка точных цитат эту попытку не запускают; после неуспеха исправления следующей попытки нет. Это отдельная стадия работы с содержанием, не HTTP retry и не неограниченный LLM-цикл.

Nullable поле `GroundedResult.repair` сохраняет первоначально отклонённый черновик: `originalGeneration` и `originalSupportCheck`. Основные поля `generation` и `supportCheck` относятся к последнему варианту. Публичные claims/sources появляются только у последнего варианта, прошедшего обе проверки; первоначальный черновик остаётся в свёрнутой диагностике **«Исправление черновика · 1 попытка»**. Старые результаты без `repair` читаются как прежде. Каждая фактически выполненная генерация и проверка входит в API usage/cost ровно один раз, в том числе сохранённые внутри `repair`; при неизвестном расходе стадии общий расход неизвестен.

Если появился блок **«Исправление черновика · 1 попытка»**, раскройте его и сопоставьте первоначальный отказ с последним ответом. Не выдавайте отклонённый текст за публичный результат. Без rewrite максимум четыре LLM-вызова, с rewrite — пять; ранний отказ может сократить их число.

## Статусы и границы

| Статус | Что означает |
|---|---|
| ANSWERED | Все пункты имеют точные цитаты и прошли отдельную проверку смысловой поддержки |
| UNKNOWN | Нечего передать после фильтра либо модель не нашла ответ в чанках; нужно уточнение |
| INVALID_EVIDENCE | Некорректная структура/цитата, неподтверждённый смысл или противоречие; также неполный, неверный или обрезанный результат проверки смысла |
| ERROR | Ошибка стадии, включая недоступность проверяющей модели, или параметров упаковки; это не успешный отказ по знанию |

Исходный JSON при INVALID_EVIDENCE доступен только в закрытой диагностике с предупреждением. Нельзя использовать его как проверенный ответ. JSON-export содержит эту диагностику; MD её не публикует.

Пункт «`-u` сохраняет ignored-файлы» может ссылаться на настоящую цитату о **неотслеживаемых** файлах. Проверка substring подтвердит цитату; новая смысловая стадия должна отклонить такой вывод. Но сама проверяющая модель может ошибиться, а дословно подтверждённое утверждение книги может быть неточным вне её примера. Поэтому смысл, полноту и важные технические оговорки по-прежнему оценивают вручную. Статус не обещает автоматическую истинность. Исторический результат без `supportCheck` не проходил новый этап.

API usage берётся из ответов провайдера, embedding usage показывается отдельно. Генерация и смысловая проверка входят в сумму отдельно, rewrite добавляет ещё один вызов и учитывается один раз. `completion_tokens` checker учитывается целиком, включая reasoning, без повторного прибавления или вычитания reasoning-токенов. `supportCheck.generation` сохраняет расход и финальный JSON из `content` даже при отклонении результата; `reasoning_content` и API key не сохраняются и не логируются. Если расход любой вызванной стадии неизвестен, общий usage/cost остаётся неизвестным; успешные отдельные измерения доступны. Стоимость — оценка диапазона по тарифу, не фактическое списание. HTTP retry, неограниченных повторов и подмены ответом без RAG нет; одна ограниченная содержательная правка видна отдельно в trace.

## Воспроизводимые проверки

В каталоге `rag`:

```powershell
.\scripts\verify-day24.ps1
```

На десять контрольных вопросов приходится **до 40 платных LLM-вызовов** без rewrite: генерация и проверка, при необходимости одна правка и её проверка. Четыре отрицательных вопроса должны завершиться без генерации. Скрипт проверяет точность, snapshot-координаты, PASSED для каждого ANSWERED, соответствие вердиктов пунктам и однократный учёт всех выполненных стадий, включая первоначальный отклонённый черновик. Он не заменяет человеческую оценку правильности вердиктов.

Лимит 2400 output tokens по умолчанию в скрипте относится только к тестовой генерации ответа; UI по умолчанию оставляет его пустым. Лимит 16384 completion tokens относится только к checker, включает reasoning и действует независимо от пользовательского лимита. Если reasoning израсходовал бюджет и финальный JSON не завершён, результат не считается успешной проверкой. Промежуточные результаты сохраняются даже при неуспехе в новый игнорируемый `data/day24-live-results-<UTC timestamp>-<run id>.json`. Полный путь выводится при запуске; предыдущие прогоны и старый `day24-live-results.json` не перезаписываются.

```powershell
$env:RAG_LIVE='true'
cd client
npm run test:e2e -- --grep 'live grounded'
```

Один дополнительный платный UI-тест: до четырёх LLM-вызовов без rewrite. Обычные `npm run test:e2e -- --grep-invert '@live'` подменяют generation API, но проверяют настоящий интерфейс и работающий корпус. Backend unit/HTTP fixture tests не вызывают DeepSeek. Подставленные вердикты в unit tests проверяют протокол и карантин ответа, а качество самой модели требует отдельного живого прогона и ручного чтения.

Для отдельной проверки модели есть `ClaimSupportLiveTest`, выключенный по умолчанию. При явно установленном `RAG_RUN_LIVE_SUPPORT=true` и доступном ключе он делает **до десяти платных вызовов** checker, без генерации ответа и rewrite. Ключ читается из `DEEPSEEK_API_KEY`, при его отсутствии — из `LLM_API_KEY`. `DEEPSEEK_BASE_URL` задаёт адрес провайдера; `RAG_SUPPORT_TEST_MODEL` и `RAG_SUPPORT_TEST_EFFORT` позволяют явно выбрать модель и effort именно теста. Эти overrides не объявляют новый default приложения или выигрыш качества.

Набор включает ложное действие git add, soft с цитатой про mixed, расширение частного merge/rebase-примера, корректный пересказ stash, количество Git-объектов с сохранённой и потерянной областью примера, обобщение трёхстороннего слияния и три утверждения про HEAD с разной точностью условий. Ожидаются семь отклонений и три принятия; это заранее заданные критерии, не уже полученные результаты. Цитаты читаются из локального корпуса. Полученные результаты сохраняются до итоговой проверки в отдельный `data/day24-support-live-<timestamp>-<run id>.json`; ошибка качества не запускает retry. Сбой провайдера может остановить тест после сохранения доступной диагностики.

Из `rag/backend`, с уже настроенным локально ключом:

```powershell
$env:RAG_RUN_LIVE_SUPPORT='true'
.\gradlew.bat test --tests '*ClaimSupportLiveTest' --rerun-tasks
Remove-Item Env:RAG_RUN_LIVE_SUPPORT
```

Каждый явный повтор этой команды снова вызывает провайдера. Обычный набор тестов пропускает live-класс, пока переменная не включена. Для сравнения профилей задайте нужные `RAG_SUPPORT_TEST_MODEL`/`RAG_SUPPORT_TEST_EFFORT` до запуска и зафиксируйте их вместе с отдельным trace; после опыта удалите только те временные переменные, которые добавили для него. Итоги всех попыток, включая неудачные, относятся к [финальному отчёту](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md), а не к счётчику обычных unit tests.

[Архитектурная карта](diagrams/day24-grounding.html) показывает зависимости компонентов, а не временную последовательность. Русский текст авторских узлов; фиксированный интерфейс viewer и HTML lang — английские. [Описание классов](../backend/src/main/kotlin/dev/aichallenge/rag/grounding/README.md).
