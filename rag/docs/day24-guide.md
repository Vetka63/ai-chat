# День 24: ответы, источники и цитаты

## Как проверить через UI

1. Откройте http://localhost:8383 и вкладку **«Источники и цитаты»**.
2. Выберите готовый STRUCTURAL индекс 3000/300. При отсутствии индексов сначала постройте их во вкладке разбиения. Ключ DeepSeek нужен только backend.
3. Оставьте кандидатов 10, максимум отобранных 5, порог 0.65, бюджет 16000. Rewrite выключен. Лимит ответа можно оставить пустым: приложение не отправляет `max_tokens`.
4. Выберите вопрос `stash` в списке. Нажмите «Ответить с цитатами». Будет один внешний LLM-вызов после локального поиска.
5. Убедитесь: ответ объясняет `-u`/`--include-untracked`, отличие ignored-файлов и `-a`/`--all`. Под каждым пунктом есть точная цитата, source, section и chunk ID. Статус «Цитаты проверены» означает проверку текста, не оценку смысла.
6. Нажмите «Открыть цитату в источнике». Документ принадлежит snapshot выбранного индекса. Разверните «Документ целиком»: цитата выделена. Escape закрывает окно.
7. Разверните поиск: найденные кандидаты, отбор и действительно переданные чанки показаны отдельно. «Не поместилось» означает бюджет, а не низкую релевантность.
8. Скачайте MD или JSON. MD содержит публичные пункты и цитаты; JSON дополнительно включает полный диагностический trace. Переключение вкладки сохраняет результат, reload — нет.
9. Пройдите все десять вопросов из списка. Для каждого отдельно проверьте: есть ли источники, совпадает ли цитата буквально, подтверждает ли она весь смысл пункта. Сверьте ответ с «Ожиданием для проверки».
10. Спросите «Какая погода завтра в Самаре?». Ожидается «Не знаю по найденным материалам» и уточнение. Нет выдуманных цитат. При пустом отборе LLM не вызывается: это видно в статистике.
11. Для вопроса о Git поставьте порог 1: ожидается такой же отказ. Верните 0.65. Cosine — не процент достоверности; настройка 0.65 подобрана для текущей модели/книги, не универсальна.
12. Для проверки ошибки ограничения ответа поставьте лимит 1 и задайте вопрос о `git reset`. Обрезанный JSON не станет публичным ответом. Верните пустой лимит. Это дополнительный платный тест, не обязательный для основной записи.

## Что происходит внутри

`GroundingController` принимает `GroundingRequest` → `GroundingService` проверяет параметры и выбирает immutable index snapshot → необязательный `QueryRewriter` уточняет только поисковый запрос → `SearchService` вычисляет embedding и cosine → `CandidateSelector` применяет порог и final K → `PromptAssembler.select` упаковывает целые чанки в бюджет.

Пустой отбор сразу даёт UNKNOWN и просьбу уточнить. Если отобранные чанки есть, но ни один не помещается, возвращается ERROR с `context_budget_too_small`.

`GroundingPromptAssembler` передаёт исходный вопрос и точные ID/тексты включённых чанков. В системной инструкции требуется JSON с `status`, `claims` и `clarification`. `DeepSeekLlmClient.completeJson` отправляет `response_format: {type: "json_object"}`. Провайдер получает только вопрос и контекст, не эталонные ответы evaluation.

Инструкция также требует отвечать именно на исходное действие/сравнение, а не перечислять правдивые сведения по похожей теме. Контекст о создании ветки не является ответом об удалении ветки; здесь нужно unknown. Это проверяется моделью и в ручной оценке, а не гарантируется substring-валидатором.

Модель возвращает, например:

```json
{"status":"known","claims":[{"text":"Факт из книги.","citations":[{"chunk_id":"ID из book_context","quote":"Дословный фрагмент переданного текста."}]}],"clarification":null}
```

Это **пример формы**, не реальный ID или проверенная цитата. Модель не создаёт source/title/section и не присылает отдельный свободный ответ.

В known поле `clarification:null` разрешено опустить: сервер восстановит null. Для unknown просьба уточнить обязательна. Остальная структура и точность цитат не исправляются «по догадке».

`ExactCitationValidator` проверяет finish reason, JSON-форму, каждый пункт и каждую цитату. ID должен быть включён в промпт; текст — точным substring без исправления пробелов. Source/title/section и координаты вычисляются сервером из чанка. Если хотя бы одна проверка не прошла, все публичные пункты удаляются. Только после успешной проверки `GroundingService` собирает поле `answer` из `claims.text`.

Vue отображает текст без исполнения HTML. При открытии источника клиент дополнительно сравнивает цитату с `document.text[canonicalStart:canonicalEndExclusive]`. Это сохранённый документ индекса, не произвольный файл с диска.

## Статусы и границы

| Статус | Что означает |
|---|---|
| ANSWERED | Все пункты имеют точные цитаты из переданного контекста |
| UNKNOWN | Нечего передать после фильтра либо модель не нашла ответ в чанках; нужно уточнение |
| INVALID_EVIDENCE | Некорректная структура, чужой ID, изменённая/слишком короткая цитата или обрезанный JSON |
| ERROR | Ошибка стадии или параметров упаковки; это не успешный отказ по знанию |

Исходный JSON при INVALID_EVIDENCE доступен только в закрытой диагностике с предупреждением. Нельзя использовать его как проверенный ответ. JSON-export содержит эту диагностику; MD её не публикует.

Пример ограничения гарантии: пункт «`-u` сохраняет ignored-файлы» может ссылаться на настоящую цитату о **неотслеживаемых** файлах. Проверка substring подтвердит цитату, но не такой вывод. Поэтому семантическую поддержку и полноту проверяем отдельно; надпись в UI не обещает автоматическую истинность.

API usage берётся из ответа провайдера, embedding usage показывается отдельно. Стоимость — оценка диапазона по тарифу, не фактическое списание. Rewrite добавляет один вызов и включается в сумму один раз. Никаких автоматических повторов или подмены ответа режимом без RAG нет.

## Воспроизводимые проверки

В каталоге `rag`:

```powershell
.\scripts\verify-day24.ps1
```

Десять оплачиваемых ответов, четыре отрицательных вопроса без генерации, проверка точности и snapshot-координат. Промежуточные результаты сохраняются в игнорируемый `data/day24-live-results.json` даже при неуспехе. Скрипт не ставит оценку смысловой правильности.

```powershell
$env:RAG_LIVE='true'
cd client
npm run test:e2e -- --grep 'live grounded'
```

Один дополнительный платный UI-тест. Обычные `npm run test:e2e -- --grep-invert '@live'` подменяют generation API, но проверяют настоящий интерфейс и работающий корпус. Backend unit/HTTP fixture tests не вызывают DeepSeek.
