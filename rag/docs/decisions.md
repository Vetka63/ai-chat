# Архитектурные решения RAG

Здесь зафиксированы причины выбора решений, чтобы последующие дни расширяли один пайплайн и не повторяли ошибки смешения доменов.

## Kotlin backend и обычный frontend

Backend использует Spring Boot, потому что пользователь знаком со Spring и хочет Kotlin. Vue/TypeScript остаётся самостоятельным клиентом. OpenAPI связывает контракты, без общего Kotlin Multiplatform runtime. Версии зависимостей закреплены; их обновление выполняется отдельно с повторной сборкой.

## Книга вместо QASPER

Русская техническая книга удобна для ручных проверок и структурного chunking. В отличие от QASPER она не поставляет готовые answer/evidence labels: их готовим отдельно. Научную эквивалентность benchmark не обещаем. Сохраняем оригинал, лицензию, revision и normalized representation.

## Локальный Ollama в Docker

Выбран отдельный контейнер, а не изменение Windows install/PATH. Это устраняет зависимость от найденной старой версии Node и отсутствия ollama executable. Native Ollama остаётся допустимой альтернативой по инструкции. Основной runtime работает на CPU; GPU включается отдельным compose override.

## SQLite и точный поиск

Для небольшого корпуса SQLite и exact cosine достаточно. Храним Float32 BLOB, не числовые массивы в огромном JSON. Схема разделяет jobs, snapshot, index и chunks. При росте корпуса можно заменить adapter/поисковую реализацию; отдельные FAISS/Python/vector DB не нужны ради сдачи первого дня.

## Один worker и атомарная публикация

Выбран single-thread executor с одним активным job. Он не является распределённым scheduler. До успеха embedding всех чанков индекс не публикуется. Restart прерывает незавершённый job, но не готовый индекс. Resumable batch queue можно добавить позднее при реальной необходимости.

## Сравнение только контролируемых изменений

Одинаковый corpus snapshot, model digest, embedding template и размерность обязательны. Параметры размера/overlap задаются явно. STRUCTURAL не считается лучше заранее: сравниваем coverage, границы, split code и реальные поисковые вопросы. Timing включает прогрев, поэтому не объявляем одну случайную задержку универсальной скоростью.

## Не реализовывать всю неделю заранее

День 21 заканчивается индексом и диагностическим retrieval. Day 22 добавляет генерацию, day 23 — rewrite/filter, day 24 — grounded output, day 25 — память. Будущие features не создают пустые пакеты или неработающие кнопки. Каждая ветка остаётся самостоятельным демонстрационным результатом.
