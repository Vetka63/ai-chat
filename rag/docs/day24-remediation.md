# День 24: исправление проверки смысловой поддержки

Этот отчёт описывает исправление дня 24 после добавления отдельного `ClaimSupportValidator` и последующее выделение профиля checker. [Первоначальный отчёт](day24-test-results.md) сохранён как история конвейера, проверявшего дословность цитат автоматически и смысл вручную. Его live-результаты и стоимость не являются проверкой новой стадии. Актуальные ветка/commit, настройки и результаты повторной живой приёмки фиксируются в [финальном отчёте](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md).

## Что исправлено

Реальная цитата не всегда подтверждает связанный с ней вывод. Утверждение может приписать действие одной опции другой или превратить частный книжный пример в универсальное правило. Одного substring-сравнения для этого недостаточно.

Текущая последовательность: генерация структурированного ответа → `ExactCitationValidator` → `ClaimSupportValidator` → публикация. Первый этап проверяет форму, принадлежность и дословность цитат; второй — полный смысл каждого пункта и сохранение условий его собственных цитат. Генератору также явно предписано сохранять предпосылки примера и не расширять подтверждённый вывод.

Проверяющая модель получает claims, их цитаты и окружающий текст только цитируемых чанков. Название раздела и окружающий текст помогают обнаружить потерянный контекст, но не заменяют недостающее доказательство. Другой пункт ответа, нецитируемый чанк и эталонные ответы не служат источниками. Проверка вызывает `LlmClient.completeVerifiedJson`: тот же транспорт DeepSeek, но отдельные `supportModel` (Pro) и `supportReasoningEffort`, с включённым thinking. Обычные `complete`/`completeJson` сохраняют Flash с выключенным thinking. Выбор effort в отдельном эксперименте не означает автоматической смены default; конфигурация и результат опыта записываются в финальном отчёте. HTTP retry и неограниченных повторов нет; возможна одна видимая содержательная правка по правилам ниже.

## Публикация и диагностика

Новый ANSWERED допускается только после обеих проверок: `supportCheck.status=PASSED` и по одному SUPPORTED на каждый пункт. UNSUPPORTED или CONTRADICTED у итогового варианта закрывает весь ответ как INVALID_EVIDENCE; публичные claims/sources пусты. У результата checker обязательны `claim_index`, `verdict`, `reason`, `evidence_scope`, `claim_scope`. Scope допускает только `general` или `example`; при сочетании evidence=example и claim=general сервер заменяет `supported` на `unsupported`. Это отдельная проверка согласованности области, которую первоначально определяет модель; её классификация тоже может ошибаться. Поля scope остаются во внутреннем JSON проверки, публичные DTO не меняются. Необязательный `text` разрешён только как дословное эхо исходного claim. Изменённый `text`, любые другие лишние поля, неизвестный вердикт/scope, пропущенный/повторный индекс, дубликат JSON-ключа, trailing JSON или обрезанный ответ проверки также ведут к карантину. Сбой провайдера возвращает ERROR. Нет частичной публикации и fallback к ответу без RAG.

`supportCheck.generation` сохраняет сообщения, финальный JSON из `content`, фактическую модель, finish reason, latency, usage и estimate даже при отклонении вердиктов. `reasoning_content` и ключ не сохраняются и не логируются. Это диагностический ответ модели, не дополнительное публичное доказательство. Поле `supportCheck` nullable с default null: старые JSON-результаты остаются читаемыми, но их прежний ANSWERED не означает прохождения нового этапа. Default-реализация нового метода `LlmClient` делегирует `completeJson` для совместимости других адаптеров и существующих test fakes.

## Ограниченное исправление черновика

Исправление ограничено одной видимой попыткой: только если первый черновик прошёл `ExactCitationValidator`, а первый `supportCheck.status` равен `REJECTED`, Flash получает исходный запрос, те же переданные источники и feedback проверки. Новый вариант снова проходит дословную и смысловую проверку. Неверная форма JSON, транспортный сбой, truncation, UNKNOWN или ошибка точных цитат эту попытку не запускают; после неуспеха исправления следующей попытки нет. Это отдельная стадия работы с содержанием, не HTTP retry и не неограниченный LLM-цикл.

Nullable поле `GroundedResult.repair` сохраняет первоначально отклонённый черновик: `originalGeneration` и `originalSupportCheck`. Основные поля `generation` и `supportCheck` относятся к последнему варианту. Публичные claims/sources появляются только у последнего варианта, прошедшего обе проверки; первоначальный черновик остаётся в свёрнутой диагностике **«Исправление черновика · 1 попытка»**. Старые результаты без `repair` читаются как прежде. Каждая фактически выполненная генерация и проверка входит в API usage/cost ровно один раз, в том числе сохранённые внутри `repair`; при неизвестном расходе стадии общий расход неизвестен.

## Стоимость и ограничения

Без исправления вопрос использует две LLM-стадии. Одна правка с повторной проверкой увеличивает максимум до четырёх без rewrite и до пяти с rewrite. Проверка смысла имеет технический лимит 16384 completion tokens, включая reasoning. Он не меняет `maxOutputTokens=null` для пользовательской генерации; тестовый лимит 2400 в скрипте относится только к её экспериментальному запуску. Поле API `completion_tokens` учитывается целиком: reasoning не вычитается и не добавляется повторно. Для checker задан отдельный HTTP timeout 180 секунд (`DEEPSEEK_SUPPORT_TIMEOUT_SECONDS`); обычный timeout генерации остаётся 120 секунд.

Общий usage/cost суммирует каждую выполненную стадию один раз. Если провайдер не вернул usage одной вызванной стадии, общая сумма остаётся неизвестной, а отдельные известные измерения сохраняются. При транспортной ошибке попытка учитывается, даже если ответ и usage стадии ещё не получены. Оценка стоимости не является подтверждённым списанием.

Смысловая проверка снижает риск неподтверждённых выводов, но сама может ошибаться. Она не доказывает истинность книги и не гарантирует полноту ответа. Совпадение с цитатой, поддержка смысла и техническая корректность вне конкретного примера оцениваются раздельно.

## Повторная живая приёмка

При первоначальном составлении этого отчёта 4 октября 2026 года новая смысловая стадия ещё не имела завершённой живой приёмки. Текущий статус не выводится из этого исторического ограничения: фактические попытки, выбранные модель/effort и результаты собраны в [финальном отчёте](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md). Для смыслового вывода нужны сохранённые результаты и чтение каждого claim вместе с цитатами и вердиктом; автоматические проверки выше их не заменяют.

`scripts/verify-day24.ps1` выполняет десять вопросов без rewrite — до 40 платных LLM-вызовов — и четыре ожидаемых отказа без генерации. Все полученные исходы сохраняются; обычный отказ по качеству не останавливает оставшиеся случаи и не вызывает транспортный retry; одна допустимая содержательная правка учитывается внутри того же результата. Итоговая проверка не считается успешной, если хотя бы один контрольный ответ отклонён. Новый trace имеет вид `data/day24-live-results-<UTC timestamp>-<run id>.json`; старые файлы не перезаписываются.

Отдельный `ClaimSupportLiveTest` включается только через `RAG_RUN_LIVE_SUPPORT=true`. Текущий fixture содержит десять настоящих проверок на цитатах локального корпуса: семь ожидаемых отклонений и три ожидаемых принятия. Это ожидания набора, а не заявление о полученных вердиктах. Ключ — `DEEPSEEK_API_KEY` с fallback на `LLM_API_KEY`; тестовые overrides — `RAG_SUPPORT_TEST_MODEL` и `RAG_SUPPORT_TEST_EFFORT`. Результаты сохраняются отдельно в `data/day24-support-live-<timestamp>-<run id>.json`. В обычном suite тест пропущен, а историческое число 76 passed не доказывает качество модели. Условия запуска и расход каждого повтора — в [day24-guide.md](day24-guide.md), фактические результаты — в [финальном отчёте](https://github.com/Vetka63/ai-chat/blob/ai-challenge-day-25/rag/docs/final-live-verification.md).

Актуальный алгоритм — в [architecture.md](architecture.md), исходные решения и их пересмотр — в [day24-plan-review.md](day24-plan-review.md). Старый рисунок `diagrams/day24-grounding.html` создан до новой стадии и сохраняется как исторический артефакт.
