Текущие средства повторной проверки:

По умолчанию тест отключён; включение — `RAG_RUN_LIVE_SUPPORT=true`, ключ — `DEEPSEEK_API_KEY` с fallback на `LLM_API_KEY`, явные overrides — `RAG_SUPPORT_TEST_MODEL`/`RAG_SUPPORT_TEST_EFFORT`.

Ручная оценка должна прочитать **каждый** опубликованный claim вместе с его quote: наличие `PASSED` у judge не гарантирует истину. `UNKNOWN`/`INVALID_EVIDENCE` — безопасный исход при недостаточном доказательстве, но слишком много отказов означает проблему полезности, которую нельзя скрывать успешными HTTP-кодами.

## Изменение расхода и поведение UI

День 24: до 4 LLM-вызовов без rewrite, до 5 с rewrite, включая одну допустимую правку и её проверку. День 25: до 5 — подготовка вопроса/памяти и grounded-цепочка. Пустой retrieval/unknown/неверные цитаты могут завершить поток раньше. HTTP retry и неограниченных повторов нет; содержательная правка ограничена одной видимой попыткой. Checker вызывается через `completeVerifiedJson`, с отдельными `DeepSeekProperties.supportModel` (Pro) и `supportReasoningEffort`, thinking enabled; точные значения опыта фиксируются в финальном отчёте. Обычные Flash-вызовы остаются с thinking disabled и пользовательским `maxOutputTokens=null` по умолчанию.

Технический cap checker — 16384 completion tokens, включая reasoning. API `completion_tokens` учитывается полностью; reasoning не прибавляется и не вычитается отдельно. В trace сохраняется финальный JSON `content`, а `reasoning_content` и ключ не сохраняются и не логируются. Usage/cost checker включены в общий расход без двойного учёта; неизвестный расход не превращается в ноль. Для checker задан отдельный HTTP timeout 180 секунд (`DEEPSEEK_SUPPORT_TIMEOUT_SECONDS`); обычный timeout генерации остаётся 120 секунд.

Результат checker содержит `claim_index`, `verdict`, `reason`, `evidence_scope`, `claim_scope`; scope принимает только `general` или `example`. Сервер не принимает `supported`, если сама модель назвала доказательство примером, а утверждение общим правилом: итоговый verdict становится `unsupported`. Классификация scope остаётся модельной; это проверка её согласованности с verdict, а не гарантия истинности. Scope не добавляется в публичные DTO. Необязательный `text` допускается только как дословное эхо исходного claim. Изменённое эхо или любые другие дополнительные поля отклоняются. Этот допуск не позволяет модели переписать утверждение вместо его проверки.

Старые сохранённые ответы без `supportCheck` остаются читаемыми, но не считаются ретроспективно проверенными новой моделью. Новая проверка не переписывает прошлую историю. Черновики/receipt находятся в браузере; подтверждённая история/память — в SQLite. Очистка browser storage удаляет локальную возможность восстановления неопределённой отправки, но не серверный чат.

## Одна ограниченная правка после смыслового отклонения

Исправление ограничено одной видимой попыткой: только если первый черновик прошёл `ExactCitationValidator`, а первый `supportCheck.status` равен `REJECTED`, Flash получает исходный запрос, те же переданные источники и feedback проверки. Новый вариант снова проходит дословную и смысловую проверку. Неверная форма JSON, транспортный сбой, truncation, UNKNOWN или ошибка точных цитат эту попытку не запускают; после неуспеха исправления следующей попытки нет. Это отдельная стадия работы с содержанием, не HTTP retry и не неограниченный LLM-цикл.

Nullable поле `GroundedResult.repair` сохраняет первоначально отклонённый черновик: `originalGeneration` и `originalSupportCheck`. Основные поля `generation` и `supportCheck` относятся к последнему варианту. Публичные claims/sources появляются только у последнего варианта, прошедшего обе проверки; первоначальный черновик остаётся в свёрнутой диагностике **«Исправление черновика · 1 попытка»**. Старые результаты без `repair` читаются как прежде. Каждая фактически выполненная генерация и проверка входит в API usage/cost ровно один раз, в том числе сохранённые внутри `repair`; при неизвестном расходе стадии общий расход неизвестен.

Четыре обмена `scripts/verify-memory-lifecycle.ps1` могут потребовать до 20 LLM-вызовов. Это верхняя граница текущего алгоритма, а не изменение исторических измерений выше.

## Самостоятельная проверка по UI

1. Откройте `http://localhost:8383`, вкладку «Чат с RAG и памятью». Создайте **новый** чат с STRUCTURAL 3000/300, хвостом 6, пустым лимитом ответа.
2. Напишите: «Хочу работать в отдельной ветке и затем объединить изменения с командой. Force push в общую ветку запрещён. Как создать ветку?».
3. Напишите: «Назовём рабочую ветку release-payment. Чем branch отличается от checkout -b?» Проверьте TERMS и ссылку на эту пользовательскую реплику. Затем: «Договорились не переписывать общую историю. Почему rebase общей ветки рискован?» — нужен **отдельный** запрет, а не замена force push.
4. Если получен ответ, раскройте его источники и «Проверка смысла». Quote должна подтверждать именно этот пункт, включая ограничения примера. Непрошедший ответ не должен выдавать непроверенные пункты как обычный ответ.
5. Проведите 7 коротких обменов про `status`, `diff`, `add`, `commit`, `log`, `fetch`, `pull`, не повторяя имя ветки/запреты. Память должна сохранить их, хотя начальные реплики уже вне хвоста. Затем задайте вопрос по Git с зависимостью от ограничения; проверьте в диагностике память и новый retrieval.
6. Создайте B: никаких фактов из A. Оставьте черновик в A, переключитесь в B и обратно: тексты независимы. Обновите страницу: подтверждённые диалоги и локальные черновики восстанавливаются.
7. После завершения запросов перезапустите только backend через compose (без `down -v`), продолжите чат без повторного объяснения цели.
8. При сетевой ошибке используйте «Проверить и повторить»: сначала проверяется SQLite через GET, повтор — только с тем же requestId. Для надёжной имитации двойной сетевой ошибки используйте автоматические browser-тесты, а не удаляйте реальные данные.

## Границы решения

Локальное одноэкземплярное приложение без публичной авторизации, распределённых workers и неограниченной пагинации. Это осознанные границы, не скрытые обещания production-ready. LLM извлечения/проверки могут ошибаться; cosine — не вероятность истины. Публичный деплой, автоматическое обновление корпуса и миграция на другой vector store требуют отдельной задачи.
