Каждый день реализуется отдельно, проходит проверку и получает собственную ветку. День 21 не прячет в себе выполнение всех заданий недели. Старые Java/Python/MCP проекты остаются без изменений.

## День 21 — индексация

Ветка: `ai-challenge-day-21`, от дня 20 v2.

1. Изолированная папка `rag`, Kotlin Spring Boot и Vue/TypeScript, отдельные порты/volumes.
2. Русская Pro Git: закреплённый commit, 36 источников глав 2/3/7/10, manifest, лицензия и checksums.
3. Безопасная нормализация AsciiDoc и метаданные, не выполнение примеров команд.

5. Реальные локальные embeddings Ollama, проверка dimension/model/digest/truncation.
6. SQLite: jobs отдельно, atomic publish готового snapshot/index/chunks/vectors.
7. UI исходников, preview, progress/errors, сравнение и экспорт; диагностический cosine search.
8. Unit, fault, persistence и UI tests; измеренный отчёт, архитектурные документы и Archify.

Критерий готовности: обе стратегии построили готовые сохраняемые индексы одного корпуса и модели; доступны текст/метаданные/вектора, измеренное сравнение, поиск и проверка после restart. Coverage и размер корпуса подтверждены измерением, а не названием датасета. Результаты конкретного запуска — в `test-results.md`.

## День 23 — rewrite и второй этап retrieval

Реализовано в `ai-challenge-day-23`, от коммита дня 22 `07fa9b4`.

- Сохранить исходный вопрос и rewritten query отдельно; переформулировка не отвечает на вопрос.
- Контракты `QueryRewriter` и `CandidateSelector`; raw candidates и final candidates видны отдельно.
- Настройки `candidateTopK`, `finalTopK`, similarity threshold; контроль topK и отсечения.
- Сравнить baseline, filter, rewrite+filter на тех же контрольных вопросах, модели и корпусе.
- Начать с прозрачного similarity-фильтра, при необходимости добавить отдельный reranker. Его модель/версия входят в config эксперимента.
- Не выдавать cosine threshold за универсальную вероятность релевантности: подобрать его по примерам, включая нерелевантные вопросы.

Реализация: CandidateSelector с similarity-фильтром, QueryRewriter с проверяемым JSON, ExperimentService и общий AnswerGenerator, четыре режима и новый UI. RAW/FILTERED разделяют один пул, rewrite-режимы — второй; rewritten query не заменяет исходный вопрос генерации. NO_CONTEXT пропускает LLM, ошибки режимов изолированы. Наблюдение и экспорт включают shared rewrite, решения кандидатов, actual messages и общий расход без двойного учёта.

Проверки: 42 backend tests, 3 frontend unit tests, 9 обычных и 2 live браузерных теста, десять тройных сравнений и нерелевантные вопросы. ## День 24 — источники и проверяемые цитаты

Реализовано в `ai-challenge-day-24` от сохранённого дня 23 `6f7a581`.

- `GroundedAnswer`: ответ, ссылки на chunk IDs, точные цитаты и статус known/unknown.
- `CitationValidator`: каждый source ID только из переданного retrieval context; quote существует в сохранённом тексте.
- После проверки дословности отдельный `ClaimSupportValidator` проверяет поддержку каждого пункта его собственными цитатами, включая границы книжных примеров. Ручная оценка качества этой стадии остаётся необходимой.
- Слабый/пустой контекст → честное «не знаю» и просьба уточнить, а не домысливание источников.
- В UI цитата открывает snapshot документа нужного индекса, а не текущую изменённую книгу.
- 10 вопросов: presence, exactness и смысловая поддержка ответа фиксируются раздельно.

Текущая реализация: отдельный grounding domain/endpoint/UI, последовательность `ExactCitationValidator → ClaimSupportValidator`. Ответ собирается только после обеих проверок. Неверный ID, изменённая цитата, truncation, неподтверждённый смысл или противоречие закрывают весь ответ со статусом INVALID_EVIDENCE; ошибка провайдера проверки даёт ERROR. Координаты относятся к snapshot выбранного индекса. Gate пропускает генерацию при пустом отборе; JSON unknown позволяет отказаться при недостаточном непустом контексте. Retry нет.

Проверяющая модель получает только claims, их цитаты и окружающий текст цитируемых чанков, без эталонных ответов. Окружающий текст может выявить потерянное условие, но не заменить недостающую цитату. Для ANSWERED нужен `supportCheck.status=PASSED` и явный SUPPORTED по каждому пункту. Это модельная оценка связи с источником, не доказательство истинности самой книги.

Успешный ответ без rewrite использует две LLM-стадии, с rewrite — три. Проверка имеет технический лимит 2048 output tokens, не меняющий nullable лимит генерации пользователя. Usage, стоимость и trace проверки сохраняются отдельно и входят в общую сумму один раз. Каждый живой прогон получает новое имя отчёта с timestamp и run ID.

Первоначальный план ограничивал смысловую проверку ручной оценкой; это историческое решение пересмотрено после обнаружения настоящих цитат, не подтверждающих полный смысл утверждений. Текущие автоматические проверки: 76 backend tests passed и 1 live test skipped; 4 frontend unit tests и сборка прошли; 12 обычных Playwright tests passed. Живая смысловая приёмка ещё не закрыта. [Сверка и история плана](day24-plan-review.md), [гайд](day24-guide.md), [отчёт об исправлениях](day24-remediation.md), [исторические результаты до новой стадии](day24-test-results.md).

## День 25 — мини-чат с памятью задачи

Новая ветка от дня 24.

- Домены `conversations` и `taskmemory`, отдельное хранение history и task state.
- Каждый turn выполняет retrieval; история не заменяет поиск по книге.
- Task memory: цель, уточнения, ограничения/термины; обновления имеют источник и проверяемый формат.
- Историю и task state можно восстановить после restart; настройки/выбранный индекс сохраняются с чатом.
- Переполнение: явное управление budget, не тихое потерянное обрезание.
- Два сценария по 10–15 сообщений: восстановление ошибочного Git-коммита и выбор команд для совместной работы с ветками. Проверить цель, память, независимость чатов и источники на каждом ответе.
