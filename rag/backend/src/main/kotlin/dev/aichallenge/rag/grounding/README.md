Домен независимых вопросов с источниками. Не меняет AnswerService дня 22 и ExperimentService дня 23; переиспользует поиск, отбор, упаковку, LLM-порт и оценку стоимости. Контроллер не содержит поиск или разбор JSON.

## Ограниченное исправление и trace

Исправление ограничено одной видимой попыткой: только если первый черновик прошёл `ExactCitationValidator`, а первый `supportCheck.status` равен `REJECTED`, grounded-генератор Pro получает исходный запрос, те же переданные источники и feedback проверки. Новый вариант снова проходит дословную и смысловую проверку. Неверная форма JSON, транспортный сбой, truncation, UNKNOWN или ошибка ссылок эту попытку не запускают; после неуспеха исправления следующей попытки нет. Это отдельная стадия работы с содержанием, не HTTP retry и не неограниченный LLM-цикл.

Nullable поле `GroundedResult.repair` сохраняет первоначально отклонённый черновик: `originalGeneration` и `originalSupportCheck`. Основные поля `generation` и `supportCheck` относятся к последнему варианту. Публичные claims/sources появляются только у последнего варианта, прошедшего обе проверки; первоначальный черновик остаётся в свёрнутой диагностике **«Исправление черновика · 1 попытка»**. Старые результаты без `repair` читаются как прежде. Каждая фактически выполненная генерация и проверка входит в API usage/cost ровно один раз, в том числе сохранённые внутри `repair`; при неизвестном расходе стадии общий расход неизвестен.

## Пример алгоритма

Пользователь спрашивает про `stash -u`. По умолчанию SearchService получает до 20 кандидатов. CandidateSelector оставляет до 10 с score ≥ 0.60; PromptAssembler.select пропускает только целые чанки в бюджет 32000 символов. Значения видны и меняются в UI. Модель видит исходный вопрос и evidence с уникальными короткими адресами E1, E2… Она возвращает ссылки `{evidence_id}` и затем факт, а не перепечатывает цитаты. Это устраняет расхождения пробелов и переносов, не разрешая выдуманные доказательства.

Валидатор разрешает evidence_id только в EvidenceCatalog текущего включённого контекста, затем берёт исходный chunk и точный passage. Legacy `{chunk_id, span_index}` тоже разрешается только среди фактически переданных чанков. `canonicalStart = chunk.start + passage.start`. Источник создаётся из metadata чанка. Внешний `VerifiedCitation` не меняется: это точная цитата с координатами snapshot. Legacy `{chunk_id, quote}` остаётся для старых fixtures: допускается только точный substring 20–600 символов. Смешивание двух форм, неизвестные номера, дробные/строковые номера и дополнительные поля отклоняются. JSON с повторными ключами или вторым документом после первого тоже не проходит.

После успешной проверки точности `ClaimSupportValidator` отдельно проверяет смысл каждого пункта. Вход специально отличается от ответа: items содержат id, statement и evidence, source_context — тексты цитируемых чанков; выход — claims с вердиктами. Окружающий текст помогает обнаружить потерянные условия книжного примера, но не заменяет недостающую цитату. Ни история чата, ни другой пункт ответа не могут служить доказательством. Проверяющая модель возвращает ровно один результат с индексом на каждый пункт: обязательны `claim_index`, `conditions`, `verdict`, `reason`, `evidence_scope`, `claim_scope`. Оба scope принимают только `general` или `example`. Необязательные поля `text` и `citations` допустимы только как точное эхо исходных полей; они не могут исправлять текст или заменять доказательства. Остальные лишние поля, изменённое эхо, дубликаты индексов/JSON-ключей, пропуски, неизвестные вердикты/scope и обрезанный JSON отклоняются. Только PASSED по всем пунктам разрешает собрать публичный ответ.

Классификация области действия отделена от verdict. Если checker пометил доказательство `evidence_scope=example`, а утверждение — `claim_scope=general`, сервер заменяет его `supported` на `unsupported`. Обязательный массив `conditions` содержит до восьми ссылок `{chunk_id, span_index, preserved}` на предпосылки собственных цитируемых чанков. Неизвестные/чужие/повторные ссылки отклоняются; любой `preserved=false` тоже запрещает supported. Scope и preserved выбирает сама модель и тоже может ошибаться: код проверяет согласованность, а не доказывает правильность классификации. Поля остаются во внутреннем JSON/trace checker; публичные DTO не расширяются.

Если модель придумала ID, пересказала вместо цитирования или смысл итогового пункта не подтверждён после допустимого исправления, весь результат INVALID_EVIDENCE: claims/sources пусты. Такой же карантин действует при неправильном ответе проверяющей модели. Сбой изолированной проверки даёт INVALID_EVIDENCE без частичной публикации и без повторного HTTP-запроса. Если score слабый — UNKNOWN ещё до генерации. Если нет ответа в сильном контексте — модель возвращает unknown с пустыми claims и уточнением; проверка смысла тогда не вызывается. Если контекст не помещается — ERROR; это не отсутствие знания.

Проверяются 1–8 пунктов, текст до 1500 символов, 1–3 цитаты: references извлекают фрагмент до 1200 символов, legacy quote — точный substring 20–600 символов. JSON не может содержать дополнительные поля `answer`, source или metadata. `finish_reason != stop` не принимается независимо от того, выглядит ли фрагмент JSON законченно. HTTP retry и baseline fallback отсутствуют; разрешена только описанная ниже ограниченная правка содержательно отклонённого черновика.

Ответ без исправления использует генерацию и по одной LLM-проверке на каждый из 1–8 пунктов. Максимум с одной правкой — 18 вызовов без rewrite, 19 с rewrite. Checker сначала ищет обычный контрпример и потерянные условия, затем проверяет доказательства. Технические знания разрешены для опровержения, но не для поддержки отсутствующего в цитатах факта. Генератор вызывает `completeGroundedJson` с отдельным `groundingModel` (Pro, thinking high); checker — `completeVerifiedJson` с `supportModel` (Pro). По умолчанию support thinking включён с отдельным `supportReasoningEffort=high`; его можно выключить через `DEEPSEEK_SUPPORT_THINKING_ENABLED=false`. Точные параметры и результаты профиля фиксируются в отчёте. Обычные `complete`/`completeJson` дней 22–23 остаются на прежней конфигурации. Nullable лимит пользовательского ответа не меняется. Default-методы порта делегируют `completeJson` для совместимости test fakes.

Технический лимит checker — **16384 completion tokens, включая reasoning**. Транспорт берёт полное `completion_tokens` провайдера, не вычитая и не добавляя reasoning отдельно. `supportCheck.generation` и `additionalGenerations` в порядке пунктов сохраняют messages, финальный raw JSON из `content`, finish reason, usage и оценку стоимости даже при отклонении вердиктов; `reasoning_content` и ключ не сохраняются и не логируются. Сумма включает каждую выполненную стадию один раз; при неизвестном usage любой стадии общая сумма остаётся неизвестной. Транспортный сбой сохраняется как отдельная попытка с неизвестным usage. Остальные отправленные проверки не теряются и не считаются бесплатными. Для checker задан отдельный HTTP timeout 180 секунд (`DEEPSEEK_SUPPORT_TIMEOUT_SECONDS`); grounded-генератор имеет отдельный timeout 180 секунд; профиль сравнения дней 22–23 не меняется.

Отдельная модельная проверка снижает риск, но не доказывает истинность книги, полноту ответа или безошибочность проверяющей модели. Ручная оценка контрольных вопросов остаётся необходимой. `ExactCitationValidator` по-прежнему отвечает только за дословность; его успешный внутренний результат отдельно не разрешает публикацию. Новое nullable поле `supportCheck` по умолчанию null позволяет прочитать старые сохранённые результаты; наличие старого ANSWERED без этого поля не означает прохождение новой проверки.
