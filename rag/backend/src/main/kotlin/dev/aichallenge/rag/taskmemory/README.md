# Память задачи и подготовка вопроса

Этот домен хранит не знания о Git, а то, что пользователь сообщил о своей задаче. Например, «сохранить изменения», «коммит опубликован», «не использовать force push», «под основной веткой понимаем main».

TaskMemory хранится на backend в SQLite, отдельно от полной истории. Browser localStorage хранит только выбранный чат, черновики и receipt незавершённой отправки — он не восстанавливает и не подменяет память задачи. Новое сообщение попадает в extraction после серверного begin; повтор прежнего requestId возвращает сохранённый turn и не запускает повторное изменение памяти или LLM-вызов.

## Слои памяти

| Слой | Пример | Что не нужно сохранять |
| --- | --- | --- |
| GOAL | Исправить ошибочный коммит и сохранить правки | Каждый локальный вопрос вместо общей цели |
| CLARIFICATIONS | Коммит уже опубликован | Гипотетическое «а если он опубликован?» как свершившийся факт |
| CONSTRAINTS | Общую историю переписывать нельзя | Временное состояние коммита как неизменяемый запрет |
| TERMS | Рабочая ветка называется feature-login | Команды и советы из ответа модели |

## Классы и алгоритм

`DialoguePreparer` — заменяемый порт. `LlmDialoguePreparer` вызывает существующий LlmClient в JSON mode, без собственного output cap, с отдельным system prompt. В его входе current question, validated memory и ограниченный recent dialogue; книги здесь нет. Он не отвечает пользователю и не выполняет инструментов.

Подготовка памяти по-прежнему использует один LLM-вызов. Весь обмен Day25 использует до трёх: подготовка, генерация grounded-ответа и отдельная проверка поддержки его пунктов цитатами. Проверка смысла получает книжные доказательства, а не TaskMemory, и не является дополнительной проверкой полноты extraction. Память, валидно извлечённая из пользователя, сохраняется и при UNKNOWN, отклонении grounded-ответа или ошибке его генерации.

Ожидаемый JSON содержит `query`, `inventory`, `updates` и `removals`. Query раскрывает местоимения для retrieval, но не заменяет original question в истории. Update задаёт layer/key/value/quote. SourceTurnId всегда назначается сервером, модель не может сослаться на произвольный чат или assistant response.

Модель сначала перечисляет в `inventory` явно сообщённые в текущем вопросе цель, ситуацию, **каждое независимое ограничение** и назначенные имена. «Назовём ветку …» автоматически сохраняет TERMS: отдельное слово «запомни» не нужно. Вопрос вместе с новой договорённостью не является поводом пропустить память. Близкие запреты, например force push и любое переписывание общей истории, не считаются одинаковыми.

Каждый элемент inventory получает действие:

- `UPSERT`: `layer/key/value/quote` обязаны точно соответствовать одному update;
- `REMOVE`: `value=null`, остальные поля точно соответствуют одному removal;
- `RETAIN`: существующие `layer/key` и **точное прежнее value**, без изменения. Это повтор уже известного факта, не новый похожий факт.

Сервер проверяет соответствие в обе стороны: обнаруженный факт нельзя молча выбросить, а изменение нельзя применить без inventory. Inventory хранится в `rawJson` диагностического trace; отдельный API DTO не добавлен, старые сохранённые диалоги читаются как прежде. Production-вызов обязательно требует новый контракт. Опциональный параметр `requireInventory` у валидатора существует только для совместимости низкоуровневых старых patch-кейсов; `LlmDialoguePreparer` всегда передаёт `true`.

`MemoryPatchValidator` проверяет finish_reason, размер, точную структуру, bounded fields, допустимый enum, одинаковые ключи и наличие каждой quote в текущем вопросе. При ошибке весь patch отвергается. Сервер применяет upsert по layer/key, поэтому новое значение того же факта заменяет старое, а не дублируется. Удалять можно только существующий ключ с цитатой текущего сообщения. Не более 20 изменений за turn и 12 записей каждого слоя (GOAL одна); переполнение — явная ошибка, не тайное вытеснение памяти.

После первого GOAL изменения этого слоя без явного префикса «Новая цель:», «Измени цель:» или «Моя новая цель:» не применяются. В новом production-контракте inventory с запрещённой заменой не может быть полностью покрыт, поэтому отвергается **вся подготовка**, без изменения памяти и без генерации ответа. Локальное пожелание должно попадать в CLARIFICATIONS, а не заменять цель. Исходное предложение модели остаётся в rawJson. Переименование или изменённая ситуация используют прежний ключ; другой ключ с тем же значением не создаёт дубликат. Явная отмена удаляет только названную существующую запись.

## Пример

User: «Нельзя терять изменения. Что делает reset --soft?»

```json
{"query":"Что делает git reset --soft с изменениями?","inventory":[{"action":"UPSERT","layer":"CONSTRAINTS","key":"preserve_changes","value":"Не терять изменения","quote":"Нельзя терять изменения."}],"updates":[{"layer":"CONSTRAINTS","key":"preserve_changes","value":"Не терять изменения","quote":"Нельзя терять изменения."}],"removals":[]}
```

Сервер добавляет sourceTurnId текущего user message. На следующем шаге «А что станет с индексом?» query может стать «Что делает reset --soft с индексом Git?», а inventory и оба массива patch быть пустыми. Память при этом сохраняется полностью; это не summary диалога.

Точное совпадение quote доказывает происхождение строки, но не семантическую эквивалентность value. Inventory и patch создаёт **одна LLM**, поэтому согласованный пропуск факта в обоих массивах не обнаруживается структурным валидатором. Это усиление extraction-контракта и проверяемости, а не гарантия идеальной памяти. Нового платного reviewer-вызова нет. Prompt запрещает гипотезы и чужие инструкции; это не математическая гарантия защиты от всех prompt injection. При критичных правилах потребуется отдельное подтверждение пользователя или специализированная validation policy.

## Проверка полноты

`MemoryCompletenessTest` проверяет связность inventory/patch, ложный RETAIN, переименование, отмену, защиту цели, запрет происхождения из assistant/старого сообщения и сохранение фактов за пределами шести обменов после перезапуска SQLite. Предложения LLM в unit-тестах — fixtures: они не доказывают качество реального извлечения.

Для реальной модели `evaluation/day25-scenarios.json` задаёт ожидания по памяти **на каждом последующем шаге**, включая имя из сообщения 2 и новое независимое ограничение из сообщения 11. `scripts/verify-day25.ps1` проверяет эти ожидания и provenance, а не только одну цель. Каждый новый запуск создаёт timestamp-отчёт; `-Phase Continue -ReportPath <путь>` продолжает конкретную проверку после перезапуска, не затирая прошлые доказательства. Для дополнительной ручной проверки используйте другое имя, затем исправьте его и явно отмените одно ограничение; после 7+ обменов проверьте, что остались новое имя и остальные правила, а не противоречивые старые значения.
