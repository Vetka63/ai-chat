# Память задачи и подготовка вопроса

Этот домен хранит не знания о Git, а то, что пользователь сообщил о своей задаче. Например, «сохранить изменения», «коммит опубликован», «не использовать force push», «под основной веткой понимаем main».

TaskMemory хранится на backend в SQLite, отдельно от полной истории. Browser localStorage хранит только выбранный чат, черновики и receipt незавершённой отправки — он не восстанавливает и не подменяет память задачи. Новое сообщение попадает в extraction после серверного begin; повтор прежнего requestId возвращает сохранённый turn и не запускает повторное изменение памяти или LLM-вызов.

## Слои памяти

| Слой | Пример | Что не нужно сохранять |
| --- | --- | --- |
| GOAL | Исправить ошибочный коммит и сохранить правки | Каждый локальный вопрос вместо общей цели |
| CLARIFICATIONS | Коммит уже опубликован | Гипотетическое «а если он опубликован?» как свершившийся факт |
| CONSTRAINTS | Общую историю переписывать нельзя | Временное состояние коммита как неизменяемый запрет |
| TERMS | Рабочая ветка называется feature-login | Команды и советы из ответа модели |

## Классы и алгоритм

`DialoguePreparer` — заменяемый порт. `LlmDialoguePreparer` вызывает отдельный метод `LlmClient.completePreparationJson` с собственным system prompt. DeepSeek использует настраиваемый профиль подготовки: по умолчанию `deepseek-v4-pro`, thinking enabled, effort `high`, HTTP timeout 180 секунд. Переменные `DEEPSEEK_PREPARATION_MODEL`, `DEEPSEEK_PREPARATION_REASONING_EFFORT`, `DEEPSEEK_PREPARATION_TIMEOUT_SECONDS` независимы от обычной генерации и смыслового checker. Технический cap подготовки — 16384 токена на JSON вместе с reasoning; он не меняет пользовательский лимит ответа. В входе current question, validated memory и ограниченный recent dialogue; книги здесь нет. Подготовка не отвечает пользователю и не выполняет инструментов. Фактические модель, finish reason, usage и стоимость записываются в PreparationTrace; reasoning-текст не публикуется. Старые адаптеры и unit fixtures по умолчанию делегируют новый метод своему `completeJson`.

Подготовка памяти использует один LLM-вызов. Весь обмен Day25 использует до пяти: подготовка, генерация grounded-ответа, проверка поддержки и при смысловом отказе одна попытка исправления с повторной проверкой. Проверка смысла получает книжные доказательства, а не TaskMemory, и не является дополнительной проверкой полноты extraction. Память, валидно извлечённая из пользователя, сохраняется и при UNKNOWN, отклонении grounded-ответа или ошибке его генерации.

Ожидаемый JSON содержит `query`, `inventory`, `updates` и `removals`. Query раскрывает местоимения для retrieval, но не заменяет original question в истории. Update задаёт layer/key/value/quote. SourceTurnId всегда назначается сервером, модель не может сослаться на произвольный чат или assistant response.

В ограниченном хвосте каждый обмен содержит исходный `user`, допущенный `assistant` (либо `null`) и nullable `resolvedQuestion` — query предыдущей подготовки, если она прошла проверку. Поэтому короткое продолжение сохраняет предмет даже после отклонённого grounded-ответа. Подготовка с issues не добавляет resolvedQuestion; отклонённый ответ не передаётся. Все три текста входят в общий лимит символов истории, обмены сохраняются целиком. Предыдущая формулировка помогает раскрыть ссылку, но не подтверждает знания о Git, не становится цитатой пользователя и не создаёт факты памяти. Явная смена операции в текущем вопросе имеет приоритет, а просьба о другом режиме не закрепляет прежний режим.

Модель сначала перечисляет в `inventory` явно сообщённые в текущем вопросе цель, ситуацию, **каждое независимое ограничение** и назначенные имена. «Назовём ветку …» автоматически сохраняет TERMS: отдельное слово «запомни» не нужно. Вопрос вместе с новой договорённостью не является поводом пропустить память. Близкие запреты, например force push и любое переписывание общей истории, не считаются одинаковыми.

Каждый элемент inventory получает действие:

- `UPSERT`: `layer/key/value/quote` обязаны точно соответствовать одному update;
- `REMOVE`: `layer/key/quote` точно соответствуют одному removal. В inventory REMOVE и в `removals` поле `value` можно независимо опустить или передать только `null`: все четыре сочетания означают одно удаление. В patch поле `action` и другие лишние поля запрещены;
- `RETAIN`: предпочтительна краткая ссылка `{action:"RETAIN",layer,key}` на ровно один существующий факт, без изменения. `value` и `quote` необязательны независимо друг от друга. Если `value` передан, требуется точное прежнее значение без нормализации; если `quote` передана, она должна быть непустым дословным фрагментом текущего вопроса. Неизвестный layer/key, лишние поля и неверные значения отклоняются. Существующие quote/sourceTurnId факта при RETAIN не меняются; повторное сохранение не создаёт новое происхождение. RETAIN не может сопровождаться изменением того же ключа в updates/removals.

Сервер проверяет соответствие в обе стороны: обнаруженный факт нельзя молча выбросить, а изменение нельзя применить без inventory. Inventory хранится в `rawJson` диагностического trace; отдельный API DTO не добавлен, старые сохранённые диалоги читаются как прежде. Production-вызов обязательно требует новый контракт. Опциональный параметр `requireInventory` у валидатора существует только для совместимости низкоуровневых старых patch-кейсов; `LlmDialoguePreparer` всегда передаёт `true`.

`MemoryPatchValidator` проверяет finish_reason, размер, точную структуру, bounded fields, допустимый enum, одинаковые ключи и наличие каждой переданной quote в текущем вопросе. Единственное исключение по обязательности quote — RETAIN без изменения уже существующего факта. Для UPSERT/REMOVE в inventory и соответствующих updates/removals quote по-прежнему обязательна, проверяется дословно и должна совпасть между inventory и patch. Это не разрешает создавать, менять или удалять факт по старому сообщению. Лишние поля и неподходящие типы отклоняются; при ошибке весь patch отвергается. Сервер применяет upsert по layer/key, поэтому новое значение того же факта заменяет старое, а не дублируется. Удалять можно только существующий ключ с цитатой текущего сообщения. Не более 20 изменений за turn и 12 записей каждого слоя (GOAL одна); переполнение — явная ошибка, не тайное вытеснение памяти.

После первого GOAL изменения этого слоя без явного префикса «Новая цель:», «Измени цель:» или «Моя новая цель:» не применяются. В новом production-контракте inventory с запрещённой заменой не может быть полностью покрыт, поэтому отвергается **вся подготовка**, без изменения памяти и без генерации ответа. Локальное пожелание должно попадать в CLARIFICATIONS, а не заменять цель. Исходное предложение модели остаётся в rawJson. Переименование или изменённая ситуация используют прежний ключ; другой ключ с тем же значением не создаёт дубликат. Явная отмена удаляет только названную существующую запись.

## Пример

User: «Нельзя терять изменения. Что делает reset --soft?»

```json
{"query":"Что делает git reset --soft с изменениями?","inventory":[{"action":"UPSERT","layer":"CONSTRAINTS","key":"preserve_changes","value":"Не терять изменения","quote":"Нельзя терять изменения."}],"updates":[{"layer":"CONSTRAINTS","key":"preserve_changes","value":"Не терять изменения","quote":"Нельзя терять изменения."}],"removals":[]}
```

Сервер добавляет sourceTurnId текущего user message. На следующем шаге «А что станет с индексом?» query может стать «Что делает reset --soft с индексом Git?», а inventory и оба массива patch быть пустыми. Память при этом сохраняется полностью; это не summary диалога.

Точное совпадение quote доказывает происхождение строки, но не семантическую эквивалентность value. Inventory и patch создаёт **одна LLM**, поэтому согласованный пропуск факта в обоих массивах не обнаруживается структурным валидатором. Это усиление extraction-контракта и проверяемости, а не гарантия идеальной памяти. Нового платного reviewer-вызова нет. Prompt запрещает гипотезы и чужие инструкции; это не математическая гарантия защиты от всех prompt injection. При критичных правилах потребуется отдельное подтверждение пользователя или специализированная validation policy.

Подготовка отличает утверждение текущей ситуации перед вопросом от условия будущего действия. Например, сообщение о уже выполненной доставке сохраняет факт, а вопрос «как проверить после доставки?» сам по себе не доказывает, что она произошла. Явная ситуация в самостоятельном вопросе не должна теряться только потому, что query уже понятен. Более сильный профиль не заменяет эти правила и не гарантирует их соблюдение; целевые live-проверки остаются обязательным свидетельством качества.

## Проверка полноты

`MemoryCompletenessTest` проверяет связность inventory/patch, ложный RETAIN, переименование, отмену, защиту цели, запрет происхождения из assistant/старого сообщения и сохранение фактов за пределами шести обменов после перезапуска SQLite. Предложения LLM в unit-тестах — fixtures: они не доказывают качество реального извлечения.

`MemoryPreparationLiveTest` включается только через `RAG_RUN_LIVE_MEMORY=true` при наличии серверного ключа. Он выполняет ровно пять подготовок через production-метод: извлечение, переименование, отмену, текущую ситуацию C9 и условный вопрос C12. Используются исключительно открытый `day25-scenarios.json` и искусственные literals памяти/шестишаговой истории с `assistant=null`: это синтетическая регрессия, НЕ replay реального trace. Тест не читает пользовательские чаты, SQLite или runtime traces, не запускает retrieval, ответы, judge или retries. Каждый запуск заранее создаёт уникальный timestamp/UUID JSON в `data/memory-preparation-live-*.json`, сохраняет результат перед assertions и не удаляет неудачные отчёты. Модель задаётся теми же `DEEPSEEK_PREPARATION_*`, а не подменой модели ответа.

Для реальной модели `evaluation/day25-scenarios.json` задаёт ожидания по памяти **на каждом последующем шаге**, включая имя из сообщения 2 и новое независимое ограничение из сообщения 11. `scripts/verify-day25.ps1` проверяет эти ожидания и provenance, а не только одну цель. Каждый новый запуск создаёт timestamp-отчёт; `-Phase Continue -ReportPath <путь>` продолжает конкретную проверку после перезапуска, не затирая прошлые доказательства. Для дополнительной ручной проверки используйте другое имя, затем исправьте его и явно отмените одно ограничение; после 7+ обменов проверьте, что остались новое имя и остальные правила, а не противоречивые старые значения.
