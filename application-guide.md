# Как устроено приложение AI Chat

Этот документ описывает активную связку Vue + Java Spring Boot. Параллельный
Python/FastAPI-проект сохранён в `ai-chat-backend-python`, но Docker Compose
сейчас запускает именно Java backend.

## Состав проекта

| Путь | Назначение |
|---|---|
| `ai-chat-client` | Vue 3 интерфейс чата |
| `ai-chat-backend` | Java 21 + Spring Boot API |
| `ai-chat-backend-python` | Параллельная версия backend на Python |
| `docker-compose.yml` | Совместный запуск frontend и Java backend |
| `.env` | Локальные секреты и режим запуска, не попадает в Git |
| `.env.example` | Безопасный пример переменных окружения |

## Общая схема работы

```text
Браузер
  │
  │ GET /api/profiles, POST /api/chat
  ▼
Vue (App.vue)
  │
  │ в Docker запрос проходит через Nginx
  ▼
Spring REST Controller
  ▼
ChatService
  ├─ AgentRegistry: выбирает YAML-профиль
  ├─ InputPolicy: проверяет ввод и собирает messages
  ├─ RequestGuard: классифицирует допустимость запроса
  ├─ DeepSeekClient: вызывает /chat/completions
  └─ OutputPolicy: проверяет и преобразует ответ
  ▼
JSON-ответ backend
  ▼
Vue показывает текст или карточку рецепта
```

Системный промпт, API-ключ и внутренние инструкции режима остаются на сервере.
Клиент передаёт только выбранные `profileId`, `responseMode`, новое сообщение и
разрешённую историю диалога.

## Что происходит при открытии страницы

1. `ai-chat-client/src/App.vue` монтирует Vue-приложение.
2. `getChatProfiles()` из `ai-chat-client/src/api/chat.js` вызывает
   `GET /api/profiles`.
3. `AgentController` возвращает только публичные поля профилей: идентификатор,
   название, описание и доступные режимы ответа.
4. Vue заполняет два переключателя: «Профиль» и «Контроль ответа».
5. Для каждой пары профиль + режим хранится отдельная история в памяти страницы.
   После обновления страницы эта история очищается.

## Что происходит при отправке сообщения

### 1. Vue формирует запрос

`ai-chat-client/src/App.vue` собирает объект:

```json
{
  "message": "Дай рецепт борща",
  "profileId": "recipe",
  "responseMode": "json",
  "history": []
}
```

`sendChatMessage()` отправляет его методом `POST` в `/api/chat`.

### 2. Контроллер проверяет форму запроса

`ChatController` проверяет, что сообщение не пустое, идентификаторы имеют
допустимый формат, а история не превышает общий верхний предел. Из браузера
разрешены только роли `user` и `assistant`: клиент не может прислать собственное
сообщение с ролью `system`.

### 3. Backend выбирает профиль и режим

`ChatService` получает профиль через `AgentRegistry`. Профили загружаются при
старте приложения из `ai-chat-backend/src/main/resources/agents/*.yml`.

Сейчас доступны:

- `general` — обычный универсальный чат;
- `recipe` — кулинарный профиль;
- архитектура допускает добавление новых YAML-профилей.

Если `profileId` или `responseMode` неизвестен, backend возвращает ошибку и не
делает запрос к DeepSeek.

### 4. InputPolicy собирает сообщения для LLM

`InputPolicy`:

1. Проверяет длину нового сообщения и истории по правилам выбранного профиля.
2. Первым добавляет закрытый серверный `system_prompt`.
3. Добавляет к нему `instruction` выбранного режима ответа.
4. После этого добавляет разрешённую историю.
5. Последним добавляет новое пользовательское сообщение.

Именно поэтому пользователь может выбрать готовый профиль, но не может
подменить его системный промпт через API.

### 5. RequestGuard классифицирует запрос рецепта

Если в профиле настроен `request_guard`, `RequestGuardRegistry` выбирает его по
полю `type`. В профиле `recipe` используется `RecipeIntentRequestGuard`.

В режиме `CHAT_MODE=llm` этот guard делает отдельный запрос к DeepSeek со своей
закрытой инструкцией. Для этого простого решения JSON и DTO не используются:
модель должна вернуть один уникальный маркер:

```text
[[ALLOW_RECIPE]]
```

Классификатор получает проверенную историю разговора, поэтому может разрешить
продолжение вроде «А теперь сделай на четыре порции», если ранее обсуждалось
конкретное блюдо.

Возможны четыре решения:

- `[[ALLOW_RECIPE]]` — рецепт блюда или продолжение разговора о нём;
- `[[REJECT_NOT_FOOD]]` — самолёт, автомобиль или другой несъедобный объект;
- `[[REJECT_UNRELATED]]` — погода или другая посторонняя тема;
- `[[REJECT_UNCLEAR]]` — название блюда определить невозможно.

Три отклоняющих маркера останавливают обработку до генерации рецепта.
Backend возвращает HTTP 422 с серверным сообщением:

```json
{
  "error": "Укажите существующее съедобное блюдо, для которого нужен рецепт."
}
```

или:

```json
{
  "error": "Профиль рецептов принимает только запросы о приготовлении блюд."
}
```

Vue показывает поле `error` отдельным сообщением в чате. Пользователь сразу
видит, что именно нужно исправить во входном запросе. Само пользовательское
сообщение остаётся на экране, но получает внутренний признак `historyExcluded`
и больше не включается в последующие запросы к LLM.

Java ищет маркеры регулярным выражением. Дополнительный поясняющий текст не
мешает, если в ответе найден ровно один известный маркер. Отсутствие маркера или
несколько различных маркеров запускают одну повторную классификацию с усиленной
инструкцией формата.
Если второй ответ также некорректен, генератор не запускается, а backend
возвращает HTTP 502:

```json
{
  "error": "Не удалось проверить, является ли запрос рецептом. Повторите запрос."
}
```

Guard всегда записывает номер попытки, принятое решение или безопасную причину,
например `verdict marker is missing` или `multiple verdict markers found`.

Классификация является семантической оценкой LLM, а не проверкой по полному
мировому справочнику блюд. Она надёжно отделяет погоду или автомобиль от еды,
но для абсолютной гарантии существования блюда понадобился бы отдельный
контролируемый каталог.

В `CHAT_MODE=fallback` внешний классификатор пропускается, потому что этот режим
предназначен для локальной проверки интерфейса без вызовов DeepSeek.

### 6. DeepSeekClient вызывает модель

После успешной классификации класс `DeepSeekClient` отправляет запрос в
`{LLM_BASE_URL}/chat/completions`. В запрос попадают:

- модель из профиля или `LLM_MODEL`;
- подготовленный массив `messages`;
- параметры профиля: `thinking`, `reasoning_effort`, `temperature`, `top_p`;
- параметры режима: `max_tokens`, `stop`, `response_format`.

Каждому обращению присваивается `callId`. Обычные INFO-логи показывают профиль,
операцию (`request-guard`, `json`, `free`), модель, количество сообщений,
ограничения, результат завершения и длину ответа. Это позволяет связать начало
и конец конкретного обращения.

При `LLM_LOG_PAYLOADS=true` дополнительно записываются сериализованный запрос и
сырой HTTP-ответ DeepSeek. В них видны системный промпт, история, сообщение
пользователя, параметры и фактический ответ модели. Заголовок `Authorization` и
API-ключ не журналируются. Поскольку пользовательский текст может быть
чувствительным, этот режим предназначен для локальной отладки и по умолчанию
выключен.

Ключ берётся из `LLM_API_KEY`. Он не включается в ответ API и не передаётся во
frontend.

В режиме `CHAT_MODE=fallback` внешний вызов не выполняется. `ChatService`
возвращает локальный тестовый ответ той же формы, чтобы интерфейс можно было
проверять без API-ключа.

Обычно разрешённый запрос использует два последовательных обращения: одно для
классификации и одно для генерации. При восстановительном повторе возможны три
обращения. Корректно отклонённый запрос использует только классификацию, а при
нарушении схемы классификатора — не более двух попыток без генерации.

### 7. OutputPolicy контролирует результат

После ответа DeepSeek `ChatService` выбирает политику из
`OutputPolicyRegistry`:

- `text` — возвращает обычный текст;
- `answer-json` — проверяет JSON универсального чата;
- `recipe-json` — проверяет строгую структуру рецепта.

Для структурированных режимов `ChatService` проверяет `finishReason` и результат
`OutputPolicy`. Если DeepSeek завершил ответ по `length` либо вернул JSON, который
не проходит схему, backend делает одну восстановительную попытку. Для неё
увеличивается `max_tokens` и добавляется числовое требование к компактности.
В логах такие вызовы имеют операцию `json-retry`.

В универсальном режиме `answer-json` поле `answer` ограничено 500 символами.
Если модель вернула валидный JSON с более длинным значением, backend безопасно
сокращает строку и добавляет `...`; наружу всё равно выходит валидный DTO и JSON.

Для рецепта используется `RecipeJsonOutputPolicy`. Он десериализует ответ в
Java record и требует ровно такую схему:

```json
{
  "dishName": "Борщ",
  "requiredIngredients": [
    "Говядина — 500 г",
    "Свёкла — 2 шт.",
    "Капуста — 300 г"
  ],
  "cookingTime": "1 час 30 минут"
}
```

Проверяются следующие условия:

- все три поля присутствуют;
- `dishName` и `cookingTime` являются непустыми строками;
- `requiredIngredients` является непустым массивом непустых строк;
- неизвестные дополнительные поля запрещены.

Если модель вернула другой JSON, backend сначала выполняет одну восстановительную
попытку. HTTP 502 возвращается только тогда, когда повторный ответ тоже невозможно
десериализовать или он снова не соответствует обязательной схеме.

Параметр DeepSeek `response_format: {"type":"json_object"}` помогает получить
валидный JSON, инструкция в `recipe.yml` описывает нужную схему, а Java-политика
независимо проверяет фактический результат. Это три разных уровня контроля.

### 8. Vue отображает результат

Backend возвращает общий конверт:

```json
{
  "reply": "Борщ",
  "structuredReply": {
    "dishName": "Борщ",
    "requiredIngredients": ["Свёкла — 2 шт."],
    "cookingTime": "1 час 30 минут"
  },
  "source": "llm",
  "profileId": "recipe",
  "responseMode": "json",
  "meta": {
    "model": "deepseek-v4-flash",
    "finishReason": "stop",
    "maxTokens": 1000,
    "responseFormat": "json_object",
    "stop": null
  }
}
```

`App.vue` распознаёт три поля внутри `structuredReply` и показывает карточку:

```text
Название блюда: Борщ
Требуемые ингредиенты:
- Свёкла — 2 шт.
Время готовки: 1 час 30 минут
```

Стабильной является схема и типы полей. Состав ингредиентов и время могут
различаться между вызовами: это генерируемое моделью содержимое. Для уменьшения
вариативности у профиля `recipe` установлена `temperature: 0.0`.

## Как читать recipe.yml

Файл `ai-chat-backend/src/main/resources/agents/recipe.yml` содержит:

| Поле | Что делает |
|---|---|
| `id`, `name`, `description`, `version` | Идентификация и описание профиля |
| `enabled` | Загружать ли профиль при старте |
| `system_prompt` | Закрытая постоянная роль кулинарного помощника |
| `input_policy` | Лимиты сообщения, истории и разрешённые роли |
| `request_guard` | Тип, инструкция и лимит токенов входного классификатора |
| `deepseek` | Параметры модели для всего профиля |
| `default_response_mode` | Режим, если клиент его не передал |
| `response_modes` | Доступные варианты управления ответом |
| `instruction` | Дополнение к системному промпту для конкретного режима |
| `output_policy` | Имя Java-проверки результата |
| `max_tokens` | Максимальный размер ответа модели |
| `stop` | Последовательность принудительной остановки |
| `response_format` | Требование JSON-объекта от DeepSeek |

Профиль загружается из ресурсов внутри JAR при старте. После изменения YAML при
Docker-запуске нужно пересобрать backend-образ.

## Docker и сетевые адреса

`docker-compose.yml` запускает два контейнера:

- `client`: Nginx + собранный Vue, доступен на `http://localhost:8080`;
- `backend`: Spring Boot, доступен напрямую на `http://localhost:8081`.

В браузере Vue обращается к относительному адресу `/api`. Nginx из
`ai-chat-client/nginx.conf` пересылает эти запросы контейнеру
`http://backend:8080`. Поэтому секретные данные не нужны в frontend.

Запуск или пересборка после изменения кода/YAML:

```powershell
docker compose up -d --build
```

Только перечитать изменённый `.env` без пересборки образов:

```powershell
docker compose up -d --force-recreate backend
```

Посмотреть состояние:

```powershell
docker compose ps
```

Посмотреть логи Java backend:

```powershell
docker compose logs -f backend
```

Остановить приложение:

```powershell
docker compose down
```

## Секреты и локальная конфигурация

`.env` предназначен для локальных значений:

```dotenv
CHAT_MODE=llm
LLM_BASE_URL=https://api.deepseek.com
LLM_API_KEY=ваш_ключ
LLM_MODEL=deepseek-v4-flash
LLM_LOG_PAYLOADS=true
```

`.gitignore` исключает `.env` из Git. В `.env.example` должны находиться только
названия настроек и безопасные примеры без настоящего ключа.

В текущем локальном `.env` подробное логирование включено. Смотреть поток:

```powershell
docker compose logs -f backend
```

## Проверка без интерфейса

Получить список профилей:

```powershell
Invoke-RestMethod http://localhost:8081/api/profiles
```

Запросить строгий рецепт:

```powershell
$body = @{
  profileId = 'recipe'
  responseMode = 'json'
  message = 'Дай рецепт борща'
  history = @()
} | ConvertTo-Json

Invoke-RestMethod `
  -Method Post `
  -Uri http://localhost:8081/api/chat `
  -ContentType 'application/json' `
  -Body $body
```

## Тесты

Java:

```powershell
cd ai-chat-backend
.\mvnw.cmd test
```

Основные проверки находятся в:

- `RecipeJsonOutputPolicyTest` — принятие правильной схемы и отказ при ошибке;
- `RecipeIntentRequestGuardTest` — блюдо, посторонняя тема, несъедобный объект и ошибочный ответ классификатора;
- `ChatServiceTest` — параметры запроса к DeepSeek и преобразование ответа;
- `ChatControllerTest` — HTTP API, профили, режимы и fallback.

Vue:

```powershell
cd ai-chat-client
pnpm test
pnpm build
```

`App.test.js` проверяет выбранный режим, тело API-запроса и отображение карточки
строгого рецепта.

## Как добавить новый профиль

Для обычного текстового профиля можно скопировать `general.yml`, задать новый
уникальный `id`, системный промпт и режимы. После перезапуска он автоматически
появится в `GET /api/profiles` и в Vue.

Если новый профиль требует собственной строгой JSON-схемы, дополнительно нужны:

1. Новый класс, реализующий `OutputPolicy`.
2. Уникальное значение, возвращаемое методом `type()`.
3. Такое же значение в `output_policy` YAML-режима.
4. Тесты правильного и неправильного ответа.
5. При необходимости — отдельное представление `structuredReply` во Vue.

Так YAML управляет промптингом и параметрами, а Java-код обеспечивает строгий
контракт и не доверяет формату, сгенерированному LLM.
