# LLM

Модуль изолирует приложение от конкретного API модели.

`LlmClient` принимает только `LlmCompletionRequest`: сообщения, параметры
генерации и диагностические идентификаторы. Он не зависит от `AgentProfile` и
заданий челленджа. `deepseek/DeepSeekClient` преобразует этот контракт в
DeepSeek `/chat/completions`, а `mistral/MistralClient` — в Mistral Chat
Completions. Оба адаптера нормализуют provider usage в `LlmUsage`.

Для сценариев с несколькими провайдерами существует `LlmProviderClient`.
`LlmProviderRegistry` выбирает его по enum `LlmProvider`. `DeepSeekClient`
одновременно реализует прежний `LlmClient`, поэтому существующие задачи не
требуют миграции. Новый провайдер добавляется отдельным адаптером и одной записью
enum, без зависимости `common` от конкретного учебного дня.

`AgentLlmRequestFactory` обычно переносит настройки выбранного YAML-профиля в
`LlmCompletionRequest`. Если только одному вызову нужны другие параметры,
прикладной сервис передаёт `LlmRequestOverrides`. Например, День 4 трижды меняет
только `temperature`, а судья Дня 3 выбирает отдельную модель. `null` в override
означает «оставить значение профиля».

`AggregateLlmMetrics` суммирует токены, длительность API и стоимость нескольких
вызовов. Стоимость считается только для модели, к которой относится глобальная
конфигурация цен. При разовом переключении на другую модель поле
`estimatedCostUsd` остаётся `null`, чтобы не показывать неверную сумму.

День 5 применяет собственный каталог цен после вызова, потому что в одном
эксперименте участвуют разные модели и провайдеры. Provider DTO остаются
внутренней деталью соответствующего адаптера.
