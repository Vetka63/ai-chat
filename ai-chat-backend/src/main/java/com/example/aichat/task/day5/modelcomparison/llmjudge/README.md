# LLM-судья сравнения моделей

Пакет оценивает качество ответов Дня 5 отдельным вызовом `deepseek-v4-pro`.
Судья запускается только по явному действию пользователя после получения как
минимум двух успешных ответов. Поэтому стоимость оценки видна отдельно и не
смешивается со стоимостью основного эксперимента.

## Поток запроса

```text
POST /api/model-comparisons/judge
  -> ModelComparisonJudgeController
  -> LlmJudgeRegistry
  -> ModelComparisonJudgeService
       -> проверка профиля, задачи и modelId
       -> сортировка вариантов в порядке конфигурации
       -> замена вариантов на A, B, C
       -> DeepSeek Pro с response_format=json_object
       -> проверка JSON и оценок
       -> обратное сопоставление A/B/C с вариантами
  -> ModelComparisonJudgeResult
```

`ModelComparisonJudgeController` преобразует HTTP DTO во внутреннюю команду.
Общий `LlmJudgeRegistry` находит реализацию по типу
`day5-model-comparison`. `ModelComparisonJudgeService` не принимает от клиента
названия или параметры моделей: допустимые идентификаторы берутся из YAML.

## Независимость оценки

До вызова LLM ответы сортируются в стабильном порядке и обезличиваются:

```json
{
  "task": "Объясни бинарный поиск",
  "candidates": [
    {"candidate": "A", "answer": "..."},
    {"candidate": "B", "answer": "..."},
    {"candidate": "C", "answer": "..."}
  ]
}
```

В запрос не входят названия `Mistral`, `DeepSeek`, уровни «слабая/сильная»,
время, токены и стоимость. Это уменьшает предвзятость по бренду и мощности.
Полностью исключить смещение нельзя: DeepSeek Pro оценивает в том числе ответ,
созданный той же моделью. Поэтому результат судьи — дополнительная экспертная
оценка, а не объективная истина; ручной выбор пользователя сохраняется рядом.

## Критерии и результат

Каждый ответ получает целые баллы от 0 до 10:

- `accuracy` — фактическая и логическая точность;
- `instructionFollowing` — соблюдение требований исходной задачи;
- `completeness` — полнота без существенных пропусков;
- `clarity` — ясность и структура.

Backend самостоятельно рассчитывает среднее значение. Провайдер выбирает
`winner` только среди переданных кодов и возвращает `summary` на 2–4 предложения.
Для каждой оценки обязательны непустые сильные и слабые стороны.

## Устойчивость и стоимость

Ответ запрашивается как `json_object` и затем строго проверяется Java-кодом.
Проверяются JSON, число evaluations, уникальность кандидатов, диапазон баллов,
победитель и текстовые поля. При повреждённом или обрезанном JSON выполняется
одна повторная попытка с увеличенным лимитом. После исчерпания попыток endpoint
возвращает `502`; исходные три ответа на клиенте при этом остаются доступны.

Метрики учитывают все попытки судьи. `ModelCostCalculator` применяет тариф
`deepseek-v4-pro` из конфигурации сильного варианта, поэтому UI и Markdown-отчёт
показывают отдельные время, токены и расчётную стоимость оценки.

Основные проверки находятся в `ModelComparisonJudgeServiceTest`, `App.test.js`
и `modelComparisonReport.test.js`.
