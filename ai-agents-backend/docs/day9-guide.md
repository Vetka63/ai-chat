# День 9. Сжатие истории

Рабочая ветка `ai-challenge-day-9` создана от `ai-challenge-day-8`.
День 8 сохранён коммитом `a663251`. В main ничего не вливалось, ветки не отправлялись.
Python и новый Vue-клиент продолжают развитие; Java и прежний клиент не менялись.

## Запуск

Из корня репозитория:

```powershell
docker compose -p ai-chat-day-8 stop agents-client agents-backend
docker compose -p ai-chat-day-9 up -d --build agents-backend agents-client
```

UI: http://localhost:8083, backend: http://localhost:8082.
На первом развёртывании скопированы 5 чатов из тома `ai-chat-day-8_agents-data`
в отдельный `ai-chat-day-9_agents-data`. Оригинальный том сохранён.
`down -v` удаляет данные — не используйте его для обычного перезапуска.

## Как проверить в интерфейсе

1. Создайте чат. В блоке «Память · День 9» выберите «Summary + последние сообщения»
   и нажмите «Применить режим». Новые/старые чаты по умолчанию используют полную историю.
2. Для быстрого опыта поставьте N=2 и период=2. Это сообщения, не пары.
   После двух завершённых обменов будет 4 сообщения; при следующей отправке
   первые два будут свёрнуты, последние два останутся без изменений.
3. Раскройте «Сводка памяти»: появится текст, версия, модель и количество охваченных сообщений.
4. Под вопросом видна строка «Σ Сжатие», под ответом — обычные метрики ответа.
   Общий расход включает оба вызова. В таблице Σ обозначает summarizer.
5. В предварительной оценке сравните «Без сжатия», «Весь prompt» и «Размер сводки».
   Если сводка ещё должна обновиться, UI об этом предупредит. До отправки никто не
   вызывает LLM ради оценки и не знает точную длину будущей сводки.
6. Перезапустите backend и обновите страницу. История, настройки, сводка и usage сохранятся.
7. Верните режим «Полная история»: агент снова получит все исходные сообщения.

Параметры по умолчанию — последние 10 сообщений и обновление порциями по 10.
Первое сжатие происходит перед отправкой после накопления 20 сообщений истории.
Между обновлениями хвост растёт; если бы он всегда был ровно N, пришлось бы делать
платное обновление summary практически каждый ход. Пара вопрос/ответ на границе не разрывается.

## Сравнение качества

До контрольного вопроса нажмите «Копия для сравнения». Создаётся независимый чат
с ТОЙ ЖЕ исходной перепиской, но другим режимом. Старые затраты и summary не копируются:
это новая точка отсчёта для сравнения. Копирование само по себе не вызывает LLM.
В списке ∞ означает полную историю, Σ — сжатую.

В обоих чатах выберите одну модель и задайте одинаковый вопрос о ранних фактах:
коде, бюджете после исправления, ограничениях и распределении задач. Сравните:

- сохранились ли все факты и исправления, нет ли выдумок;
- API input/output/total обоих режимов;
- общую стоимость, включая ВСЕ вызовы summary;
- время ожидания: сжатие выполняется перед основным ответом и добавляет задержку.

«Скачать MD-отчёт» экспортирует метрики, настройки, текущую сводку и сообщения.
В отличие от прежнего отчёта Дня 8 теперь файл содержит текст переписки:
проверьте личные данные перед публикацией.

**Токенов стало примерно на 33% меньше, но стоимость в этом прогоне выросла.**
У полной истории почти весь input попал в дешёвый кэш DeepSeek. Создание сводки
и изменившийся префикс дали дополнительные cache miss и output tokens.
Это реальное наблюдение, а не ошибка суммирования. Сжатие помогает помещать диалог
в окно модели и снижает токены, но окупаемость зависит от модели, кэша, периода обновлений
и количества последующих запросов. На короткой истории экономии может вообще не быть.

Подготовка общего исходного сценария отдельно: 33 544 токена, $0.001764366 по тарифу.
Она общая для обоих режимов и не включена повторно в каждую ветку сравнения.
Денежные значения — расчёт по тарифам, а не подтверждение банковского списания.

## Ошибки, точность и ограничения

- Исходные messages не удаляются. Summary хранится отдельно; переключение режима не разрушает память.
- При ошибке/пустой/обрезанной сводке старое состояние не меняется; новый вопрос остаётся в истории.
  UI получает summary_failed, основной ответ не запрашивается. Неудачный summarizer с usage тоже учитывается.
- Локальная оценка DeepSeek по-прежнему приблизительная. API usage — фактический источник расхода.
  «Разница prompt» сравнивает оценки одним методом, это не окончательная денежная экономия.
- Сжатие выполняется по числу сообщений, не по приближению к лимиту. Огромный текущий запрос,
  несжатый хвост или запрос самого summarizer могут переполнить окно. Своего запрета по токенам нет.
- Модель сжатия совпадает с выбранной моделью чата; temperature=0, max_tokens не передаётся.
  Основной ответ: temperature=0.7; по умолчанию max_tokens не передаётся.
  В описанном выше историческом эксперименте использовался лимит 1200.

### Ручной лимит ответа

В правой панели клиента есть блок «Длина ответа». Изначально ограничение выключено:
API сам выбирает лимит по умолчанию, это не означает бесконечный ответ.
Включение предлагает 1200; ползунок и числовое поле позволяют выбрать значение
до максимума выбранной модели из каталога. Настройка сохраняется в SQLite при
отправке, отдельно для каждого чата, и копируется при создании копии для сравнения.
Новый чат начинает без лимита. Неотправленные настройки не сохраняются.

POST runs и preview принимают `max_output_tokens`: положительное целое или `null`.
Явное `null` отключает лимит, отсутствие поля использует сохранённый параметр чата.
Без лимита `reserved_output_tokens=null`, процент окна описывает только вход.
Резерв провайдера неизвестен; предупреждение о переполнении не блокирует отправку.
Старые записи с резервом 1200 продолжают показываться как исторические значения.

Для тестирования можно явно передать `--max-output-tokens 1200` в скрипты
`day8_experiment.py` и `day9_experiment.py`. Без этого флага лимит ответа не задаётся.
У служебной сводки также убран прежний фиксированный лимит 1024 токена, который
мог обрывать её и блокировать основной ответ. Компактность задаётся прежним промптом
(не более 300 слов). Ползунок основного ответа не применяется к сводке.
- SQLite/asyncio-lock рассчитаны на один процесс uvicorn, не на несколько реплик.
- Summary может потерять или исказить факт. Исходные сообщения сохранены для проверки и восстановления.

## Где менять поведение

### Как читать события сжатия в UI

Вопросы пользователя нумеруются отдельно от всей истории: запрос №8 обычно является
сообщением истории №15. При минимуме 10 и пороге 4 перед ним уже есть 14 сообщений;
сжимаются №1–4, последние 10 остаются целиком. Нынешний вопрос ещё не входит в порцию.

Вызов summary показан отдельной служебной карточкой, не вторым сообщением ассистента.
Таблица расхода различает номер API-вызова, тип (ответ/сжатие), номер пользовательского
запроса и статус. Оба вызова одной отправки учитываются отдельно, без двойного суммирования.

Новые summary-записи сохраняют `compression`: диапазон (номера с единицы), размер
истории до вопроса, несжатый остаток, прежнее покрытие, версию и снимок настроек.
У неуспешных событий это план попытки, не подтверждение сжатия. Старые записи не
изменяются: при наличии связанного основного вызова показывается итоговое покрытие,
а неизвестные диапазон новой порции и старые настройки явно помечаются неизвестными.

Preview возвращает прогресс накопления старых сообщений. Он не запускает LLM.
Изменения полей памяти вступают в силу только после «Применить настройки»; UI отдельно
показывает сохранённые значения и предупреждает о неприменённом черновике настроек.

### Как читать экономию токенов

В блоке «Эффект сжатия» показываются четыре разные величины:

1. «Без сжатия, вход» — локальная оценка всех основных prompt с полной историей.
2. «Со сжатием, вход» — локальная оценка подготовленных prompt со сводкой.
3. «Сокращено на входе» — разница первых двух значений.
4. «Создание сводок, API» — фактический `total_tokens` служебных LLM-вызовов.

Чистая экономия равна пункту 3 минус пункт 4. Она может быть отрицательной: сразу
после создания сводки затраты ещё могут не окупиться. Последующие запросы повторно
используют сводку, поэтому накопительная экономия обычно растёт.

Для DeepSeek первые три значения приблизительные, поскольку до отправки применяется
локальная эвристика. Расход сводки берётся из `usage` ответа API. Если `usage` нет,
приложение показывает итог как неизвестный, а не как ноль. При смене модели доступна
разбивка, поскольку методы токенизации у провайдеров могут отличаться.

`src/capabilities/context_memory/README.md` описывает алгоритм и границы модуля.
Промпт сжатия — `summary_prompt.txt` рядом с ним. Настройки чата — ContextSettings.
Подключение — `application/bootstrap.py`, приватные правила диалогового агента остаются
в `agents/dialogue`. Модуль можно подключать к другим агентам; UI показывает настройки
только агентам, объявившим capability `context_memory`.

API: POST conversations принимает context_settings; PATCH conversations/{id}/context
сохраняет режим; POST conversations/{id}/fork создаёт копию; GET conversations/{id}
возвращает summary и runs. Клиент не присылает произвольную историю или системный промпт.
