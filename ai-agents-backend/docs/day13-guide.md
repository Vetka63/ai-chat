# День 13 — сохраняемое состояние задачи

Ветка `ai-challenge-day-13` создана от Дня 12 (`beb92ec`). Изменён только Python
наставник и его Vue-клиент. Java и прежние задания не удаляются. День 14 и День 15
пока не реализованы. Подробная архитектура недели — в корневом `week-3-challenge.md`.

## Что реализовано

У алгоритмического наставника теперь есть явный автомат:

```text
planning → execution → validation → done
    ↑          ↑          │
    └──────────┴──────────┘  возврат к плану / доработка
```

Точные переходы:

| Фаза | Событие | Результат |
| --- | --- | --- |
| planning | start_execution | execution |
| execution | start_validation | validation |
| validation | request_changes | execution |
| execution или validation | request_replan | planning |
| validation | finish | done |
| любая незавершённая active | pause | та же фаза, paused |
| paused | resume | та же фаза, active |

`phase` — этап, `status` — active/paused, `current_step_id` — конкретный шаг
сохранённого плана, `expected_action` — подсказка следующего действия.
Сервер вычисляет подсказку из этапа и артефактов, например сохранить план,
продолжить шаг, перейти к проверке. Пауза не стирает этап и шаг.
Нельзя установить фазу произвольным текстом или перепрыгнуть planning → done.

В Дне 13 проверяется **порядок**, а не бизнес-готовность: start_execution пока
не требует утверждённого плана, finish не требует принятого отчёта. В Дне 15
появятся approvals конкретных версий и дополнительные условия. Обычный ответ
модели ориентируется на этап через prompt, но семантическая защита от просьбы
«дай код до плана» ещё не является гарантией.

## Где это в интерфейсе

Откройте http://localhost:8083/, выберите «Алгоритмический наставник».
В правой панели есть блок «Задача · День 13» над профилем и памятью.

1. Создайте задачу, выбрав профиль и введя условие.
2. Обсудите план в чате. Раскройте «Сохранить план» и укажите шаги, по одному
   на строку. Нажмите «Сохранить новую версию».
3. Нажмите «К реализации», выберите текущий шаг в списке и обсуждайте его.
4. Нажмите «Пауза». Отправка чата блокируется, этап и шаг остаются видимыми.
5. Перезапустите backend, снова откройте наставника и задачу.
6. Нажмите «Продолжить», напишите «Продолжим с того места, где остановились».
7. Сохраните текст решения отдельным артефактом и нажмите «К проверке».
8. Обсудите проверку, сохраните отчёт с источником, затем завершите задачу.

Артефакты сохраняются **явно**, не автоматически из каждого ответа. Это позволяет
отделить переписку/черновики от результатов задачи. На этом этапе достаточно
перенести нужный текст ответа в форму. Сохранение формы — не LLM-вызов.
После done основной чат и изменение артефактов закрыты; новую работу начинайте
новой задачей. Панель долговременной памяти остаётся доступна для сохранения знаний.

## План, решение и отчёт

План содержит до 30 шагов с непустыми заголовками и стабильными серверными ID.
Каждое сохранение создаёт новую версию; предыдущая не перезаписывается.
Форма нового плана создаёт новые ID; API может сохранить ID шагов прежнего плана.
Выбор текущего шага — явное действие пользователя, не заявление о выполненном тесте.

Решение хранится как текст. Отчёт содержит текст и источник:

- `llm_review` — анализ моделью, код не запускался;
- `user_test_result` — результат запуска, предоставленный пользователем.

Исполнителя кода нет. Приложение не запускает `exec` над ответами LLM.
Артефакт хранит версию рабочей памяти и ссылки на версии плана/решения,
актуальные при сохранении. API также принимает ID сообщения-источника своей задачи.
Форма ручного ввода не приписывает текст конкретному сообщению автоматически.
Если рабочая память позже менялась, UI предупреждает о необходимости проверить
актуальность артефакта. Полное аннулирование approvals относится к Дню 15.

## Что отправляется в LLM

Сохраняется сборка Дня 12: системный prompt, профиль, рабочая память,
долговременные записи, хвост N сообщений и текущий вопрос.
В рабочий JSON добавлен `workflow`: снимок текущего состояния и последние
версии трёх артефактов. Поэтому этап и шаг не исчезают, когда ранняя реплика
выпадает из окна N. Журнал событий и все прежние версии в prompt не дублируются.
Снимок этого блока записан у каждого run и доступен в MD-отчёте.
Токены учитываются в общей оценке prompt/рабочей памяти, actual usage — отдельно.

## Ошибки, параллельность и повтор запросов

Команды состояния требуют `command_id` и `expected_revision`. Эти поля также
передаёт новый UI при отправке основного сообщения. Для совместимости старый
API-вызов без полей принимается: сервер назначает ID и использует свой снимок;
но повтор такого старого вызова **не имеет клиентской гарантии дедупликации**.

- Тот же ID и payload успешной команды → сохранённый результат без второго вызова.
- Тот же ID с другим payload → `409 command_conflict`.
- Устаревшая версия → `409 state_conflict`.
- Недопустимый переход → `409 transition_not_allowed`.
- Отправка при паузе → `409 task_paused`, без сообщения и без LLM.
- Основной запрос другой активной команды → `409 task_busy` на уровне reservation.
- Повтор незавершённой/ошибочной команды → явный pending/error/interrupted,
  не неявный платный retry.

Пауза не ждёт сетевой ответ LLM и повышает версию состояния. Поздний ответ
не публикуется; пользовательский вопрос остаётся в истории, расход записывается.
Даже pause → resume до возврата ответа не делает старый результат актуальным.
Пауза не отменяет уже отправленную провайдеру платную работу.

Вопрос и reservation записываются одной транзакцией. После LLM успешный ответ,
финальные метрики, событие и replay-кэш сохраняются другой общей транзакцией.
Внутри SQL-транзакций нет HTTP-вызовов. Ошибка сохранения откатывает частичный ответ.
SQLite защищает один pending основной run на задачу уникальным индексом.

При рестарте pending runs/команды становятся interrupted. Ответ автоматически
не генерируется заново; если usage не успел сохраниться, расход неизвестен.
Recovery рассчитан на один процесс приложения. Несколько независимых процессов
с общим startup-recovery пока не поддерживаются; очередь и lease — будущая работа.

## Проверки

Автоматически: 113 backend-тестов и 58 тестов клиента. Покрыты граф, пауза на
planning/execution/validation, сохранение шага, поздний ответ, pause+resume во время
вызова, откат транзакции, конфликт версии, replay без дублей, изоляция задач,
восстановление и миграция БД Дня 12. Production-сборка клиента и Docker успешны.

Реальный эксперимент выполнен двумя вызовами DeepSeek Flash:

| Момент | API input | API output | Всего | Время |
| --- | ---: | ---: | ---: | ---: |
| Шаг проверки [3,3], до паузы | 1338 | 246 | 1584 | 2051 мс |
| Продолжение после рестарта | 1629 | 252 | 1881 | 1913 мс |

Всего 3465 токенов API. После рестарта модель узнала текущий шаг и продолжила
трассировку разных индексов. Повтор каждого ID вернул идентичный результат без
дополнительного LLM-вызова. Это проверка восстановления контекста, не доказательство
корректности алгоритма на всех входах.

Через браузер проверены восстановленная пауза, шаг плана, сохранение решения,
переход к validation и пауза на этом этапе. Демонстрационная задача
«День 13 — продолжение после паузы» оставлена для просмотра.

## Воспроизведение и запуск

```powershell
# Из корня ai-chat; прежние тома не удаляются
docker compose -p ai-chat-day-12 stop agents-client agents-backend
docker compose -p ai-chat-day-13 up -d --build agents-backend agents-client

# Из ai-agents-backend: создаёт демонстрационную задачу, расходует один LLM-вызов
.venv\Scripts\python.exe scripts/check_day13.py --allow-llm
# Запомните chat из результата. Из корня:
docker compose -p ai-chat-day-13 restart agents-backend
# После готовности backend, из ai-agents-backend:
.venv\Scripts\python.exe scripts/check_day13.py --resume CHAT_ID --allow-llm
```

Скрипт задаёт 1200 max_output_tokens только для своего короткого эксперимента.
Значение по умолчанию новых чатов не изменено. Каждый Compose project использует
отдельный volume; День 12 остановлен, его данные сохранены. Старые версии кода
не следует запускать против БД более нового дня. Миграция вперёд добавочная;
перед переносом реальных данных сделайте резервную копию.

## Карта кода

- `capabilities/task_workflow/` — общие модели, порт Unit of Work, сервис.
- `agents/algorithm_coach/workflow_policy.py` — граф и предметные схемы.
- `infrastructure/sqlite_task_workflow.py` — транзакции, replay и recovery.
- `infrastructure/migrations/013_task_workflow.sql` — четыре новые таблицы.
- `application/routes/tasks.py` — GET `/task`, POST `/task/events`, `/artifacts`, `/step`.
- `agents/algorithm_coach/agent.py` — LLM-вызов с reservation и атомарным commit.
- `ai-agents-client/src/features/tasks/` — самостоятельная панель и команды.
- `tests/test_task_workflow.py` — проверки Дня 13.
