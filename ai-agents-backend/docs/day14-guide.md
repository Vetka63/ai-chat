# День 14 — обязательные правила алгоритмического наставника

## Что реализовано

У каждой задачи есть отдельный список инвариантов: язык, точная сигнатура Python,
разрешённые импорты и произвольные смысловые правила. Это не пожелания профиля
и не сообщения в переписке. Пользователь явно сохраняет их через UI/API.

Например, для Two Sum: только Python; `two_sum(nums, target)`; никаких импортов;
не менять исходный `nums`. Предпочтение профиля «Java» или просьба «игнорируй
правило» не изменяет этот список. Правила принадлежат задаче, не всем чатам агента.
Новые задачи создаются без активных правил; пример в UI — только черновик.

## Путь одного запроса

```text
Запрос пользователя → reservation + сохранение вопроса
  → input judge (DeepSeek Pro)
  → основная LLM (модель чата)
  → output policy → AST-проверки → output judge (DeepSeek Pro)
  → сверка актуальности памяти/этапа/правил
  → атомарное сохранение ответа и метрик
```

Если активных правил нет, проверки пропускаются. Обычный разрешённый запрос
при правилах стоит три LLM-вызова: input judge, основной ответ, output judge.
Конфликт на входе — только один judge, основная модель не вызывается. Статическая
ошибка ответа — input judge + основная модель, без output judge.

Запрос judge получает стадию, все активные правила, профиль, условие задачи,
текущий state, проверяемый запрос или пару запрос/кандидат. Вся история и
долговременные записи ему не передаются. Ключ остаётся в HTTP-авторизации.
Новая внешняя передача этих данных и дополнительные платные вызовы согласованы
с пользователем отдельно. Не помещайте в задачу сведения, которые нельзя
отправлять выбранному провайдеру.

## Три результата проверки

- `pass`: можно продолжить; это оценка, не математическое доказательство.
- `conflict`: обнаружено нарушение, HTTP 422 `invariant_conflict`.
- `uncertain`: соблюдение не подтверждено, HTTP 503 `invariant_uncertain`.

Ошибка API, усечение ответа или невалидный JSON judge дают uncertain. Ошибка
провайдера дополнительно сохраняется в `check.error_code` и run; она не
маскируется под содержательный конфликт. Автоматических повторов нет.

Отказ имеет типизированный контракт `details.type=policy_refusal`, `source=policy`,
`model=null`. В UI это баннер плюс постоянная запись в «Проверках», не выдуманное
assistant-сообщение. Вопрос пользователя сохраняется, отклонённый кандидат — нет.
Поэтому после отказа в переписке может остаться вопрос без ответа. Вердикт можно
посмотреть и после перезагрузки в панели правил. Фаза, шаг и рабочая память от
отказа не меняются; журнал проверок и расходы пополняются.

## Статика и семантика

Локальный AST-разбор ничего не исполняет. Проверяются язык блоков, синтаксис,
имена/параметры/defaults/аннотации функции, разрешённые корни импортов. В первой
версии язык — только Python; импорты — стандартная библиотека, `-` запрещает все.
Поддерживаемые формы динамической загрузки и интроспекции блокируются как
uncertain. Это не sandbox и не полное обнаружение всех обходов.

Объяснение без кода не обязано содержать сигнатуру функции. Полное решение из
формы артефакта проверяется строже. Синтаксически неполные фрагменты и отдельные
helper-блоки могут быть консервативно отклонены: давайте полное решение одним
Python-блоком. Даже плохой пример с запрещённым импортом в ответе будет отклонён
локально; обсуждать его можно текстом.

Неизменность массива, выбранная архитектура, сложность, бизнес-правила оценивает
judge. Он обязан вернуть JSON с одной оценкой каждого ID, включая ненарушенные
правила. Пропущенные, повторные и чужие ID не разрешаются. Prompt injection и
семантические ошибки полностью исключить нельзя. Judge не доказывает Big-O
и не запускает тесты; Дня 15 и исполнителя кода здесь ещё нет.

## Ручные артефакты и изменение правил

Форма плана/решения/отчёта проходит те же проверки перед сохранением. Кнопка
«Сохранить» может вызвать ещё один judge; она не обходит проверки output.
Невалидная схема/фаза отклоняется до платного вызова. Команда резервируется по
ID, сетевой вызов идёт вне SQL-транзакции. Повтор успешной команды возвращает
исходный результат без повторной оплаты.

Сохранение списка правил атомарно увеличивает его ревизию, возвращает фазу
к `planning`, сбрасывает выбранный шаг. Если задача на паузе, пауза сохраняется.
Старые артефакты остаются в истории с прежней `invariant_revision`, но больше
не включаются в prompt и не считаются текущими. Любое сохранение правил, даже
того же списка, начинает новую ревизию. Завершённая задача не редактируется.

Пауза доступна и во время проверки артефакта. Изменение правил/памяти/этапа в
другом клиенте делает поздний результат неактуальным: он не публикуется и не
продвигает задачу. Потраченные токены всё равно учитываются.

## Где находится код

- `capabilities/invariants/` — DTO, порты и общий `InvariantGuard`.
- `agents/algorithm_coach/validators/` — конкретные AST-правила наставника.
- `agents/algorithm_coach/llm_judge/` и `prompts/invariant_judge.txt` — semantic judge.
- `agents/algorithm_coach/agent.py` — точки проверки input/output/артефакта.
- `infrastructure/sqlite_invariants.py` — правила и аудит; миграция `014_invariants.sql`.
- `infrastructure/sqlite_task_workflow.py` — reservation, атомарная фиксация и CAS.
- `application/routes/invariants.py` — GET/PUT правил конкретного чата.
- `ai-agents-client/src/features/invariants/` — редактор и журнал.

Правила лежат в `task_invariants`, полный аудит — в `invariant_checks`; история
диалога остаётся в `messages`. UI/API показывают последние 50 проверок, каждый
содержит снимок правил. Артефакты и задача ссылаются на версию правил.
Нет полной отдельной истории всех редактирований списка, если проверка версии
ещё не запускалась. Аудит не содержит полный отклонённый кандидат.

## Конфигурация, метрики и запуск

Серверные переменные (ключ тот же, что для обычного DeepSeek):

```dotenv
PY_AGENT_JUDGE_MODEL=deepseek-v4-pro
PY_AGENT_JUDGE_MAX_OUTPUT_TOKENS=2000
```

Лимит 2000 относится только к служебному JSON judge, не к ответу чата.
При 20 длинных правилах его может не хватить — будет uncertain; увеличьте
серверную настройку (до 16000) при необходимости. В demo-режиме нет реального
semantic judge: его непроверенный ответ не даёт разрешения. Для правил нужен LLM.

```powershell
docker compose -p ai-chat-day-14 up -d --build agents-backend agents-client
```

Перед переключением между днями остановите прежние контейнеры, занимающие
8082/8083. Не используйте `down -v`: это удалит данные. Новый Compose-проект
имеет отдельный том, старые чаты автоматически туда не копируются.

UI: http://localhost:8083, health: http://localhost:8082/health (`day=14`).
Статистика различает `invariant_input/output/artifact`, показывает API usage
и оценку стоимости judge отдельно. Эти суммы уже включены в общий расход.
Успешный run judge — корректный ответ проверки, но verdict может быть conflict.
Для ручного артефакта отдельного сообщения пользователя нет, номер запроса — «—».
MD-отчёт содержит текущие правила, последние 50 проверок и все метрики вызовов.
Проверьте переписку и память отчёта перед публикацией.

## Сценарий сдачи

1. Выберите наставника, создайте Two Sum, откройте «Обязательные правила».
2. Заполните пример и явно сохраните: Python, сигнатура, без импортов, не менять nums.
3. Попросите коротко объяснить алгоритм со словарём: ожидается ответ и два pass.
4. Попросите Java или изменение nums на месте: ожидается отказ с ID и причиной.
5. Перейдите к реализации. Сохраните решение с `import numpy`: локальный отказ.
6. Сохраните корректный полный код без изменения входа: judge проверяет артефакт.
7. Поставьте паузу, измените правило: planning + paused; старый артефакт помечен.
8. Перезапустите backend: правила, проверки, пауза и артефакты восстановятся.
9. Скачайте MD-отчёт, сравните причины отказов и дополнительные расходы.

Автоматический реальный smoke создаёт только новую тестовую задачу:

```powershell
cd ai-agents-backend
.\.venv\Scripts\python.exe scripts/check_day14.py --allow-llm
```

Нормальное прохождение — пять платных вызовов. При неопределённости сценарий
останавливается, не повторяет вызовы сам. Тестовые чаты сохраняются для просмотра.

## Результаты проверки реализации

156 backend-тестов и 66 тестов клиента; production-сборка Docker. Реальный
успешный smoke: Flash для ответа, Pro для judge; 5 вызовов, 7588 API-токенов.
Первый диагностический прогон дополнительно израсходовал 5351 токен
и безопасно остановился на невалидном JSON judge. После уточнения инструкции
полного списка ID повторный прогон прошёл. Это не гарантия идеального JSON
в будущих вызовах: fail-closed и явная ошибка остаются необходимыми.

В браузере проверены аудит/расход, форма правил и изменение правил на паузе.
После пересоздания backend сохранены правила v3, planning/paused, старое решение,
5 проверок и 5 runs успешного сценария. Новый День 14 использует отдельный том;
данные Дня 13 не удалены. Два демонстрационных чата оставлены для просмотра.
