# День 11 — явные слои памяти

Ветка: `ai-challenge-day-11`, от `ai-challenge-day-10`. Новый агент:
**Алгоритмический наставник** (`algorithm_coach`). Прежний `dialogue`,
Java-проект и прежний клиент сохранены.

## Запуск

Из корня репозитория:

```powershell
docker compose -p ai-chat-day-11 up -d --build agents-backend agents-client
```

Клиент: http://localhost:8083, backend: http://localhost:8082/docs.
Если порты заняты предыдущим днём, остановите его два сервиса с соответствующим
именем Compose-проекта. Не используйте `down -v`: он удаляет том с историей.

Проект `ai-chat-day-11` использует отдельный том `ai-chat-day-11_agents-data`.
Поэтому чаты предыдущего дня не появляются автоматически: они не удалены и
остаются в его томе. Если запустить обновлённое приложение на существующей базе,
добавочная миграция сохраняет прежние таблицы и диалоги.

Ключи по-прежнему читаются сервером из локального `.env`; клиент их не получает.
Модель выбирается внизу чата. Лимит ответа по умолчанию не задан приложением.

## Что хранится и что отправляется

| Слой | Где хранится | Область | Как пополняется |
| --- | --- | --- | --- |
| Краткосрочная | `messages` | Текущий чат | Обычная переписка |
| Рабочая | `tasks.problem`, `task_memory` | Одна задача = один чат | Карточка, ручная запись, подтверждённое предложение |
| Долговременная | `long_term_memory` | Агент + локальный профиль | Ручная запись или явное подтверждение |
| Предложения, ещё не память | `memory_proposals` | Задача | Отдельный запрос по кнопке |

В SQLite остаётся **вся переписка**. Краткосрочный контекст запроса — последние N
сообщений этой переписки. N выбирается при создании и считается по отдельным
сообщениям, а не парам вопрос–ответ. Текущий новый вопрос добавляется сверх N.

Порядок основного LLM-запроса:

1. Системный промпт наставника.
2. JSON рабочей памяти: карточка условия и активные записи.
3. JSON активных долговременных заметок.
4. Последние N сохранённых сообщений.
5. Новый вопрос пользователя, ровно один раз.

Карточка и заметки — данные, а не дополнительные системные команды.
Источники, версии, предложения и служебные ID в эти текстовые блоки не включаются.
Неподтверждённые предложения в основной запрос не попадают.
При противоречии карточки и сообщения наставник просит явно уточнить карточку;
это инструкция модели, а не семантическая гарантия. Детерминированные инварианты —
отдельная работа Дня 14.

## Управление в UI

1. Выберите справа «Алгоритмический наставник».
2. Нажмите «Новый чат», введите название и условие; оставьте N=4.
3. В правой панели раскройте нужный слой памяти.
4. Карточка редактируется отдельно. Сохранение карточки не вызывает LLM.
5. В «Сохранить в память вручную» явно выберите слой, название и содержимое.
   Рабочие поля: цель, подход, план, решение, тестовые случаи, наблюдения,
   ограничения. Долговременным заметкам можно давать свои названия.
6. Чтобы получить подсказки LLM, выберите своё сообщение из текущего хвоста и
   нажмите «Предложить, что запомнить». Это **один дополнительный API-вызов**.
7. Для каждого предложения отдельно нажмите «Подтвердить» либо «Отклонить».
   Обычный ответ в чате сам по себе ничего не записывает в эти два слоя.
8. Долговременную запись можно отключить, не удаляя. Её значение и происхождение
   сохраняются, но в следующем блоке долговременной памяти она отсутствует.
   Упоминания той же информации в хвосте переписки остаются: для чистого сравнения
   используйте новую задачу или дождитесь их выхода за окно N.

Ручная запись с тем же названием заменяет существующую и повышает её ревизию.
Новая правка текста помечается как ручная; переключение активности сохраняет
прежний источник. Удаление чата удаляет карточку, рабочую память и предложения,
но не долговременную память. Последнюю удаляют отдельной явной кнопкой.

В Дне 11 есть один серверный профиль «Мой учебный профиль». Выбор пользователя,
аутентификация и персонализация появятся отдельно; это локальное учебное приложение,
а не многопользовательский сервис.

## Сценарий для сдачи

Условие: «Дан массив целых чисел и target. Вернуть индексы двух различных элементов
с нужной суммой. Если пары нет — пустой список. При нескольких парах подходит любая».

1. Создайте задачу Two Sum с N=4 и этим условием.
2. Напишите: «Хочу разобраться с поиском через словарь. Сначала давай подсказки».
3. Запустите предложения памяти. Посмотрите выбранные моделью слои и причину.
   Не подтверждайте вслепую: модель может ошибиться в классификации.
4. Сохраните подход через словарь в рабочее поле «Подход».
   Сохраните общую учебную заметку в долговременную память.
5. Обменяйтесь ещё несколькими сообщениями. Убедитесь, что ранняя реплика
   отсутствует в краткосрочном хвосте, но подход остался в рабочей памяти.
6. Спросите: «Какой подход мы выбрали и почему?». Посмотрите блок
   «Память в последнем запросе»: требование действительно было передано.
7. Создайте вторую задачу — например, проверку скобок. В ней нет условия и подхода
   Two Sum, зато есть общая заметка. Это демонстрирует границы двух слоёв.
8. Отключите долговременную запись и задайте вопрос повторно. Сравните снимки
   запросов; содержание ответа LLM вероятностное, поэтому снимок — основное
   доказательство передачи/исключения данных.
9. Перезапустите backend:

```powershell
docker compose -p ai-chat-day-11 restart agents-backend
```

Обновите страницу, снова выберите наставника и задачу. История, карточка, записи
и предложения восстановятся. Скачайте MD-отчёт из раздела расхода токенов.
Перед публикацией проверьте отчёт: он содержит и долговременную память.

Наставник **не исполняет код**. Рассуждения о примерах и предложенные тесты не
являются результатом реального запуска Python.

## Как устроен код

- `agents/algorithm_coach/`: самостоятельный агент, фабрика, настройки,
  предметные input/output/context/memory policies, Pydantic-модель условия,
  промпты ответа и предложений.
- `capabilities/memory_layers/`: общий контракт репозитория, модели трёх слоёв,
  команды с версиями и сервис явной записи. Другой агент может подключить этот
  механизм со своей политикой разрешённых полей, без копирования наставника.
- `infrastructure/sqlite_memory_layers.py`: транзакционные операции и проверка
  принадлежности записей; агент не обращается к SQL.
- `infrastructure/migrations/011_memory_layers.sql`: новые таблицы.
  `migrations.py` хранит применённые версии в `schema_migrations`.
- `capabilities/token_accounting/call.py`: учёт жизненного цикла LLM-вызова,
  включая расход при невалидном ответе и ошибке применения результата.
- `application/routes/memory.py`: тонкие HTTP-маршруты; выбирают агента,
  передают типизированную команду и возвращают workspace памяти.
- Клиент `features/memory/`: API, composable для синхронизации, MemoryPanel.
  Старый ответ загрузки не может подменить память после смены чата.

В начале генерации агент читает согласованный снимок памяти. Перед публикацией
ответа проверяет версии задачи и профиля. Если в другом окне изменили память,
возвращает `409 state_conflict`, не сохраняет устаревший ответ и оставляет вопрос
в истории. Usage уже выполненного запроса всё равно учитывается.

Принятие предложения проверяет также ID и ревизию конкретной целевой записи.
Это защищает новую ручную правку от старого предложения LLM. Повторное подтверждение
возвращает 409 и не создаёт дубликат. При ошибке JSON подтверждённая память не меняется.

Системные блоки и хвост сохраняются как снимок состава в `run.memory_context`
(для хвоста — стабильные ID). У служебного вызова записываются выбранный источник
и фактически отправленные существующие записи. UI/отчёт различают эти снимки
и актуальное состояние памяти.

## API памяти

Префикс: `/api/v1/agents/algorithm_coach/conversations/{chat_id}/memory`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | пустой | Чтение workspace |
| PUT | /problem | Замена карточки |
| POST | /entries | Явная запись или обновление поля |
| POST | /entries/{id}/delete | Удаление с проверкой версии |
| POST | /proposals | Анализ одного сообщения пользователя |
| POST | /proposals/{id} | accept / reject |

Все команды изменения содержат `task_revision` и `profile_revision` из последнего
workspace. Идентификатор профиля клиентом не выбирается.
GET и preview ничего не записывают и не вызывают LLM.

## Проверки и дальнейшие этапы

На момент завершения реализации: **82 backend-теста, 42 теста клиента — успешно**.
Docker-сборка запущена; три реальных запроса DeepSeek потратили 1529 токенов по API.
После перезапуска контейнера восстановились история, карточки, подтверждённая
рабочая память и метрики. В браузере проверено ручное сохранение в панели.

```powershell
cd ai-agents-backend
.\.venv\Scripts\python.exe -m pytest
cd ../ai-agents-client
pnpm test
pnpm build
```

Автотесты проверяют фактический состав запроса на подставной LLM, границы задач
и профилей, отключение заметки, удаление чата, подтверждения, ошибки, версии,
миграции и восстановление после перезапуска. Реальный API проверяется отдельно
скриптом `scripts/check_day11.py` — это платные тестовые вызовы, не часть pytest.
Запуск из backend: `python scripts/check_day11.py --allow-llm`. Он делает три
вызова с тестовым лимитом 1200, оставляет два демонстрационных чата и удаляет только
собственную временную долговременную заметку. Снимки вызовов сохраняют её для отчёта.

Версионированные артефакты плана/кода/валидации и `task_artifacts` вводятся вместе
с жизненным циклом Дня 13. Пока план/решение/тесты явно сохраняются как рабочие поля.
Дни 12–15 не реализованы; следующий шаг — профиль и персонализация.
Пер-процессные блокировки рассчитаны на один worker; транзакции защищают правки
памяти, но распределённая очередь и идемпотентность отправки диалога пока не добавлены.
