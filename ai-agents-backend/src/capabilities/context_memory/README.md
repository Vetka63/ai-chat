# Управление контекстом

Это подключаемая capability агента, а не самостоятельный агент. Она получает
сохранённый `Conversation`, системный промпт и новый текст, после чего выбранная
стратегия строит список `messages` для LLM. Сам `DialogueAgent` по-прежнему отвечает
за input/output policy, вызов модели и сохранение вопроса с ответом.

## Стратегии

| mode | Что попадает в основной запрос | Дополнительный LLM-вызов |
|---|---|---|
| `full` | system + вся история + новый user | нет |
| `summary` | system + summary + несжатый хвост + новый user | периодическое обновление summary |
| `sliding_window` | system + последние N сообщений + новый user | нет |
| `sticky_facts` | system + facts + последние N сообщений + новый user | обновление facts перед каждым ответом |
| `branching` | system + история только активной ветки + новый user | нет |

`ContextStrategyRegistry` связывает строковый mode с реализацией. Чтобы добавить
новый алгоритм, достаточно реализовать `prepare(ContextRequest) -> PreparedContext`
и зарегистрировать объект в `ContextMemory`; код агента менять не нужно.

## Файлы

- `models.py` — настройки и состояния summary/facts/checkpoint.
- `contracts.py` — порты репозиториев, не зависящие от SQLite.
- `runtime.py` — единый вход и результат стратегий.
- `service.py` — реестр и фасад `ContextMemory`.
- `strategies/` — по одному модулю на алгоритм.
- `summarizer.py`, `summary_prompt.txt` — накопительная сводка Дня 9.
- `facts.py`, `facts_prompt.txt` — строгий JSON и измеряемое обновление facts.
- `infrastructure/sqlite_summary.py`, `sqlite_facts.py`, `sqlite_branching.py` —
  постоянные адаптеры SQLite.

## Sliding Window

`keep_last=N` означает ровно последние N сообщений обеих ролей. N может быть
любым целым от 1 до 100. Старые строки не удаляются из SQLite — они лишь не
попадают в конкретный LLM-запрос. Выбранная при создании стратегия неизменяема;
для другого алгоритма создаётся новый чат.

## Sticky Facts

Перед основным ответом отдельный вызов получает прежний JSON facts и только новое
сообщение пользователя. Он обязан вернуть `{"facts":{"key":"value"}}`.
Pydantic запрещает лишние верхнеуровневые поля и значения не-строки. Успешный
результат атомарно заменяет состояние и повышает revision.

Facts — данные, а не инструкции: в основной запрос они добавляются как user-блок
с явным предупреждением. Новый пользовательский текст и свежий хвост имеют приоритет.
Если JSON пуст, повреждён или ответ оборван, прежние facts сохраняются, основной
ответ всё равно выполняется, а UI получает предупреждение. Вызов `purpose=facts`
имеет собственные usage, стоимость, длительность и ошибку.

## Branching

Checkpoint хранит `message_count` и снимок facts в выбранной точке. Из него одной
транзакцией создаются ровно две новые беседы: обе получают сообщения только до
checkpoint, свои UUID и метаданные root/parent/checkpoint/branch. Более поздние
сообщения родителя не копируются. Продолжение одной ветки не меняет другую.

Checkpoint неизменяем; повторное создание пары веток из той же точки возвращает
`branches_already_created`. Переключение ветки — обычная загрузка другого
`conversation_id`; истории родственных веток никогда не объединяются автоматически.

## Summary и совместимость с Днём 9

Summary продолжает работать без изменений: сворачивает целые пары сообщений,
хранит оригиналы и подставляет сводку вместо покрытого префикса. Только для этого
режима `keep_last` должен быть чётным (2–100), а `summarize_every` — чётным (2–100).
Служебный вызов записывается как `purpose=summary`.

## Preview, ошибки и многопоточность

`prepare(generate=False)` ничего не сохраняет и не вызывает LLM. Поэтому preview
для Sticky Facts показывает текущее, а не ещё не извлечённое состояние. Платные
вызовы происходят только при отправке сообщения.

Оригинальный вопрос сохраняется до внешних вызовов. Внутри одного процесса операции
одного чата защищены `asyncio.Lock`. SQLite и локальные lock рассчитаны на один
процесс uvicorn; нескольким workers потребуются distributed lock/lease.
