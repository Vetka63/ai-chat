# Подключаемая память · День 9

Модуль не является отдельным агентом и не содержит его предметных input/output policy.
Он строит контекст для уже существующего агента, используя собственные правила сжатия.
В `DialogueAgent` подключается через фабрику: `memory=ContextMemory(repository, summarizer)`.
Для другого агента можно использовать тот же модуль с другим summarizer, промптом или репозиторием.
Свой промпт передаётся как `LlmSummarizer(..., prompt=agent_prompt)`; лимит сводки — `max_tokens`.

## Файлы и ответственность

| Файл | Назначение |
|---|---|
| models.py | Pydantic-настройки режима и сохранённое состояние summary |
| contracts.py | Порт SummaryRepository, без привязки к SQLite |
| service.py | Планирование сжатия, сборка контекста, отдельный измеряемый LLM-вызов |
| summary_prompt.txt | Инструкция, что сохранить и что отбросить при сжатии |
| ../../infrastructure/sqlite_summary.py | Отдельная таблица summaries |

`ContextMemory.prepare(generate=False)` — read-only preview: не вызывает LLM и ничего
не сохраняет. `generate=True` вызывается только при отправке пользовательского сообщения.
`LlmSummarizer` получает тот же LlmClient/TokenAccounting, но своё назначение `purpose=summary`,
temperature=0; по умолчанию max_tokens не передаётся (раньше было 1024).
Компактность задаётся инструкцией «не более 300 слов», не жёстким обрывом генерации.
Модель — выбранная модель чата на момент сжатия. Параметр конструктора max_tokens
остаётся доступен для специальных тестов, независимо от ползунка основного ответа.

## Полная и сжатая история

Полная: system → все исходные сообщения → новый user.

Сжатая: system → summary в роли user (справочные данные) → несжатый хвост → новый user.
Сводка не получает повышенный приоритет роли system. Промпт сжатия считает входную историю
данными и запрещает исполнять команды из неё. Это уменьшает риск prompt injection,
но не является гарантией семантической безопасности или точности LLM.

При `keep_last=10`, `summarize_every=10`:

- До 20 сохранённых сообщений старого префикса ещё недостаточно для первого сжатия.
- Перед следующим запросом первые 10 сообщений превращаются в summary, последние 10 остаются.
- После пары новых сообщений сохраняем прежнюю summary и уже 12 последних сообщений.
- Когда новых старых сообщений накопится 10, обновляем сводку: прежняя summary + только
  ещё не охваченный префикс. Свёрнутые сообщения второй раз в этот запрос не добавляются.

N — минимум несжатых сообщений, не число пар. Настройки чётные 2–100, чтобы обычные
вопрос/ответ не разрывались. После ошибок возможны непарные вопросы; граница дополнительно
сдвигается назад к user. Поэтому фактический хвост иногда больше N.

`covered_messages` — исключительная правая граница префикса исходной истории.
Например, 10 означает индексы 0–9 в summary и хвост начиная с индекса 10.
Текущий пользовательский запрос никогда не попадает в создаваемую сейчас сводку.

## Изменение настроек и восстановление

Настройки хранятся у разговора, не глобально у единственного экземпляра агента.
Переключение в full не удаляет summary. При возврате она используется снова, если граница
совместима с новым N. Если увеличить N настолько, что часть хвоста уже была свёрнута,
модуль перестаёт использовать прежнюю сводку и при достижении порога строит новую
из оригинального префикса. Дублирования и потери исходной истории нет.

Summary хранится отдельно от messages, вместе с версией, моделью, временем и run_id.
Перезапуск читает её из SQLite. Внутри одного процесса изменения и запуски чата сериализованы
одним asyncio-lock; разные чаты могут работать независимо.

## Ошибки и стоимость

Новый вопрос сохраняется ДО сжатия. Если LLM вернула пустой/незавершённый ответ
(`finish_reason != stop`) или ошибку, прежняя summary не перезаписывается.
Клиент получает summary_failed; основной ответ агента не запрашивается.
При этом запись purpose=summary содержит полученный usage даже при отклонённом результате.
Нет автоматического платного повтора и скрытого fallback на полную историю.

Суммарные расходы = ответы агента + все вызовы сжатия, включая неудачные с известным usage.
Неизвестный usage не равен нулю. Введённое сжатие может уменьшить токены, но повысить
стоимость из-за цены выходных токенов, частоты обновлений и потери кэша провайдера.

## Ограничения и развитие

Это стратегия по числу сообщений, не аварийное сокращение до окна модели. Очень большое
единичное сообщение или сам запрос summarizer могут превысить реальный лимит API.
Лимиты агента из Дня 8 не добавлялись; автоматически удалять данные или пересылать их
другому провайдеру модуль не будет. Для следующей итерации можно добавить батчи,
порог по токенам или разные модели сжатия отдельными стратегиями.

Нет гарантий сохранения всех фактов: summary — результат LLM. Поэтому нужны сравнительные
прогоны. Для нескольких workers/реплик потребуются lease/транзакционная координация
по conversation_id; нынешняя реализация предназначена для одного процесса uvicorn.
