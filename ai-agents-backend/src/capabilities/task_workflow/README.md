# Автомат задачи — день 13 v2

Один чат алгоритмического наставника содержит одну задачу. Состояние задачи
хранится в `task_workflow` отдельно от сообщений, а подтверждённые результаты —
в `task_artifacts`. `task_workflow_events` фиксирует каждое изменение этапа,
шага и паузы. SQLite-миграция: `013_task_workflow.sql`.

## Правила

Последовательность этапов: `planning → execution → validation → done`.
После каждого ответа модели появляется кандидат результата текущего этапа.
Пользователь может продолжать диалог или поправить текст кандидата и подтвердить:

| Команда | Исходный этап | Что сохраняется | Новый этап |
| --- | --- | --- | --- |
| `accept_plan` | planning | шаги плана | execution |
| `accept_solution` | execution | текст решения | validation |
| `accept_validation` | validation | отчёт и источник проверки | done |

`pause` и `resume` не меняют этап и выбранный шаг. `select_step` выбирает только
шаг подтверждённого плана во время реализации. Диалог не меняет состояние
автомата: пользователь подтверждает предложенный результат в UI/API.
`expected_action` вычисляется из текущего этапа, паузы и наличия свежего ответа.

Команда содержит `expected_revision`. При изменении задачи в другой вкладке
устаревшая команда получает HTTP 409. При ответе LLM исходная версия автомата
проверяется в одной транзакции с сохранением ответа. Если во время генерации
задачу поставили на паузу, поздний ответ не публикуется; вопрос остаётся
в истории и его можно продолжить после возобновления.

## Границы следующих дней

День 14 добавит отдельные обязательные правила задачи и проверки входа/выхода.
День 15 добавит явные утверждения версий плана и проверки перед переходами.
На дне 13 уже соблюдается порядок фаз и требуется ответ-кандидат; содержание
плана и правильность кода ещё не подтверждаются автоматически.

API: `GET /api/v1/agents/{agent_id}/conversations/{id}/workflow` и
`POST .../workflow/actions`. Маршрут доступен только агентам с capability
`task_workflow`; источник истины — SQLite, а не текст ответа модели.
