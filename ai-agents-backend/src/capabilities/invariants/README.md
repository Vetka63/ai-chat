# Обязательные правила задачи — день 14 v2

`models.py` описывает правило, версию набора и результат проверки. `service.py`
объединяет локальную проверку, semantic judge и сохранение аудита. Модуль не
зависит от Two Sum и не хранит правил в переписке.

Правила относятся к одному `task_id`, не к профилю и не ко всем чатам агента.
Содержимое вводится явно в UI/API. Изменение разрешено только во время активного
`planning`, до принятия плана. Это не даёт незаметно сделать ранее принятый план
или решение несовместимыми с новыми ограничениями. Обновление повышает версии
набора правил и workflow, отменяет старого кандидата ответа и пишет событие.

Проверки выполняются на трёх границах:

1. `input`: намерение пользователя до основного LLM-вызова;
2. `output`: ответ основной модели до его публикации;
3. `artifact`: отредактированный пользователем результат до перехода этапа.

При явном конфликте вместо запрещённого ответа сохраняется понятный отказ.
Невалидный JSON, отсутствие ключа или сбой judge дают `uncertain`: результат
не объявляется безопасным. Для текущего этапа можно повторить запрос.
Если активных правил нет, дополнительного вызова judge нет.

Реализация алгоритмического наставника находится в
`agents/algorithm_coach/validators/invariants.py` и
`agents/algorithm_coach/llm_judge/invariants.py`. Judge использует
`deepseek-v4-pro` через существующий ключ DeepSeek. Миграция `014_task_invariants.sql`
создаёт отдельные таблицы `task_invariant_sets`, `task_invariant_rules` и
`task_invariant_checks`; удаление задачи удаляет её правила каскадно.

Semantic judge — вероятностная проверка, не математическое доказательство
соблюдения произвольного текста правила. Локальная проверка пока распознаёт
явно неверную метку языка блока кода при сохранении решения; код не исполняется.
