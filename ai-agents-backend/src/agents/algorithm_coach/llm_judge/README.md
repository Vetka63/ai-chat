# Semantic judge алгоритмического наставника

`InvariantJudge` — отдельная LLM-проверка, а не второе решение задачи. Основная
модель может быть Flash или Mistral; judge выбирается независимо серверным
`PY_AGENT_JUDGE_MODEL` (по умолчанию `deepseek-v4-pro`). Используются существующие
серверные credentials соответствующего провайдера; клиент ключа не получает.

В judge уходят только system-инструкция проверки и JSON: stage, активные правила,
условие задачи, текущий workflow state и актуальные артефакты, профиль, проверяемый запрос либо пара
request/candidate. Вся история и долговременные записи не передаются. Секретный
ключ используется HTTP-клиентом для авторизации, не включается в prompt.

Например, правило R: «Не изменять nums». Запрос «объясни решение со словарём»
получит pass, просьба «отсортируй nums на месте» должна получить conflict. Для
кода с неясным поведением внешней функции ожидается uncertain. Каждый ответ judge
обязан содержать ровно одну оценку каждого ID:

```json
{"checks":[{"rule_id":"R","verdict":"conflict","reason":"Сортировка на месте изменяет исходный список nums"}]}
```

Pydantic проверяет форму, код — множество ID и отсутствие дубликатов. Лишнее
поле, пропущенный ID, markdown вместо JSON или усечённый ответ — ошибка проверки.
Повторной отправки автоматически нет. Это не «поиск слова pass» в тексте.

RecordedLlmCall сохраняет отдельные метрики invariant_input, invariant_output,
invariant_artifact, включая ошибки и фактический usage. Валидный verdict=conflict
означает успешный вызов judge, но отказ policy. У ошибочного judge audit.run_id
может отсутствовать; связь с run находится по memory_context.command_id.
Проверяемый отклонённый кандидат в аудите не сохраняется, но уходит провайдеру;
audit хранит правила и короткие причины. Это вероятностная оценка, не гарантия.

С Дня 15 в список всегда добавляется серверное правило `workflow-stage` с текущей
фазой. Например, «дай готовый код» на planning — конфликт, а на execution после
утверждения плана — допустимый запрос. При validation отчёт с описанной нерешённой
ошибкой и пустым `blocking_issues` должен отклоняться как противоречивый.
Judge видит актуальный план/решение/отчёт, но не весь журнал старых версий.
Один JSON обязан содержать оценки всех пользовательских правил и правила этапа
(максимум 20 + 1). Это те же вызовы, не отдельная цепочка для каждого правила.

Поэтому обычный ответ наставника теперь требует до трёх LLM-вызовов: input judge,
основной ответ, output judge. Сохранение артефакта — ещё один judge, если локальные
проверки прошли. Отсутствие пользовательских правил не отключает проверку этапа.
Ошибка формата основного кандидата блокирует его до output judge. Переходы,
пауза и принятие уже проверенной версии сами по себе не вызывают LLM.
