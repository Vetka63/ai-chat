# Лаборатория локальных LLM

Отдельное приложение для новой недели AI Advent Challenge. Backend — Kotlin / Spring Boot, клиент — Vue 3 / TypeScript.
Дни 26–27: независимые запросы и локальный чат с историей. День 29: лаборатория оптимизации технического экстрактора,
сравнение параметров/промптов/skill и Qwen3 4B FP16 против Q4_K_M, опционально DeepSeek. RAG дня 28 в этой ветке отсутствует.

## Запуск на Windows

Нужны Docker Desktop с Linux containers / WSL2 и драйвер NVIDIA для GPU. На проверенном компьютере: RTX 4080 SUPER, 16 ГБ VRAM, около 32 ГБ RAM. Для CPU можно не подключать `compose.gpu.yml`.

В PowerShell:

```powershell
cd F:\ai-advent-challenge\ai-chat\local-llm
./scripts/start-day29.ps1 -Model qwen3:4b-q4_K_M -Build
# Если нужен явный доступ к DeepSeek с ключом из ../.env:
./scripts/start-day29.ps1 -Model qwen3:4b-q4_K_M -Cloud
# Для отдельного FP16-прогона той же задачи и тех же настроек:
./scripts/start-day29.ps1 -Model qwen3:4b-fp16 -Cloud
```

Скачивание Q4 занимает около 2,6 ГБ, FP16 — 8,1 ГБ; это размеры весов на диске, не весь расход RAM/VRAM.
Для скачивания нужна сеть. Затем LOCAL работает локально без ключа; cloud-функции Ollama отключены.
DeepSeek доступен только при `-Cloud` и ключе `DEEPSEEK_API_KEY` (или существующем `LLM_API_KEY`) в локальном корневом `.env`.
Ключ не попадает в клиент и Git. Автоматического cloud fallback нет. Скрипт выгружает прежнюю модель и не удаляет данные/веса.

После переустановки Docker данные по решению пользователя остаются на C, исходники — на F.
Папка установки Docker Desktop на F не определяет расположение Linux data disk. Скрипт проверяет
фактический диск данных: минимум 20 GiB свободно, без автоматического удаления чего-либо.
Только проверка места, без перезапуска/скачивания: `./scripts/start-day29.ps1 -CheckOnly`.
Готовность проверяется через Docker CLI; backend/Ollama имеют health checks.

- UI: http://localhost:8483
- Backend: http://localhost:8482/api/v1
- Ollama: http://localhost:11436

В UI три раздела: «День 27 · Чат», «День 26 · Проверки», «День 29 · Оптимизация» (`/#optimization`).
Таблицы прежних `runs`, `chats`, `messages` остаются в `lab.sqlite`. Эксперименты дня 29 — в отдельной `optimization.sqlite`.
Результаты сохраняются на backend и доступны из разных браузеров, после перезапуска и смены активной локальной модели.

Перезапуск сохраняет завершённые результаты; незавершённые помечаются ошибкой без автоматической генерации. В чате неудачное сообщение пользователя остаётся видимым. Последний неуспешный ход можно повторить явно, без дублирования реплики. Удаление чата требует подтверждения и удаляет только его сообщения. Приложение рассчитано на одного локального пользователя, без аккаунтов; не публикуйте его API в интернет.

## Управление

```powershell
# Перезапустить только приложение этой недели
docker compose -f compose.yml -f compose.gpu.yml restart backend client
# Остановить только это приложение, сохранив модели и данные
docker compose -f compose.yml -f compose.gpu.yml stop
# Проверить фактическую загрузку модели на GPU
docker compose -f compose.yml -f compose.gpu.yml exec ollama ollama ps
```

В этой ветке активная локальная модель меняется серверной настройкой `OPT_LOCAL_MODEL` через скрипт запуска.
В памяти Ollama допускается одна модель и один запрос. Старые чаты с другой моделью сохраняются, но не смогут вызвать
неразрешённую текущей конфигурацией модель. Для исходной демонстрации дней 26–27 используйте их отдельные ветки.

Пустой лимит выхода в днях 26–27 не добавляет `num_predict` в запрос: используется настройка Ollama.
Контекст по умолчанию — 8192 токена, температура — 0,7, reasoning выключен. В лаборатории дня 29
output cap задаётся явно; кандидат использует 6144/512. Токены reasoning тоже входят в бюджет.
Обрезание (`done_reason=length`) отмечается `TRUNCATED`, даже если итоговый текст пуст:
thinking и usage сохраняются. Пустой ответ при нормальном stop — `FAILED`.
Размер prompt ограничен 16000 символами для первой лаборатории; это проверка размера HTTP-входа, не оценка токенов.

Чат передаёт полную историю завершённых ходов без сжатия. `truncate=false` запрещает Ollama молча выбрасывать начало переписки при превышении окна, `shift=false` запрещает сдвиг контекста во время генерации. Переполнение может дать явную ошибку или незавершённый ответ; оно не удаляет сохранённую историю. Модель фиксируется при создании чата, остальные параметры можно менять перед каждым сообщением. Сведения из других чатов не передаются.

## Восстановленные данные и резервные копии

После переустановки Docker прежние volumes были удалены пользователем. В текущую SQLite офлайн
импортированы восемь старых серий дня 29 из независимых JSON на F, без новых LLM-вызовов.
Старые чаты дней 26–27 не восстановлены; новые демонстрации памяти/изоляции сохранены в текущем UI.
Чат памяти: `/#chat/f5b6a1f8-5bd7-44d4-bfdd-d88f01ffb22b`.
В текущей ветке Q4 доступна всем трём экранам; исходные ветки 26/27 имеют свой конфиг моделей.

`scripts/restore-day29-results.py` — административная утилита stdlib Python, не часть Kotlin backend.
Она импортирует только terminal result.json, пропускает идентичные UUID, отклоняет конфликты
и не пересчитывает ответы/оценки. Использовать на отдельной копии SQLite при остановленном backend:

```powershell
python ./scripts/restore-day29-results.py --artifacts ./artifacts --database ./artifacts/restored-copy.sqlite
python -m unittest discover -s ./scripts/tests -v
```

Этот пример создаёт отдельную копию, не заменяет живую БД. Если result.json и уже сохранённый UUID
различаются (например, вывод отредактирован позже), импорт прекращается без перезаписи результата.
В Docker volume находятся `lab.sqlite` и `optimization.sqlite`; проверенные независимые копии —
`artifacts/recovery-20261008/final-data`. Эти файлы и JSON artifacts исключены из Git.
Нельзя считать named volume резервной копией: Docker uninstall/reset и `down -v` могут удалить данные.

Официальные источники: [Ollama chat API](https://docs.ollama.com/api/chat), [qwen3:8b](https://ollama.com/library/qwen3:8b), [GPU в Docker Desktop](https://docs.docker.com/desktop/features/gpu/).
