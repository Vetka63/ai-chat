# Домен chat — день 27

## Что добавлено

Обычный диалог с локальной Qwen через Ollama. Память — это сообщения SQLite, которые backend передаёт заново при каждом запросе. Модель не обучается на этих сообщениях и не хранит сессию сама. Аккаунтов и облачных вызовов нет.

## Классы

| Файл | Роль |
| --- | --- |
| `Contracts.kt` | `Chat`, `ChatMessage`, DTO создания/отправки, исключения домена |
| `ChatController.kt` | REST API; валидация нового сообщения; не принимает историю от браузера |
| `ChatService.kt` | Подготовка хода, дедупликация, локальный вызов, сохранение результата, retry |
| `ChatRepository.kt` | SQLite, внешние ключи, порядок сообщений, атомарные операции |
| `ChatContextBuilder.kt` | Системная инструкция и сообщения одного чата |

Общие `Generation`, `RunStatus`, `LlmMessage`, `LlmChatRequest` и `LocalLlmRuntime` лежат в `generation`. `GenerationGate` делит один слот между чатом и лабораторией. HTTP-реализация runtime — `runtime/OllamaRuntime`.

## Как получается память

Первый вызов:

```text
SYSTEM: инструкция локальному ассистенту
USER: Меня зовут Сергей. Собираюсь в Казань на три дня.
```

После ответа в БД появятся USER и ASSISTANT. Второй вызов:

```text
SYSTEM: та же инструкция
USER: Меня зовут Сергей. Собираюсь в Казань на три дня.
ASSISTANT: Сергей, условия поездки приняты.
USER: На сколько дней я собираюсь?
```

После перезапуска backend читает те же строки SQLite и собирает такой же контекст. Новый чат получает собственную системную инструкцию и собственные сообщения: сведений о Сергее в нём нет.

## Хранилище

- `chats`: ID, время изменения, JSON с названием, моделью и системным prompt.
- `messages`: ID, chat_id, порядковый номер, request_id, role, status, JSON реплики/параметров/метрик.
- `runs`: старые независимые запуски дня 26; используются отдельным репозиторием.

`UNIQUE(chat_id, ordinal)` защищает порядок; `UNIQUE(chat_id, request_id, role)` — от повторных реплик. Внешний ключ с `ON DELETE CASCADE` удаляет сообщения только выбранного чата. Завершение хода обновляет USER и добавляет ASSISTANT одной транзакцией. БД лежит в volume `local-data`, а не в Git.

## Ошибки и повтор

USER сохраняется **до** долгого LLM-вызова. При сбое его статус становится FAILED, текст и параметры остаются на экране. Ошибка не является сообщением модели и не входит в последующий контекст.

Отправка того же `requestId` с тем же телом возвращает уже сохранённый результат, не вызывает модель ещё раз. Другое содержимое с этим ID даёт 409. Для реального повторного получения ответа есть отдельный `/retry`: он работает только для последнего FAILED хода и не добавляет второго USER. Старую ошибку нельзя повторить после более поздних сообщений — иначе изменился бы смысл последующего контекста.

При перезапуске незавершённые RUNNING помечаются FAILED. Скрытого повторного вызова нет; пользователь выбирает retry сам.

## Ограничения

Модель выбирается при создании чата; температура, reasoning и максимум ответа — для каждого нового хода. Пустой максимум не задаёт `num_predict`. Окно сейчас 8192 токена; автоматической суммаризации и удаления старых сообщений нет. `truncate=false` запрещает тихое сокращение входной истории, `shift=false` — вытеснение её во время генерации. Переполнение сообщается как ошибка или незавершённый ответ. История в SQLite от этого не удаляется.

Общее ограничение — одна генерация на экземпляр backend. Это намеренная защита одной локальной GPU, не распределённый scheduler. Приложение не публикуется в интернет: доступа по аккаунтам и пользовательского разграничения здесь нет.

Ollama API и параметры сверены с [исходным контрактом v0.35.1](https://github.com/ollama/ollama/blob/v0.35.1/api/types.go).
