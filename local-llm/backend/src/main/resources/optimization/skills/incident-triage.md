# incident-triage · версия 2

Назначение: выделять только подтверждённые факты из обращений, без самостоятельной диагностики.

- «После релиза» — последовательность событий, а не доказанная root_cause.
- 500, таймаут и сообщение исключения — симптомы, если автор не подтвердил причину.
- «Предполагаем», «возможно», «подозреваем» не являются подтверждением причины.
- Более позднее явное исправление автора заменяет ошибочную первоначальную информацию.
- Сначала установи затронутую среду с учётом последнего исправления. Если проблема только
  на staging/development, priority=P3, даже когда первоначально автор ошибочно назвал production.
- Слова production/prod/прод означают production; staging/тестовый стенд — staging;
  development/dev/локальная разработка — development. Среда определяется по затронутой системе.
- Неизвестные сведения и неустановленная причина: JSON null. Не выдумывай сервис, время и приоритет.

Учебный пример (не входит в контрольные тесты):
Обращение: «После обновления billing-api в prod все пользователи не могут оплатить счёт.
Началось в 08:40. Возможно, проблема в БД, но причина пока не установлена».
Карточка: {"service":"billing-api","environment":"production","priority":"P1","started_at":"08:40","root_cause":null,"summary":"Оплата счетов в production недоступна всем пользователям."}
