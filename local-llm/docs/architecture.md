# Архитектура лаборатории локальных LLM

## Границы приложения

`local-llm` — отдельная папка рядом с `rag`, со своими `backend`, `client`, compose-проектом `ai-chat-local-llm` и томами `local-models` / `local-data`. День 26 реализован в `ai-challenge-day-26`, день 27 — в дочерней `ai-challenge-day-27`. Следующие расширения определяются после получения заданий. День 27 сохраняет прежний HTTP API и отдельный экран лабораторных запусков.

Внешняя зависимость для генерации одна — локальная Ollama. Интернет нужен при установке библиотек и весов; во время генерации backend обращается к `http://ollama:11434` внутри Docker-сети. На Windows этот runtime доступен на `127.0.0.1:11436`. Облачных ключей, DeepSeek-клиента и cloud fallback в проекте нет.

## Пакеты backend

| Пакет / класс | Назначение |
| --- | --- |
| `config/LabProperties` | Адрес runtime, разрешённые модели, SQLite, timeout, контекст |
| `generation/LocalLlmRuntime` | Граница между приложением и конкретным движком локальной модели |
| `generation/Contracts` | Типы запроса, результата и состояния выполнения |
| `generation/GenerationService` | Сохранение запуска, вызов runtime, классификация и сохранение фактического исхода |
| `generation/GenerationGate` | Общий слот для лаборатории и чатов: одна генерация на экземпляр backend |
| `runtime/OllamaRuntime` | `/api/tags`, `/api/show`, `/api/chat`; преобразование HTTP-ответа в доменный результат |
| `runs/RunRepository` | SQLite-запросы, история запусков и восстановление после перезапуска |
| `web/LabController` | HTTP API для UI и внешних клиентов; сценарии дня 26 |
| `web/Errors` | Понятные ошибки валидации и занятости |
| `chat/ChatController` | Создание, чтение, удаление чатов; отправка нового сообщения и явный retry |
| `chat/ChatService` | Серверный флоу диалога, идемпотентность и сохранение фактического исхода |
| `chat/ChatRepository` | Отдельные таблицы `chats` / `messages`, порядок, транзакции и восстановление |
| `chat/ChatContextBuilder` | Системная инструкция + реплики только выбранного чата + текущее сообщение |

## Последовательность одного запроса

1. UI получает runtime, сценарии и список прошлых запусков через backend.
2. Пользователь выбирает установленную модель и сценарий либо пишет свой prompt.
3. `POST /api/v1/runs` проходит валидацию. В первой версии генерации выполняются по одной; второй параллельный запрос получает 409, очереди и скрытого повторения нет.
4. Service создаёт UUID, сохраняет запрос со статусом `RUNNING` и запускает измерение времени.
5. Адаптер проверяет allowlist, наличие локальных весов и способность генерировать текст. Каждый запрос содержит только одно пользовательское сообщение.
6. Ollama получает `/api/chat`, `stream=false`, выбранные параметры и контекст 8192. `num_predict` передаётся только при явном выборе пользователем.
7. Ответ Ollama содержит текст, причину завершения, input/output tokens и временные метрики. Наносекунды переводятся в миллисекунды. Tokens/sec = eval_count / eval_duration; это скорость декодирования, не скорость всего HTTP-запроса.
8. `done_reason=stop` → `COMPLETED`, `length` → `TRUNCATED`, пустой/невалидный ответ или ошибка runtime → `FAILED`. Ошибка не является полезным ответом модели. Автоматический retry не выполняется.
9. Итог сохраняется в SQLite и возвращается UI. Открытие истории не запускает модель.

Состояние `COMPLETED` означает завершённую генерацию с непустым текстом. Оно не является оценкой истинности: для контрольных задач в UI отдельно показано ожидаемое содержание.

## API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/v1/runtime` | Связь, версия Ollama, установленные разрешённые модели |
| `GET /api/v1/scenarios` | Три контрольных запроса и ожидания |
| `POST /api/v1/runs` | Новый запуск, ответ / ошибка и метрики |
| `GET /api/v1/runs` | Список сохранённых запусков |
| `GET /api/v1/runs/{id}` | Полный фактический результат |
| `GET /api/v1/runs/{id}/report` | MD-файл с сохранённым ответом, параметрами и метриками; без вызова модели |
| `GET /actuator/health` | Здоровье backend; доступность Ollama показывается отдельно в runtime |

SQLite `runs` хранит UUID, дату и полный JSON payload с запросом и результатом. HTTP API не предоставляет удаления. При старте прежние `RUNNING` становятся `FAILED` с сообщением о перезапуске. Полезные завершённые записи остаются без изменений.

## Frontend

`api.ts` содержит общий HTTP-контракт, `App.vue` — переключатель разделов, `features/lab/LabView.vue` — сохранённый экран дня 26, `features/chat/ChatView.vue` — переписку дня 27. Чат имеет свой API-модуль и CSS. Слева список диалогов, в центре сообщения и поле ввода, справа скрываемые настройки. Переписка и список имеют отдельный скролл; открытие и новый ответ прокручивают переписку вниз. На узком экране настройки открываются отдельной панелью и закрываются собственной кнопкой. Выбранный чат закрепляется в URL (`#chat/<id>`), а сами сообщения всегда читаются с сервера. HTML модели выводится как текст и не исполняется.

## Контекстный диалог дня 27

1. `POST /api/v1/chats` фиксирует модель и системную инструкцию нового чата.
2. Клиент отправляет только новое сообщение, параметры и UUID `requestId` в `POST /api/v1/chats/{id}/messages`. Произвольные roles/history/system prompt от клиента не используются.
3. `ChatService` проверяет requestId. Повтор уже завершённого запроса возвращает сохранённый чат; тот же ID с другим содержимым даёт HTTP 409. Повтор RUNNING не запускает ещё одну модель.
4. Под общим `GenerationGate` USER сохраняется до обращения к Ollama.
5. `ChatContextBuilder` собирает системную инструкцию, завершённые реплики в порядке БД и новый USER. Ранее FAILED ходы видны на экране, но не становятся контекстом. Реальные TRUNCATED ответы передаются с дальнейшей историей; UI предупреждает об их неполноте. Reasoning и диагностические ошибки не подмешиваются в messages.
6. `OllamaRuntime.chat` отправляет `messages`, `stream=false`, `think`, `num_ctx=8192`, `truncate=false`, `shift=false`. Запрос остаётся локальным, без fallback.
7. При успехе статусы USER и ASSISTANT сохраняются одной транзакцией; при ошибке остаётся USER с FAILED и причиной. Метрики фактического вызова хранятся у ASSISTANT.
8. HTTP-ответ возвращает полный обновлённый чат. Потеря связи не означает, что сервер не сохранил результат: UI сначала перечитывает чат и при неопределённости позволяет отправить тот же ID, а не новый.
9. `POST /api/v1/chats/{id}/messages/{requestId}/retry` — явный повтор только последнего FAILED хода, с его сохранёнными параметрами и той же USER-записью.
10. `DELETE /api/v1/chats/{id}` каскадно удаляет его messages. Удаление блокируется во время генерации. Лабораторные `runs` и другие чаты не затрагиваются.

SQLite и GenerationGate рассчитаны на один экземпляр backend. Для нескольких реплик потребуются распределённые блокировки/очередь и другой способ восстановления RUNNING. Авторизации нет: это локальное учебное приложение с портами на `127.0.0.1`.

Полное описание: [README домена chat](../backend/src/main/kotlin/dev/aichallenge/local/chat/README.md).

## Расширение

Новую задачу недели можно добавить отдельным доменным пакетом и экраном, используя интерфейс `LocalLlmRuntime` и историю измерений. Другой локальный runtime реализует этот интерфейс. Memory, RAG, fine-tuning, сравнение моделей или tool calling не смешиваются с транспортом Ollama и добавляются только когда понадобятся по заданиям.
