# День 29: лаборатория оптимизации, без RAG

Ветка `ai-challenge-day-29` создана от `ai-challenge-day-27`. Реализация дня 28 сохранена
отдельным checkpoint-коммитом в своей ветке. Эта лаборатория не импортирует книги и не использует embedding/index/retrieval.

## Задача и критерии

Локальная LLM превращает синтетическое техническое обращение в карточку:
`service`, `environment`, `priority`, `started_at`, `root_cause`, `summary`.
Среда и приоритет имеют закрытые множества значений; неизвестное значение — JSON null.
Причина извлекается дословно только при явном подтверждении. Симптомы и гипотезы не превращаются в причины.
Резюме должно быть русским, непустым, до 240 символов; его смысл проверяет человек.

20 тестов версионированы в `backend/src/main/resources/optimization/cases.json`:
10 calibration для настройки, 10 holdout для итогового сравнения. Эталон не включается в LLM-сообщения.
Длинные входы содержат детерминированный шум, а не случайно меняющиеся данные.
Результаты не исправляются и не фильтруются для красивой демонстрации.

## Границы модулей

| Пакет | Назначение |

| `optimization/config` | Активная локальная модель, отдельная БД, флаг облака и ключ |

UI расположен в `client/src/features/optimization`; старые чат и лаборатория остаются отдельными экранами.

## Алгоритм запуска

1. Клиент выбирает provider, prompt profile, skill и настройки; локальная модель берётся из startup-конфига backend.
2. Клиент заранее сохраняет UUID-квитанцию в localStorage и делает один POST.
3. Backend сначала проверяет UUID: тот же запрос возвращает сохранённый эксперимент, другой — ошибку.
4. Проверяет вход и серверную доступность провайдера; резервирует общий `GenerationGate`.
5. Фиксирует model digest, quantization, runtime version, точные сообщения и SHA256 каждого prompt.
6. Сохраняет RUNNING в SQLite, возвращает HTTP 202 и передаёт lease фоновой virtual thread.
7. Для каждого case сохраняет RUNNING, делает ровно один LLM-вызов, оценивает сырой ответ, сохраняет итог.
8. Для LOCAL отдельно семплирует `/api/ps` каждые 250 мс. Telemetry не содержит prompts и не вызывает модель.
9. Клиент читает состояние примерно каждые 900 мс. Ошибка polling не вызывает повторную генерацию.
10. После последнего case сохраняется terminal status и освобождается слот. Чаты и другие эксперименты не конкурируют за GPU.

При перезапуске незавершённый эксперимент становится INTERRUPTED. Завершённые cases остаются сохранёнными;
оставшиеся не перезапускаются автоматически. Для нового прогона нужен новый UUID.
При неопределённом результате POST клиент сначала делает GET квитанции. Явный повтор того же UUID безопасен.

## Что означает результат

- `COMPLETED`: модель вернула завершённый текст. Это не утверждение о правильности.
- `TRUNCATED`: provider сообщил `length`; частичный текст (вплоть до пустого итогового answer)
  сохраняется вместе с Thinking и usage, не считается точной завершённой карточкой.
- `FAILED`: ошибка вызова, включая переполнение окна или отсутствие runtime.
- `validJson`: один JSON без Markdown, дублей ключей и хвостового текста.
- `validSchema`: ровно шесть ключей, корректные типы и enum, непустое резюме до 240 символов.
- `matchedFields`: точное сравнение пяти ожидаемых полей. Синоним в root_cause может дать несовпадение;
  поэтому контракт требует дословную причину, а ручной анализ всё равно необходим.
- `exactFields`: совпали пять полей и схема корректна. Это не автоматическая оценка смысла summary.
- В UI неудачные случаи входят в знаменатель качества; latency-медиана считается только по COMPLETED.

## Ресурсы и применимые параметры

Ollama принимает temperature, num_predict, num_ctx, thinking, top_p, top_k, seed.
Передаются `truncate=false` и `shift=false`: недостаточное окно даёт ошибку, а не молчаливое удаление входа.
Seed фиксируется, но побитовая повторяемость между runtime/железом/квантованиями не обещается.

`/api/ps` возвращает model allocation `size`, `size_vram` и фактическое `context_length`.
Sampler сохраняет наблюдавшийся максимум только для запрошенного context_length. При смене окна
кадры старой конфигурации не учитываются; краткие переходные расходы загрузки сюда не входят.
Это **не RSS процесса, не общий RAM контейнера и не физический peak всей видеокарты**.
`size - size_vram` — оценка non-VRAM части allocation, не измеренный RSS. Отсутствующие метрики показываются как «—», не 0.
Время runtime, загрузка и токены/с берутся из ответа Ollama; полное время включает HTTP, метаданные и завершение sampler.
Холодную загрузку нужно рассматривать отдельно от прогретых вызовов.

DeepSeek получает те же task messages и skill, но не фиктивные локальные параметры.
Для v4: без thinking применяется temperature, top_p фиксирован 1; с thinking temperature не действует,
top_p не ниже 0.95, reasoning_effort=high. context window/top_k/seed не передаются.
Серверные RAM/VRAM и generation-only скорость облака неизвестны. Показываются полное время и API usage.
Токенизаторы провайдеров различаются, поэтому число токенов не является универсальной единицей объёма текста.

Источники: [Ollama API](https://docs.ollama.com/api/chat), [runtime allocation](https://docs.ollama.com/api/ps),
[DeepSeek v4 параметры](https://api-docs.deepseek.com/guides/thinking_mode/).

## Skills и безопасность

`incident-triage.md` — локальный пакет правил с одним учебным примером, не fine-tuning и не плагин Codex.
Загружается только из classpath; клиент не может передать путь к произвольному файлу, URL или shell-команду.
Skill можно включить для любой модели одинаково. Сохраняются его ID, версия и hash.
Технический Qwen chat template/служебные токены не изменяются: меняется task prompt.
Специализированный шаблон повторяет краткое задание после длинного обращения, чтобы снизить эффект
отвлекающих логов; это общая инструкция для любого input, а не подстановка эталонных ответов.

Облако по умолчанию выключено, включается явно; ключ читается из env backend, не попадает в DTO/prompt/SQLite/MD.
HTTP-ошибки DeepSeek обезличены. Никакого cloud fallback, hidden judge, автоматических повторов нет.
SQLite, runtime artifacts, тексты и `.env` исключены из Git и Docker build context.
Модели проверяются как локальные: cloud tags Ollama запрещены. Контейнеры доступны только через localhost.

## Методика сравнения

1. На calibration сравнить prompt отдельно, затем skill отдельно, затем temperature/max tokens/context отдельно.
2. Зафиксировать кандидат до итогового прогона holdout. Кандидат может ухудшить результат — это тоже вывод.
3. Для FP16/Q4 использовать **ту же архитектуру Qwen3 4B, тот же input/prompt/settings/thinking/skill**, sequential запуск.
4. При смене startup-модели результаты остаются в `optimization.sqlite`; UI позволяет выбрать сохранённый запуск для сравнения.
5. DeepSeek — дополнительный reference, а не доказательство влияния квантования.
6. Не менять baseline на заведомо плохие значения для красивого «после». Не удалять ошибки из отчёта.
7. Меньший max tokens — потолок, не обещание ускорения: если обе модели закончили раньше, сам потолок ничего не экономит.
8. Меньший контекст экономит память лишь при достаточном окне для реального input+output. Проверять длинные cases.

Архитектура добавляет следующую задачу новым skill, каталогом и evaluator, а не копированием HTTP-клиентов и хранения.
