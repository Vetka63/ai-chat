# День 29: понятный сценарий проверки и видео

## Подготовка

Ветка `ai-challenge-day-29`, папка `F:\ai-advent-challenge\ai-chat\local-llm`.
Docker Desktop должен работать. Для GPU используем `compose.gpu.yml`.
Секретный ключ хранится в корневом `.env`, не показывайте этот файл на видео.

```powershell
cd F:\ai-advent-challenge\ai-chat\local-llm
./scripts/start-day29.ps1 -Model qwen3:4b-q4_K_M -Build -Cloud
```

Для полностью локального режима уберите `-Cloud`. Скрипт загрузит недостающие веса, затем поднимет backend/client.
Если эксперимент ещё RUNNING, скрипт попросит дождаться его завершения, а не прервёт работу.
Открыть `http://localhost:8483/#optimization`.

## Основная демонстрация: оптимизация под задачу

1. Откройте «День 29 · Оптимизация». Справа видно активную модель Qwen3 4B Q4_K_M.
2. Нажмите «Базовый профиль». Его настройки: temperature 0.7, output cap 1024, context 8192,
   thinking выключен, top_p 0.8, top_k 20, seed 42, базовый prompt, skill выключен.
3. В блоке тестов выберите «Контрольный · 10» и «Выбрать весь набор». Своё обращение оставьте пустым.
4. Нажмите «Запустить эксперимент». UI показывает последовательное выполнение всех 10 случаев.
5. Дождитесь terminal status. Покажите: количество завершённых вызовов, точные карточки, поля, схему,
   latency, VRAM. Выберите конкретную вкладку h01/h03/h07/h09 и раскройте исходное обращение.
6. Покажите, что неизвестная причина остаётся null; staging не превращается в production;
   текст команды внутри лога не должен менять контракт ответа. Если модель ошиблась — UI показывает несовпадение.
7. Нажмите «+ Новый эксперимент». Выберите «Кандидат оптимизации» либо настройки зафиксированного кандидата
   из `day29-verification.md` (окно 6144, output cap 512, temperature 0.7, skill включён).
   Выберите **тот же набор и число повторов**. Запустите.
8. В «Сравнить с сохранённым экспериментом» выберите базовый запуск. Ответы одного обращения и метрики видны рядом.
9. UI предупреждает, что менялись prompt/skill/parameters: это общий эффект оптимизации, не доказательство
   эффекта какого-то одного параметра. Для отдельного temperature/prompt/skill теста меняйте только его.
10. Выберите длинный h10. Слишком маленькое окно может дать FAILED; не скрывайте это — увеличьте окно
    и сделайте **новый** эксперимент. Не называйте ухудшившийся профиль оптимальным.
11. Заполните «Мой вывод», «Сохранить вывод», «Скачать MD». Обновите страницу: результат и вывод остаются.

Настройку кандидата выполняют на calibration; итоговый holdout не используют для подбора параметров.
Готовые сохранённые результаты позволяют показать сравнение на видео без повторных запросов.
Даты, exact model digest, prompt hash и параметры доступны в деталях и MD.

## Квантованная против FP16 — отдельный эксперимент

1. На Q4 запустите выбранный набор с зафиксированными настройками, prompt и skill.
2. После завершения в PowerShell:

```powershell
./scripts/start-day29.ps1 -Model qwen3:4b-fp16 -Cloud
```

3. Обновите UI. Справа должно быть `qwen3:4b-fp16`, quantization `F16`.
4. Откройте прежний Q4-эксперимент: настройки нового запуска скопируются из него,
   но справа активной моделью останется FP16. Нажмите «Запустить эксперимент».
5. Выберите Q4-результат для сравнения. При одинаковом input/prompt/settings не должно быть предупреждений
   о смешении параметров; модели должны иметь одинаковый размер 4B и разные quantization/digest.
6. Покажите качество, память, токены/с и время загрузки. Первый вызов каждой модели может быть холодным.
7. FP16 — float16 без низкобитного integer-квантования, не FP32. Не сравнивайте Q4 4B с FP16 8B как эффект квантования.

## Сравнение с DeepSeek

1. Справа выберите «DeepSeek API», затем Pro или Flash. Проверьте то же обращение/набор, prompt и skill.
2. На UI есть предупреждение о платной передаче текста. Не вставляйте реальные рабочие логи с секретами.
3. Запустите и выберите локальный сохранённый результат для сравнения.
4. Покажите ответы/поля/латентность/usage. Ресурсы облачного сервера отмечены «—», не нулём.
5. Окно контекста, top K, seed не применяются к DeepSeek. Temperature в thinking не влияет;
   top P действует только в thinking с нижним порогом 0.95. Это отражено в UI и MD.
6. Это сравнение разных моделей/провайдеров, а не квантования.

## Повторы и воспроизводимый CLI

Каждый POST запускает только выбранные cases × repetitions; максимум 20×3.
Независимые прогоны не используют историю предыдущих запросов и не кешируют ответы.

```powershell
./scripts/verify-day29.ps1 -Provider LOCAL -PromptProfile BASELINE -Split calibration -ContextSize 8192 -MaxTokens 1024
./scripts/verify-day29.ps1 -Provider LOCAL -PromptProfile SPECIALIZED -Skill -Split calibration -ContextSize 6144 -MaxTokens 512
```

По умолчанию создаётся новая ignored-папка artifacts с квитанцией и result.json.
Повтор с **тем же** `-OutputDirectory` и настройками читает существующий UUID и не генерирует заново.
Не используйте старую папку для изменённых параметров. Новый прогон — новая папка.

## Что важно не перепутать

- COMPLETED не равно верному ответу: смотрите schema и matchedFields.
- Пять полей оцениваются автоматически; смысл summary — вручную.
- Память в UI — sampled model allocation Ollama, не RSS процесса и не весь расход видеокарты.
- Низкий output cap может обрезать JSON; лимит сам по себе не ускоряет ответ, завершившийся раньше него.
- Одинаковый seed не гарантирует один и тот же ответ для другой precision/runtime/GPU.
- Для вывода о стабильности нужен набор и несколько повторов, не один удачный пример.

Остановить приложение без удаления данных:

```powershell
docker compose --env-file ../.env -f compose.yml -f compose.gpu.yml stop
```
