## 1. Цель и границы недели

Добавить агента, который хранит отдельно переписку, данные задачи и долговременные знания; использует профиль пользователя; восстанавливает этап работы; соблюдает инварианты и правила переходов.

У приложения уже есть состояние: история, summary, facts и checkpoint хранятся в SQLite. Новая часть — явная модель **задачи**, её артефактов, обязательств и допустимых действий. LLM получает снимок состояния при запросе; источником истины остаётся backend и его хранилище.

Основные проекты: `ai-agents-backend` (Python, FastAPI, Pydantic, SQLite) и `ai-agents-client` (Vue). Java-проект и прежний клиент продолжают существовать. Новая реализация использует текущий UI и инфраструктуру LLM; LangChain и LangGraph для этих заданий не нужны.

## 2. Предлагаемый сценарий: алгоритмический наставник

Рекомендуемое направление — `AlgorithmCoachAgent`, агент для разбора и решения алгоритмических задач. Его полезный результат: условие, согласованный план, решение, оценка сложности и отчёт проверки. Пользователь может вернуться к задаче позже без повторного объяснения.

Пример на всю неделю: задача в стиле Two Sum. Даны массив целых чисел и target. Вернуть индексы двух разных элементов с нужной суммой либо пустой список. При нескольких решениях допустима любая подходящая пара. Условие вводится текстом; интеграция с аккаунтом LeetCode и автоматическое получение заданий не требуются.

| Возможность | Пример для алгоритмического наставника |
| --- | --- |
| Краткосрочная память | «Почему в этом месте проверяем словарь до добавления элемента?» |
| Рабочая память | Условие Two Sum, примеры, ограничения, подход через словарь, код, найденный контрпример |
| Долговременная память | «Изучаю хеш-таблицы», сохранённая заметка о приёме поиска дополнения |
| Профиль | Новичку — подробные примеры; опытному — короткое обоснование и сложность |
| Состояние | Обсудили план, начали реализацию, остановились перед проверкой дубликатов |
| Инварианты | Python, фиксированная сигнатура функции, запрет сторонних библиотек, исходный массив не изменять |
| Контроль переходов | Запрос «сразу дай готовый код» при неутверждённом плане не запускает реализацию |

Назначение сохраняемых решений обязательно явно: «для этой задачи используем словарь» относится к рабочей памяти; «предпочитаю сначала подсказку» относится к профилю. Выбор алгоритма одной задачи не становится глобальным правилом.

Альтернатива, если важнее обсуждать архитектуру приложений: ассистент подготовки ТЗ и технического плана. Он естественно демонстрирует ограничения по стеку и бизнес-правила, но качество его решений сложнее проверить на конкретных примерах. Предлагаемый план использует алгоритмического наставника; выбор предметной области ещё можно скорректировать до реализации.

### Проверка алгоритма и выполнение кода

Для обязательного объёма недели агент анализирует решение, составляет тестовые случаи и сохраняет `ValidationReport`. В отчёте явно указан способ проверки:

- `llm_review` — проверка моделью, код не исполнялся;
- `user_test_result` — результат запуска, явно предоставленный пользователем;
- `automated_execution` — резерв для будущего изолированного исполнителя.

Pydantic подтверждает формат, AST-проверка — синтаксис и некоторые ограничения, LLM-review — только оценку модели. Ни один из этих шагов сам по себе не доказывает корректность на всех входах. В UI и отчёте запрещено называть LLM-review успешным запуском тестов. Пользователь принимает отчёт с указанием его источника.

Изолированное выполнение Python-кода можно добавить отдельной итерацией, если это будет нужно для обучения. В текущий план оно не входит: вызов `exec` в процессе backend для сгенерированного кода не используется.

## 3. Что переиспользовать и что изменить

В текущем коде уже есть `AgentRegistry`, контракт `Agent.run`, `LlmClient`, маршрутизация DeepSeek/Mistral, SQLite-хранилища и учёт токенов. `DialogueAgent` получает зависимости через фабрику. Это подходящая основа для ещё одного агента.

Есть границы, которые нужно учитывать:

- `ContextMemory` сейчас выбирает один из пяти способов сборки истории. Он не управляет сущностями задачи и профиля.
- Sticky Facts принадлежат одному чату и переписываются LLM целиком. Это не подтверждённые долговременные знания пользователя.
- Публичные `Message` содержат только роль и текст. Для происхождения новых записей памяти понадобится стабильный идентификатор сохранённого сообщения; номер в списке для этого недостаточен.
- `AgentResult` уже содержит поля summary/facts. Не следует добавлять в него все DTO задач, профилей и инвариантов: их состояние получит отдельный API рабочего пространства.
- В `application/main.py` многие действия напрямую вызывают хранилища. Изменения рабочей памяти и состояния задачи должны проходить через прикладные сервисы, применяющие правила агента.
- Текущие `asyncio.Lock` действуют только внутри процесса. Для записей состояния дополнительно нужны версии и транзакции SQLite.

Добавляем самостоятельный `agents/algorithm_coach`, зарегистрированный рядом с `dialogue`. Он использует общие порты и сервисы по композиции. Не наследуем всю реализацию `DialogueAgent` и не дублируем его HTTP-вызовы и подсчёт стоимости: переиспользуем инфраструктуру, а повторяющийся учёт одного LLM-вызова при необходимости выделяем в небольшой общий сервис.

Для нового агента на этой неделе используем последние N сообщений как краткосрочный контекст плюс явно выбранные слои памяти. Имеющиеся стратегии Дней 9–10 остаются доступны у диалогового агента. Совмещение Branching с задачами и инвариантами требует собственной семантики копирования и в эту неделю не включается.

## 4. Границы модулей и структура

Предметные правила, промпты, input/output policy, валидаторы и семантический judge принадлежат конкретному агенту. Переиспользуемые механизмы имеют общие контракты: хранилище памяти, сборка блоков контекста, автомат, проверка ограничений. Для каждого модуля добавляется README; классы и нетривиальные методы описываются по-русски.

Целевая структура создаётся постепенно, по мере появления соответствующих заданий:

```text
ai-agents-backend/src/
  agent_core/                         # базовые контракты агента и LLM
  agents/
    dialogue/                        # агент Дней 6–10
    algorithm_coach/
      agent.py                       # координация одного обращения
      factory.py                     # сборка его зависимостей
      config.py
      models.py                      # ProblemSpec, Plan, Solution, Review
      input_policy.py
      output_policy.py
      memory_policy.py               # что разрешено писать в каждый слой
      workflow_policy.py             # события, проверки, требования к артефактам
      validators/                    # схема, AST, сигнатура и правила задачи
      llm_judge/                     # семантическая проверка ограничений с Дня 14
      prompts/                       # ответ, извлечение, review, инварианты
      README.md
  capabilities/
    context_memory/                  # существующие стратегии истории
    token_accounting/                # существующий учёт, дополнительные purpose
    memory_layers/                   # с Дня 11: слои, предложения записи, provenance
    personalization/                 # с Дня 12: профиль и применение предпочтений
    task_workflow/                   # с Дня 13: состояние, события, переходы
    invariants/                      # с Дня 14: контракт правила и результат проверки
  application/
    bootstrap.py
    main.py                          # сборка приложения и подключение роутеров
    routes/                          # новые API памяти, профилей и задач
  infrastructure/
    sqlite_*.py                      # адаптеры портов
    migrations/                      # версионированные изменения схемы с Дня 11
```

Внутри новых `capabilities/*` — собственные `models.py`, `contracts.py`, сервис и README. Не создаём пустые пакеты заранее. Не заводим новый общий контейнер `utils` для доменных правил. Когда второй агент потребует похожую функцию, он сможет подключить capability со своей политикой.

В экземпляре агента находятся конфигурация и зависимости. Изменяемые профиль, задача и память загружаются по идентификаторам на каждый запуск. Поэтому один зарегистрированный агент может обслуживать множество изолированных задач. «100 агентов» не требует 100 процессов или копий всей истории в RAM. Распределённые workers, очередь и отдельные сервисы остаются следующим масштабом; первая реализация запускается одним процессом с SQLite.

## 5. Модель памяти и область владения

Для учебного локального приложения вводим `profile_id`. На Дне 11 создаётся один профиль с именем; на Дне 12 добавляются редактируемые предпочтения и несколько профилей. Это локальные персоны для экспериментов, а не система аутентификации разных пользователей.

MVP: одна задача — один связанный чат. Новая задача получает отдельную рабочую память. Профиль выбирается при создании задачи и фиксируется у неё. Открытие существующего чата продолжает ту же задачу; новая задача того же профиля видит подходящую долговременную память, но не рабочие данные старой задачи.

| Слой | Область | Хранение | Как записывается | Что попадает в LLM |
| --- | --- | --- | --- | --- |
| Краткосрочная память | `agent_id + conversation_id` | существующая таблица `messages` | каждое сообщение сохраняется автоматически | последние N сохранённых сообщений и новый запрос ровно один раз |
| Рабочая память | `agent_id + profile_id + task_id` | `tasks`, `task_memory`, `task_artifacts` | подтверждённые структурированные данные условия, план, решение и результаты проверок | актуальное условие, решения, текущие артефакты и состояние |
| Долговременная память | `profile_id + agent_id` | `long_term_memory`; профиль отдельно в `profiles` | явное добавление/редактирование или подтверждение предложения | выбранные активные заметки и предпочтения профиля |

«Краткосрочная» означает область использования, а не потерю при перезапуске. Историю продолжаем хранить в SQLite, хотя в prompt может входить только её хвост. Отдельное хранение слоёв достигается отдельными таблицами и репозиториями в одном файле SQLite; три отдельных сервиса для этого не нужны.

Профиль и долговременные заметки живут независимо от чатов. Удаление чата с задачей удаляет её рабочие данные, но сохраняет профиль и подтверждённые долгосрочные записи. Это поведение описывается в форме удаления. Источник такой записи может стать недоступен после удаления чата; сама запись хранит краткое описание происхождения и не удаляется каскадно вместе с источником.

### Явная политика записи

1. Переписка записывается как факт взаимодействия; она не превращается автоматически в профиль или инварианты.
2. Пользователь может заполнить карточку задачи и отредактировать разрешённые рабочие поля напрямую.
3. При необходимости агент предлагает структурированное изменение: слой, поле, новое значение, основание и источник. Предложение отображается до применения.
4. Рабочие сведения из сообщения, особенно ограничения, принимаются через подтверждение карточки или предложения. Сгенерированные план, код и отчёт сохраняются как **черновые артефакты**, что не означает их утверждение.
5. Любое продвижение информации в долгосрочную память требует явного действия «Запомнить для следующих задач». Пользователь выбирает или подтверждает слой.
6. Профиль и инварианты изменяются отдельными действиями UI/API. Обычная фраза в чате их не переписывает.

Для записей: `id`, область владения, ключ/тип, значение, версия, источник, время, автор изменения и статус подтверждения. Для proposals: целевая версия данных и состояния `pending/accepted/rejected`. Изменившиеся исходные данные делают старое предложение непригодным к слепому применению.

Источник привязывается к стабильному ID сообщения или артефакта. Добавляем отдельный DTO сохранённого сообщения с ID; транспортный `Message(role, content)` для LLM не обогащается внутренними метаданными БД.

`MemoryWritePolicy` проверяет допустимые поля и область записи. LLM возвращает предложение, а не SQL-команду или путь в хранилище. Произвольный ключ из её ответа не может изменить статус задачи, approval, профиль или правило.

### Чтение и сборка контекста

Контекст для нового агента состоит из инструкций роли и этапа, действующих инвариантов, профиля, выбранных долговременных записей, рабочей памяти и последних N сообщений с текущим запросом. Каждый смысловой блок добавляется один раз.

Для небольшого объёма учебной памяти — явный выбор активных заметок пользователя и фильтрация по профилю/агенту, без embeddings и векторной БД. UI показывает включённые записи. Обязательные правила и рабочее состояние не выбрасываются скрытно ради экономии токенов. Сохраняем наблюдение за лимитом модели и прозрачный учёт всех переданных блоков.

Прежнее правило Sticky Facts «последующие сообщения имеют приоритет» не применяется к утверждённым инвариантам. Свободный текст заметки или сообщения не становится системной командой.

## 6. Персонализация

`UserProfile` содержит имя, язык объяснения, уровень подготовки, желаемую подробность, формат и мягкие предпочтения. Начальные примеры: «Новичок» и «Опытный разработчик». У задач профиля есть собственные жёсткие условия; обязательные правила с Дня 14 задаются как инварианты.

Предпочтение «обычно отвечай коротко» можно переопределить запросом «сейчас объясни подробнее». Инвариант «решение только на Python» так не переопределяется. В UI мягкие предпочтения и обязательные ограничения обозначаются раздельно.

Профиль включается в каждый основной запрос агента. Служебные запросы получают профиль как типизированные данные, но их JSON-схема и служебные инструкции имеют приоритет над стилем ответа. Обновлённая версия профиля применяется со следующего запроса; снимок версии записывается у каждого запуска. Изменение профиля не подменяет профиль уже существующей задачи другим ID.

## 7. Задача, артефакты и автомат

Базовая `Task` появляется на Дне 11 как контейнер условия и рабочей памяти. С Дня 13 она получает `TaskState`:

```text
phase: planning | execution | validation | done
status: active | paused
current_step_id: ссылка на конкретный шаг текущего плана
expected_action: тип ожидаемого действия
revision: версия состояния
```

`paused` — отдельный статус, поэтому пауза не стирает фазу. Текущий шаг связан с сохранённым планом и результатами, а ожидаемое действие вычисляется backend по состоянию и доступным артефактам. Не поручаем LLM свободно придумывать статус.

Сохранённый план содержит шаги со стабильными ID, а каждый артефакт — собственную ревизию. С Дня 15 подтверждение ссылается на конкретные версии: `approved_plan_revision`, `validated_solution_revision`, ревизию инвариантов и ID отчёта. Одного глобального `approved=true` недостаточно.

### Различие Дней 13 и 15

День 13: явные фазы, допустимый порядок, пауза, восстановление и действия UI. Пользователь двигает задачу по графу событий; backend уже отклоняет неизвестные состояния и скачок `planning → done`. Это минимальная корректная реализация конечного автомата.

День 15: содержательные условия этих переходов и ограничения **поведения** агента. Утверждение должно относиться к актуальному плану; validation — к актуальному решению; текст «сразу напиши код» не должен выдавать реализацию в обход стадии. UI и прямой HTTP-запрос проходят одну серверную политику.

Целевой граф к Дню 15:

| Из | Событие | В | Условие |
| --- | --- | --- | --- |
| planning | `approve_plan` | execution | план существует, относится к актуальным условиям и прошёл проверку ограничений |
| execution | `submit_solution` | validation | решение связано с утверждённым планом; обязательные статические проверки успешны |
| validation | `request_changes` | execution | сохранены замечания и шаг, требующий исправления |
| validation | `accept_validation` | done | отчёт для текущего решения существует, принят пользователем, нет блокирующих замечаний |
| execution/validation | `request_replan` | planning | явно создана новая версия плана, старые approvals и validation аннулированы |
| любая активная незавершённая фаза | `pause` | та же фаза, paused | текущий шаг и данные сохранены |
| paused | `resume` | та же фаза, active | восстановлены прежний шаг и ожидаемое действие |

После `done` задача доступна для чтения и сохранения знаний. Новое решение или пересмотр завершённой задачи оформляется новой задачей в объёме этой недели. Пауза в `done` не нужна: работы уже нет.

Новый код аннулирует проверку предыдущей версии решения. Изменение условия, плана или обязательных правил сбрасывает связанные подтверждения и возвращает задачу на согласование плана. Косметические изменения профиля не меняют уже утверждённые технические требования.

### Пауза во время запроса и устойчивость

Пауза сохраняется независимо от выполняющегося HTTP-запроса к LLM. Она повышает ревизию задачи. Если ответ пришёл после паузы или после изменения правил, его метрики учитываются, но он не продвигает задачу и не применяется как актуальный артефакт. UI объясняет, почему результат устарел. Уже отправленный вызов может быть оплачен даже при отмене ожидания клиентом.

При перезапуске незавершённый run становится `interrupted`; автоматических повторных платных вызовов нет. Состояние и артефакты последнего подтверждённого шага сохраняются. Продолжение запускается явным действием пользователя.

## 8. Инварианты и проверки

`TaskInvariant` хранится отдельно от переписки: ID, тип, параметры или текст правила, область `task_id`, ревизия, автор и активность. Для первой версии инварианты принадлежат задаче; профиль задаёт мягкие предпочтения. Общие для всех задач жёсткие правила можно будет вынести отдельно при появлении такого требования.

У алгоритмического агента два вида проверок:

1. **Детерминированные:** разрешённый этап и вид действия, Pydantic-схема, Python-синтаксис, сигнатура, запрещённые импорты. Для запрета внешних библиотек — явный список разрешённых импортов и блокировка поддерживаемых форм динамического импорта. Это проверка учебного артефакта, не sandbox выполнения кода.
2. **Семантические:** выбранный подход, отсутствие изменения входа, обоснование сложности. Здесь agent-specific judge сопоставляет запрос/результат с правилами и возвращает `pass / conflict / uncertain` и ссылки на правила.

LLM-judge может ошибаться. Формулируем гарантию точно: backend детерминированно запрещает недопустимые переходы и выдачу кандидата, который не прошёл настроенные проверки; абсолютной семантической гарантии для произвольного текста нет. Для сложных алгоритмических утверждений нужна отдельная проверка или реальное выполнение тестов.

Проверяем конфликт до генерации, затем проверяем сгенерированный артефакт до показа и применения. При `conflict`, `uncertain`, недоступном judge или ошибке его JSON не выдаём непроверенный кандидат как допустимое решение. Возвращаем понятное объяснение и сохраняем состояние. Бесконечных повторов генерации нет; новый запрос проверки выполняется явно.

Пример отказа: «В этой задаче закреплён Python. Предложение использовать Java нарушит правило “Язык решения”. Могу продолжить на Python; изменить само правило можно в карточке задачи». Отказ связан с конкретным правилом, а не общим сообщением «ошибка валидации».

Judge имеет отдельную конфигурацию модели, разрешённую сервером, и использует общий LLM-router/учёт токенов. По умолчанию при реализации выберем доступную модель из текущего каталога; это не зависит от модели Codex, которой пишется код. Не переносим Java-реализацию judge в Python механически.

## 9. Обращение к агенту и хранение результатов

Целевой проход после Дня 15:

1. Проверить принадлежность чата, задачи и профиля. Загрузить их версии.
2. Обработать явную команду UI/API через сервис задач или сохранить обычное пользовательское сообщение.
3. Проверить статус, допустимость действия на текущей фазе и конфликт с инвариантами.
4. Собрать именованные блоки памяти и профиль, записать снимок состава контекста и оценку токенов.
5. Выполнить LLM-запрос. Ответ — внутренний типизированный кандидат, а не произвольная запись состояния.
6. Проверить JSON, тип артефакта, правила и семантические ограничения, отобразить его в читаемый ответ.
7. В короткой транзакции сверить версии, сохранить принятый ответ/черновик/предложения и события. При конфликте версии результат не применять.
8. Вернуть ответ и обновить UI через API рабочего пространства задачи.

Служебные извлечения, основной ответ и judge учитываются отдельно: новые `purpose` добавляются вместе с соответствующим днём. Не делаем повторное извлечение facts всего диалога, когда нужная информация уже есть в подтверждённой рабочей памяти.

`InputPolicy` и `OutputPolicy` существующего диалогового агента работают с текстом. Новые проверки stateful-агента должны дополнительно получать типизированный снимок задачи. Добавляем нужные контракты к новому модулю, не меняя массово сигнатуры всех прежних политик.

Для структурированных результатов применяем Pydantic-модели с запретом лишних полей. Отдельные типы ответа позволяют различать объяснение, план, реализацию и отчёт. На Дне 15 сервер разрешает только типы, соответствующие этапу; семантическая проверка дополнительно проверяет обход через текст объяснения. Название JSON-поля само по себе не доказывает соблюдение стадии.

Для детерминированных отказов нужно честное происхождение результата: добавить совместимый вариант `source=policy` и допустимость отсутствующего `model`, либо отдельное типизированное событие отказа в контракте. Перед реализацией выбрать один вариант и обновить тесты клиента; не приписывать отказ несуществующему вызову LLM. Предпочтительный вариант — `source=policy`, `model=null`.

### Данные и транзакции

Новые таблицы вводятся миграциями по дням: `profiles`, `tasks`, `task_memory`, `task_artifacts`, `long_term_memory`, `memory_proposals`; далее `task_events`, `task_invariants`, `task_approvals`. Значения предметных моделей можно хранить JSON-колонками с Pydantic-валидацией; идентификаторы, связи и версии — явными столбцами.

Новый `SqliteTaskUnitOfWork` объединяет изменения задачи, артефактов и событий в одну транзакцию. Внутри неё нет внешних LLM-вызовов. Репозитории новых модулей принимают одну connection в этом сценарии: несколько независимых auto-commit методов не обеспечат атомарность.

Команды состояния и отправки имеют `command_id`; повтор команды не создаёт второй переход или дубликат сообщения. Проверка `expected_revision` и условный UPDATE защищают от устаревшего UI. Для одного task_id допускается один активный запуск; пауза и отмена имеют отдельный путь. Зафиксированное выполнение возвращается повторно, незавершённое — явно помечается; неопределённый исход сетевого вызова не повторяется автоматически под видом гарантии exactly-once API.

Первый миграционный шаг должен распознать существующую схему Дня 10 без удаления данных. Новые таблицы не пересоздают существующие чаты. Для сдачи дней используем отдельные Docker Compose project names и volumes, поэтому схема Дня 15 не открывается backend из Дня 11. При необходимости переносится копия БД с миграцией вперёд, а исходный volume сохраняется.

## 10. API и интерфейс

Сохраняем текущий чат по центру, список чатов слева и настройки справа. В выборе агентов появляется «Алгоритмический наставник». Новый frontend-проект не требуется.

При создании задачи выбирается профиль и вводится название/условие. Для нового агента не показываем несовместимые стратегии Branching/Sticky Facts. Выбор модели и лимита ответа остаётся возле текущих элементов управления; состояние задачи не сбрасывается от смены модели.

Справа по дням добавляются панели:

- **День 11:** «Память» с тремя слоями, источниками, предложениями и кнопками сохранения/удаления; карточка условия задачи.
- **День 12:** «Профиль» с предпочтениями, выбором при создании и явным отображением действующей версии.
- **День 13:** «Задача» с фазой, текущим шагом, ожидаемым действием, кнопками паузы/продолжения и журналом событий.
- **День 14:** «Обязательные правила» и объяснения конфликтов.
- **День 15:** доступные действия этапа и причина недоступности остальных, подтверждения плана/проверки.

Панели получают отдельные Vue-компоненты и composables (`features/memory`, `features/profiles`, `features/tasks`, `features/invariants`). `useAgentChat` не должен становиться единственным местом логики всех новых функций. `AgentInfo.capabilities` управляет видимостью, а backend самостоятельно проверяет поддержку операций.

Основной run сохраняет привычный контракт чата. Новые маршруты рядом: чтение рабочего пространства задачи, редактирование памяти, принятие предложения, работа с профилем и событиями задачи. Изменение phase прямым PATCH произвольной строки не предоставляется; API принимает именованное событие и версию.

Ошибки различимы: `409 state_conflict`, `409 transition_not_allowed`, `409 task_paused`, `422 invariant_conflict`; техническая ошибка провайдера не маскируется как отказ по правилу. Запрещённая команда не изменяет фазу или рабочую память. Показываем допустимое следующее действие.

Для демонстрации расширяем MD-отчёт снимками слоёв, профиля, этапа, событий, правил, источников validation и метрик. Каждый день имеет воспроизводимый сценарий в `docs/dayNN-guide.md`.

## 11. Итерации, ветки и критерии приёмки

Порядок веток накопительный: `ai-challenge-day-10` → `ai-challenge-day-11` → `ai-challenge-day-12` → `ai-challenge-day-13` → `ai-challenge-day-14` → `ai-challenge-day-15`. Ветка каждого дня создаётся от проверенного коммита предыдущего. В ней есть все предыдущие задания, но нет реализации следующих дней.

После этапа: релевантные тесты, сборка, запуск Docker, ручной сценарий пользователя и отдельный коммит. Публикация веток и слияние в `main` — по команде пользователя. Архитектурный документ может описывать следующие дни заранее. Первым коммитом Дня 11 можно зафиксировать согласованный план, не добавляя код будущих заданий.

### День 11 — три слоя памяти

Ветка: `ai-challenge-day-11`.

1. Добавить отдельного алгоритмического агента и фабрику; зарегистрировать рядом с `dialogue`.
2. Ввести один локальный профиль-владелец, Task/ProblemSpec и миграции; пока без автомата фаз.
3. Реализовать три области памяти, типизированные proposals, проверки записи и явное подтверждение долгосрочного сохранения.
4. Подключить сборку контекста: последние N сообщений + рабочие данные + активные долгосрочные заметки. Добавить стабильные ID источников.
5. Добавить UI памяти, карточку задачи и отчёт, объясняющий включённые записи.
6. Проверить изоляцию задач, восстановление и влияние каждого слоя; написать руководство сдачи.

Приёмка: сообщение есть в истории; подтверждённое условие — в рабочей памяти; сохранённая учебная заметка — в долговременной. Новый чат/задача не получает старое условие, но видит выбранную заметку. Перезапуск сохраняет все три слоя. Ошибка LLM/JSON не затирает подтверждённые записи. Прежний dialogue-агент проходит регрессионные тесты.

Демонстрация: короткий хвост N=4, несколько реплик после сохранения условия, затем вопрос о задаче. Ранняя реплика может выпасть из хвоста, но подтверждённое условие остаётся в рабочем слое. Удаление выбранной заметки исключает её из следующего prompt.

### День 12 — профили

Ветка: `ai-challenge-day-12`, от завершённого Дня 11.

1. Расширить профиль типизированными предпочтениями и версией, добавить создание/редактирование и выбор при создании задачи.
2. Реализовать правила приоритета предпочтений и включение профиля в каждый запрос.
3. Изолировать долговременную память по профилю; добавить снимок версии в метрики/отчёт.
4. Подготовить два профиля и одинаковый вопрос с одинаковой моделью и рабочими данными.

Приёмка: новичок получает развёрнутый пример, опытный — компактный ответ; факты условия одинаковы. Новый чат автоматически использует выбранный профиль. Заметки одного профиля не попадают в другой. Изменение предпочтений действует на следующий запрос и не меняет прошлые снимки.

### День 13 — сохраняемый автомат

Ветка: `ai-challenge-day-13`, от завершённого Дня 12.

1. Добавить phase/status/current_step/expected_action и версии плана/решения/отчёта.
2. Реализовать базовый граф событий, журнал переходов и проверки переходов на backend.
3. Подключить UI этапов, паузу и продолжение с сохранением конкретного шага.
4. Ввести атомарное сохранение результатов, проверку ревизий, повтор команды без дубликатов и восстановление interrupted runs.
5. Проверить паузу в planning, execution и validation, а также ответ LLM, пришедший после паузы.

Приёмка: после перезапуска агент показывает прежний этап, шаг и ожидаемое действие, использует сохранённые артефакты. Прямой переход planning → done отклоняется. Ошибка API не переводит задачу вперёд. Пока нет полного набора бизнес-условий approvals Дня 15.

### День 14 — инварианты

Ветка: `ai-challenge-day-14`, от завершённого Дня 13.

1. Ввести отдельное хранилище правил, версии и явное редактирование.
2. Добавить проверки запроса/кандидата, AST-проверки и предметный семантический judge.
3. Сохранять результаты проверки и затраты judge отдельно; отказы формировать с ID правила и допустимым продолжением.
4. Подключить UI правил и предупреждений; при изменении правил делать связанные артефакты устаревшими и возвращать задачу к планированию.
5. Проверить конфликт, допустимый запрос, неопределённый verdict, невалидный JSON и недоступность judge.

Приёмка: просьба «реши на Java» конфликтует с закреплённым Python; кандидат со сторонним импортом не публикуется как допустимое решение. Рабочее состояние после отказа не меняется. Запрос «игнорируй предыдущие ограничения» не удаляет правила. Отдельно показать, что сложность и семантика проверяются моделью, а не доказываются статическим анализом.

### День 15 — условия переходов и защита от обхода

Ветка: `ai-challenge-day-15`, от завершённого Дня 14.

1. Добавить подтверждения конкретных версий плана и validation, условия графа переходов.
2. Ограничить допустимые действия и артефакты для текущей фазы; проверить текстовый обход стадии через обычный чат.
3. Связать изменения кода/плана/условий/правил с аннулированием устаревших подтверждений.
4. Обновить UI доступных действий и причин блокировки, экспортировать журнал жизненного цикла.
5. Провести сквозной сценарий с паузой, перезапуском, ошибкой LLM, двумя конфликтующими командами и попытками перескочить этап.

Приёмка: реализация недоступна без актуального утверждённого плана; done недоступен без принятого отчёта по текущей версии решения. Нельзя принять старый validation после изменения кода. При паузе переходы работы блокируются, после resume продолжается тот же шаг. Прямые HTTP-вызовы дают те же ограничения, что UI.

## 12. Общий сценарий сдачи и проверка

Одна последовательность расширяется по дням:

1. Создать задачу Two Sum, ввести условие и примеры, подтвердить рабочую карточку.
2. Сохранить учебную заметку для будущих задач и показать три слоя с источниками.
3. Сравнить объяснение дополнения `target - value` для двух профилей.
4. Получить план, перейти к реализации, остановиться на шаге обработки дубликатов, перезапустить backend и продолжить.
5. Закрепить Python, сигнатуру и отсутствие внешних библиотек; запросить Java и увидеть мотивированный отказ.
6. В новой задаче попросить код до утверждения плана; затем пройти разрешённый путь. Попробовать done до validation и принятие устаревшего отчёта.

Примеры для отчёта проверки: `[2,7,11,15], target=9`; `[3,3], target=6`; отрицательные значения; отсутствие пары; пустой массив согласно нашему условию. Проверяются разные индексы и нужная сумма; если пар несколько, сравнение не привязывается к одной конкретной паре. Список ожидаемых примеров не обозначается выполненными тестами без источника выполнения.

Автоматические тесты backend используют fake LLM и временную SQLite: области памяти, подтверждения, изоляция профилей, граф и условия переходов, сбои, конфликт версий и восстановление. Проверки клиента покрывают пользовательские действия и отображение блокировок. Проверка состава prompt явно подтверждает слои, отсутствие дублирования нового сообщения и отсутствие чужих данных.

Реальные LLM-прогоны выполняются целевыми сценариями после локальных тестов; сохраняются ответы, фактический usage и источник проверки. Для оценки персонализации и памяти показываем реальные отличия ответов, не делаем вывод только из успешного unit-теста. Ключи и БД с личными диалогами остаются вне Git.

## 13. Решения на согласование и статус работ

Предлагаемые исходные решения:

- Предметная область: алгоритмический наставник с задачами, вводимыми текстом.
- Один новый агент на все пять дней, новые возможности добавляются последовательно.
- Один чат соответствует одной задаче; профиль выбран при создании; повторное открытие продолжает ту же задачу.
- Общие механизмы подключаются к агенту; его предметные policy, validators и judge остаются в собственном пакете.
- Продвижение в долгосрочную память и утверждение значимых решений — явные действия пользователя.
- SQLite, Pydantic и текущий Vue-клиент; без новых внешних систем памяти и без автоматического запуска произвольного кода.
- На Дне 13 — базовый граф; на Дне 15 — подтверждения версий и проверка содержательных условий перехода.
